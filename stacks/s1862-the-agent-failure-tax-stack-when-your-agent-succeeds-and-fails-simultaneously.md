# S-1862 · The Agent Failure Tax Stack — When Your Agent Succeeds and Fails Simultaneously

Your agent runs without errors, produces confident outputs, and fails in ways that look like success. It loops silently for 35 minutes, confabulates policies that never existed, incrementally exceeds cumulative limits one transaction at a time, and pushes broken infrastructure because it can't distinguish manual overrides from drift. The failure mode is not a crash — it is a confident wrong answer that costs real money.

## Forces

- **Agents fail silently; traditional software crashes loudly.** A web service that goes down logs a stack trace. An agent that goes wrong returns HTTP 200 with plausible nonsense. The absence of error codes means absence of alerting — unless you build semantic failure detection explicitly.
- **Failure accumulates before it surfaces.** The $1.2M refund agent didn't breach its per-transaction cap — it issued 340 transactions each under $500, each evaluated in isolation. The voice agent told 200 customers a non-existent policy. Single-action guards miss cumulative failure.
- **Recovery strategies that work for traditional systems break agents.** Exponential backoff fixes transient API errors but does nothing for semantic errors (plausible wrong answers). A circuit breaker stops cascading API failures but cannot catch a model confidently hallucinating tool arguments. You need a taxonomy before you can apply the right remedy.
- **Agents introduce irreversible action risk.** Unlike a crashed microservice that retries harmlessly, an agent that sends an email, pushes a commit, or issues a refund cannot undo the action. Recovery must be designed before the action is taken, not after it fails.

## The Move

A layered failure architecture with four distinct recovery tiers, applied based on error classification — not a monolithic retry loop.

**Tier 1 — Error Classification First.** Before attempting recovery, classify the failure type. Transient API errors (503, timeout, 429) get retry. Client errors (400, auth) get fixed-or-escalate. Semantic errors (confident wrong answers, policy confabulation) get grounded verification — never retry blindly. An agent that retries a hallucination compounds it.

**Tier 2 — Circuit Breaker with Jitter.** Wrap every LLM call, tool call, and inter-agent message in a circuit breaker with three states: closed (normal), open (fallback active), half-open (testing recovery). Trip on >50% failure rate over a sliding window with a minimum request count, or on consecutive failures. Prevent thundering herd: exponential backoff with jitter reduces retry storms by 60–80% versus fixed intervals (AWS distributed systems research). Jitter is not optional — synchronized retries recreate the failure.

**Tier 3 — Bounded Recovery Ladder.** When an agent loops or deadlocks, climb a fixed escalation path rather than unbounded retry: (1) nudge — inject a prompt redirect; (2) replan — re-prompt with the original goal; (3) reset — clear conversation history and restart; (4) escalate — human review with full decision tree. Each rung has a step limit. Never let the agent run indefinitely.

**Tier 4 — Checkpoint/Resume + Human Escalation.** Serialize agent state after each successful tool call — conversation history, accumulated results, current plan. On failure, resume from the last checkpoint rather than restarting. For irreversible actions (refunds, commits, emails), require a mandatory summary step and human confirmation before execution. Idempotency is not optional: design every step so re-running produces the same result.

**Tier 5 — Graceful Degradation Hierarchy.** When full capability is unavailable, fall through explicitly: Level 1 (primary model, all tools, real-time data) → Level 2 (fallback smaller model, e.g., Haiku instead of Opus) → Level 3 (cached pre-computed responses). Mark degraded responses with metadata so consumers know the quality level.

- **Real incident — E-commerce refund agent (Q3 2025):** Agent issued ~$1.2M in unauthorized refunds across 340 transactions before detection. Per-transaction cap ($500) existed but cumulative spend was not tracked. Root cause: evaluated each transaction in isolation. Fix: cumulative refund caps per customer session + mandatory summary step before high-value refunds. — [Agentbrisk: AI Agent Failures: Real Incidents](https://agentbrisk.com/blog/ai-agent-failure-modes-real-incidents/)
- **Real incident — Claude Code Terraform drift (January 2026):** Agent with full repo access removed a manually-added security group rule blocking port 5432. The rule was an emergency measure the agent couldn't distinguish from unintended drift. Root cause: no do-not-remove annotation convention for manual overrides. Fix: DO_NOT_REMOVE tagging system + human approval required for security group changes. — [Agentbrisk: AI Agent Failures: Real Incidents](https://agentbrisk.com/blog/ai-agent-failure-modes-real-incidents/)
- **Real incident — Voice AI retention agent (mid-2025):** Agent told callers a non-existent 90-day money-back guarantee existed, creating $340K liability across 200 customers. Agent confabulated a plausible-sounding policy when it lacked a clear answer. Root cause: no policy constraint in system prompt; absence of firm policy triggered generation rather than refusal. Fix: explicit policy grounding — agent can only reference structured policy database; I-dont-know is a required valid response. — [Agentbrisk: AI Agent Failures: Real Incidents](https://agentbrisk.com/blog/ai-agent-failure-modes-real-incidents/)
- **Production deployment deadlock (verbatim):** "A context-monitor component repeatedly fired a new-session event at 6-minute intervals, each spawning a new memory-sync subagent. With no guard checking whether a sync was already running, multiple subagents competed for the same memory files, token budgets, and session state. The result was a 35-minute hang until an external watchdog sent a process signal." Fix: a single check — is a sync task already running? — [Zylos AI Research: AI Agent Self-Healing and Failure Recovery](https://zylos.ai/en/research/2026-05-06-agent-self-healing-failure-recovery)
- **HN community — eval-first principle:** "Evaluations are vital for improving performance. Without evals, you really do not know if you are moving the needle at all." LLM-as-judge has extreme confirmation bias — inflated scores unless paired with human-labeled golden datasets for critical paths. — [Hacker News: Principles for production AI agents (128 points)](https://news.ycombinator.com/item?id=44712315)
- **HN community — idempotency and observability:** "Agent operations should be designed so that re-running the same step produces the same result, enabling safe retries." Full decision tree replay (not just final outputs) is required for debugging multi-agent chains. Standard distributed systems observability (OTEL, tracing) works for latency/token counts but breaks down for inter-agent coordination debugging. — [Hacker News: Debugging multi-agent AI workflows](https://news.ycombinator.com/item?id=47358618)

Separate breakers at three boundaries: LLM API calls, external tool calls, inter-agent communication. — [Brandon Lincoln Hendricks: Circuit Breaker Patterns for AI Agent Reliability (2026-03-25)](https://brandonlincolnhendricks.com/research/circuit-breaker-patterns-ai-agent-reliability)

## Gotchas

- **Retry loops amplify semantic errors, not just API errors.** Blind retry on a confident wrong answer produces a confident wrong answer faster. Classify errors before retrying.
- **Per-transaction guards miss cumulative failure.** Any time an agent controls a cumulative resource (spend, usage, access), you need a running total guard, not just per-action limits.
- **Agents cannot distinguish manual overrides from drift.** If your infrastructure has emergency measures that bypass normal configuration, annotate them explicitly (e.g., DO_NOT_REMOVE tags). The agent will otherwise "fix" them.
- **Silent quality degradation is the hardest failure to detect.** The agent produces outputs and takes actions. No errors are raised. Quality drifts because the model version changes, the context gets contaminated, or external API formats shift. Continuous evaluation suites against production outputs are the only detection mechanism.
- **Jitter is not optional on retry backoff.** Without jitter, all retrying agents wake up simultaneously and recreate the failure they are trying to recover from. Use uniform or exponential jitter on all retry delays.
