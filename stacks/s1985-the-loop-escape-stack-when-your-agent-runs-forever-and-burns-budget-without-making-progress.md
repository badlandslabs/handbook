# S-1985 · The Loop Escape Stack — When Your Agent Runs Forever and Burns Budget Without Making Progress

[Your AI coding agent is three hours into a debugging task. It has made 847 tool calls, written and deleted 2,400 lines of code, and consumed $1,200 in API credits. It is not closer to solving the problem than it was at call #3. It is looping — retrying the same wrong approach with minor variations, unaware it has stalled. Traditional software crashes and gives you a stack trace. AI agents return 200 OK while silently burning budget and degrading their own context. Loop detection, circuit breakers, and structured recovery must be engineered in, not hoped for.]

## Forces

- **Compounding failure rates make loops inevitable.** A 95% one-shot success rate sounds impressive. Four tool calls at 95% each = 81% reliability. Each additional step multiplies failure probability. Real agentic workflows require 10–20+ tool calls, which collapses reliability to unusable levels without explicit recovery. The math doesn't lie: loops are not edge cases — they are the statistical default.
- **Agents look identical when stuck vs. working hard.** Activity proxies — API call counts, file edits, log volume — rise in both stuck loops and slow-but-converging legitimate work. You cannot distinguish failure from effort without measuring actual progress toward the goal, not busyness.
- **Mutation happens before you detect the problem.** When an agent's tool call mutates external state (SQL DELETE, filesystem write, API POST) and subsequently fails, the damage is already done. The agent returns a 200, reports success, and the side effects persist. Recovery must be engineered *before* the mutation, not after the error surfaces.
- **Per-call retry limits create cascade amplification, not containment.** When a provider returns 429s, per-call retry logic without global coordination causes retry amplification: each of 100 concurrent agent runs retries independently, multiplying load and prolonging the outage. Containment must be global, not per-call.

## The Move

**Layer 1 — Circuit breakers (hard stops):** Set independent safety limits that halt execution unconditionally when breached. Use *composable* rules evaluated at the orchestration layer, not just `max_tokens` on a single call. The four signals: (1) iteration count — N steps without task completion, where N is tuned per task type; (2) cost cap — hard ceiling on total spend per run, independent of per-call limits; (3) time budget — wall-clock timeout, especially critical for multi-step reasoning; (4) repeated error signal — same tool fails N times with the same error class (e.g., rate limit), indicating a systemic rather than transient problem.

**Layer 2 — Stuck-loop recovery ladder:** When a loop detector fires, climb a bounded escalation ladder rather than immediately escalating to human handoff. Progression: (1) *nudge* — inject a prompt fragment reminding the agent of what has already been tried and asking it to propose a new approach; (2) *replan* — have the agent re-decompose the task from scratch with explicit acknowledgment of prior failures; (3) *context reset* — truncate conversation history to the last checkpoint and restart from there; (4) *human handoff* — escalate to a human with full trajectory and error summary. The ladder prevents both premature escalation and endless recovery loops.

**Layer 3 — Progress-based detection:** Distinguish stuck from slow with a metric that *only* increases on real work: failing tests resolved, unique sources gathered, checklist items completed, assertions passing. Do not use activity volume (API calls, file edits, log lines) as a progress proxy — it rises during both productive and stuck behavior. The detector fires only when the progress metric is flat across N consecutive heartbeats.

**Layer 4 — Checkpointing and state persistence:** Snapshot the agent's full state (conversation history, tool results, intermediate outputs, decision rationale) at every step boundary. On failure or manual reset, resume from the last checkpoint rather than re-executing from the beginning. LangGraph's built-in checkpointers, OpenAI Assistants API thread persistence, and Temporal-style workflow snapshots all implement this pattern. Checkpointing is especially critical for long-horizon tasks where a mid-run failure would otherwise waste hours of work.

**Layer 5 — Rich error surfacing for self-correction:** When a tool call fails, surface the complete error response to the agent — status code *plus* response body, headers, and error message — not just a generic exception. Agents self-correct only when they can see *why* something failed. HTTP libraries using `raise_for_status()` discard the response body and leave the agent guessing. Complete error detail enables the agent to adjust subsequent calls rather than blindly retrying the same failed approach.

## Gotchas

- **Max iterations is too blunt an instrument.** A hard iteration cap stops productive slow work along with stuck loops. Tune per task type (debugging = higher limit than simple lookups) and combine with a progress metric rather than using iteration count alone.
- **Checkpointing without a rollback plan is incomplete.** Saving state is necessary but not sufficient — you also need a defined rollback action for each tool type (undo SQL with a transaction log, revert filesystem writes with version control, call a compensating API for external mutations). Without a defined undo action, checkpointing just lets you observe failure more clearly.
- **Circuit breakers that only monitor cost miss behavioral loops.** A loop that isn't expensive (small, fast tool calls with repeated failures) can run indefinitely without hitting a cost cap. The five-signal approach — cost, iterations, time, repeated errors, circular behavior — is more robust than any single signal. Implement at least three of the five for meaningful coverage.
