# S-2180 · The Schema Grounding Stack — When Your Agent Picks the Wrong Table and Then Reasons Perfectly From It

Your text-to-SQL agent scores 86% on Spider 1.0. Your data warehouse has 200 tables and 1,400 columns with three active SQL dialects, six years of organic naming conventions, and a deprecated `orders` table that still receives writes from a legacy service. The agent picks `orders` instead of `fact_revenue`. The query returns. The numbers are wrong. The agent is perfectly confident. This is the schema grounding problem: the failure happens before the model ever generates a token — it happens in what context the model receives.

## Forces

- **The benchmark-to-production collapse is real.** GPT-4o scores 86.6% on Spider 1.0 (5–30 tables, single dialect) and drops to 10.1% on Spider 2.0 (enterprise-scale schemas). No model upgrade closes this gap — it is an information architecture problem, not a reasoning problem (Spider 2.0, Y. Liu et al., 2025).
- **Table selection is the highest-leverage error.** Pinterest found that first-shot acceptance rates in production were around 20% — most rejections were table selection errors, not SQL syntax errors. The model generates valid SQL against the wrong schema (Tian Pan, tianpan.co, April 2026).
- **Context packaging kills models faster than context length.** A full DDL dump for 200+ tables exceeds what even long-context models can reliably attend over. The model receives every column name but not the foreign key semantics, join paths, or downstream table dependencies it needs to choose correctly.
- **"Hallucination" is the wrong label.** When a model picks `orders.amount` instead of `fact_revenue.net_revenue`, it is not hallucinating — it is making a plausible inference from insufficient grounding. The column names and table names are all correct. The business semantics are missing from the context.
- **Schema metadata is perishable.** Column names change, tables get deprecated, business logic evolves. A schema dump taken at index time can be stale within weeks. Agents have no signal that the canonical source for "net revenue" moved from `orders` to `fact_revenue` six months ago.

## The Move

- **Build a schema graph, not a schema dump.** Replace full-DDL-in-context with a precomputed knowledge graph over the database schema — foreign key relationships, join paths used by production queries, table lineage, and business-semantic labels. The agent queries the graph for relevant tables, not the raw schema for table names (Pretensor, pretensor.ai, May 2026).
- **Separate table selection from query generation as an explicit planning step.** Route the agent through a two-stage pipeline: (1) intent classification + table ranking via a lightweight model call, (2) full query generation against the selected tables. This lets you audit and validate table selection independently from SQL generation.
- **Anchor on business-semantic definitions, not column names.** Define canonical column aliases and business logic rules as structured grounding artifacts — e.g., "net_revenue = SUM(fact_revenue.amount) WHERE category IN ('sales', 'subscription') AND fact_revenue.type != 'refund'". The agent references these definitions rather than inferring business logic from column names.
- **Enforce a schema boundary contract.** Treat deprecated tables, shadow writes, and dual-write scenarios as first-class failures in the grounding layer — flag them at query planning time, not at result validation time. A deprecated table that still receives writes is a data quality hazard that surfaces as a model error.
- **Evaluate retrieval quality independently from answer quality.** Your eval suite should report: (1) did the agent retrieve the correct tables? (2) did it retrieve the correct columns? (3) did it apply the correct business logic? If you only measure whether the final answer is correct, you cannot tell whether to fix the index, the grounding artifacts, or the generation prompt.
- **Use permission-aware retrieval as a grounding filter.** In enterprise settings, the agent should only reason over tables the current user is permitted to access. This is both a security constraint and a relevance signal — restricting the schema surface reduces hallucination surface area (Devinity Solutions, devinitysolutions.com, May 2026).

## Gotchas

- **Dumping full DDL into context does not ground the agent — it overwhelms it.** Vector similarity search over a DDL corpus finds syntactic matches, not semantic relationships. A column named `net_amount` in a deprecated table will outrank a semantically correct column in a canonical fact table if the embedding model hasn't learned your schema conventions.
- **Benchmark performance is a lie about production readiness.** Spider 1.0 validates SQL generation against clean, canonical schemas. It does not test table selection under schema complexity, deprecated-table interference, or multi-dialect translation. A model that scores 90% on Spider 1.0 and 10% on Spider 2.0 is not "90% production-ready" — it is validated on a task that doesn't resemble production.
- **Business logic lives outside the schema.** The column `amount` means different things in different tables (pre-tax vs post-tax, gross vs net, including refunds vs excluding them). The schema encodes types, not semantics. If you don't encode the semantic definitions the business actually uses, the agent will infer them from column names and get them wrong at scale.
- **Schema changes invalidate grounding silently.** An index over the schema DDL will return stale results after a migration. The agent will generate valid SQL against a schema that no longer matches the data. Version your grounding artifacts and build freshness checks into the retrieval pipeline.
