# S-2846 · The Amnesiac Resume Stack — When Your Agent Completes Step 4 of 8 and No One Tells It Where to Continue

An agentic workflow crashes at step 4 of 8. The developer restarts it. The agent begins at step 1 again — re-reads every document, re-calls every API, re-spends every token — and either repeats work or, worse, produces contradictory outputs because the world state has changed since step 3 ran. The agent has no memory of where it was. Recovery means starting over, or hands-on manual triage. This is the **Amnesiac Resume** problem: agents that can fail mid-execution but cannot resume from their last known good state.

## Forces

- **Agents have execution state but no durable checkpoint** — the agent's reasoning trace exists in context, not in storage. A crash, timeout, or restart wipes the trace and forces restart from scratch. The work done is not recoverable without manual intervention.
- **Idempotency is harder than it looks** — step 3 of your workflow might write a partial record, send an email, or create a resource. Rerunning it on resume could produce duplicate side effects, conflicting state, or errors that abort the second run. Raw checkpointing is not the same as safe resume.
- **Ambiguous failure masks the question "did step 3 actually happen?"** — a tool call can return a network error while the server-side operation succeeded. The agent doesn't know if it should retry. Retry risks duplication; skip risks omission. This is the core ambiguity of agentic state recovery.
- **Long-running agents amplify the blast radius** — a 3-step workflow that crashes is annoying. A 40-step coding agent that crashes at step 31 has burned significant compute and context. The cost of no-resume grows with agent complexity and autonomy level.
- **Checkpoint overhead competes with agent throughput** — saving state after every step adds latency and storage cost. Saving only on completion misses the window. The right checkpoint frequency is a non-obvious tradeoff between recovery granularity and performance.

## The Move

**Save durable checkpoints, validate tool outcomes, and build explicit recovery paths — not just retry loops.**

- **Emit a checkpoint after every meaningful step boundary.** Serialize: current goal, completed steps, tool results so far, and any side-effect IDs (created records, sent emails, transaction IDs). Store in a durable backend (Redis, Postgres, S3). Not just in the LLM context window — in external storage the agent can re-read on restart.
- **Treat tool call outcomes as uncertain until confirmed.** A successful HTTP response (200) doesn't mean the operation completed. Use idempotency keys, check for duplicate effects on retry, and prefer read-after-write confirmation patterns. The agent should verify state before proceeding, not assume success.
- **Build a recovery branch, not just a retry branch.** When the agent crashes, the recovery logic should: (1) re-read the checkpoint, (2) re-evaluate whether prior steps actually succeeded against live state, (3) skip confirmed completions, (4) retry only the steps whose outcomes couldn't be verified. This is more robust than blind retry or blind skip.
- **Use explicit step IDs with completion markers.** Instead of "step 3 is done," record "step-3: completed, output: {order_id: 12345, confirmed: true}." The recovery path reads these markers and knows exactly which steps are confirmed, which are unconfirmed, and which must be re-executed.
- **Implement partial-result acknowledgment at tool boundaries.** Tools that produce side effects should return a structured acknowledgment: `{status: "executed", resource_id: "...", verified: false}`. The calling code stores this. On recovery, the agent can re-query `resource_id` to confirm state without re-executing.
- **Budget recovery time in the failure plan.** When an agent crashes, give the recovery path a distinct (and cheaper) prompt: "You were at step N. The goal was X. Your last completed step returned Y. Proceed from step N+1." Don't re-run the full reasoning chain — give the agent the summary and a direct instruction to continue.

## Gotchas

- **"We'll just retry on failure" is not a recovery strategy.** Retry without idempotency verification causes duplicate side effects — duplicate emails, duplicate charges, duplicate database records. The retry logic must know whether the prior call succeeded before attempting again.
- **Context window loss on restart is the silent killer.** If your checkpoint is only in the LLM context, a crash wipes it. The checkpoint must be in durable external storage that survives process restarts, not just in memory or in the agent's working context.
- **Agents can produce confident partial completions.** A step that "looks" successful (HTTP 200, no error message) may have completed the wrong operation or completed it against stale data. Confidence in output does not equal verification of side effect. Always confirm state, not just response.
- **Checkpoint frequency is a tradeoff, not a binary choice.** Checkpointing after every tool call adds latency and storage overhead. Checkpointing only on step completion means the agent restarts from the last completed step and may re-execute sub-step work. The right answer depends on step cost and side-effect risk — not on defaulting to one extreme.
- **Recovery prompts are not the same as the original prompts.** When resuming, don't replay the full original context and re-prompt from the beginning. Give the agent a recovery brief: what was completed, what the current state is, what to do next. Full replay wastes tokens and risks the agent re-deriving a different plan.
