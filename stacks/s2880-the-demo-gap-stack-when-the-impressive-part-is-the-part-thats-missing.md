# S-2880 · The Demo Gap Stack — When the Impressive Part Is the Part That's Missing

Anthropic's "Building Effective AI Agents" guide gets 543 HN points and lands on every agent team's reading list. Six months later, the same teams are debugging agents that confidently do the wrong thing for six hours, make unauthorized API calls, or silently degrade because nobody added retry logic. The guide is correct. The teams following it forgot the scaffolding.

Agent demos look magical because the scaffolding is invisible. The demo shows the LLM, a tool call, and a result. It hides the five components that make production work: orchestration, tool layer, approval layer, memory layer, and observability layer. Teams that copy the visible pattern without the invisible ones ship unreliable agents and blame the model.

## Forces

- **The Anthropic pattern is the destination, not the starting point.** Anthropic recommends simple, composable patterns using direct LLM API calls. But their examples implicitly assume you have retry logic, observability, guardrails, and approval layers — they just don't show you how to build them. Starting with "just call the API" without the infrastructure produces fragile agents, not simple ones.
- **Frameworks obscure what they're actually doing for you.** LangChain and LangGraph handle retries, state management, and observability under the hood. When you swap them for "simple API calls," you gain debugging clarity but lose those abstractions — unless you rebuild them. Many teams discover this the hard way.
- **Model capability is not the bottleneck in production.** The Furmanets 2026 analysis put it plainly: "Models are strong; reliability comes from architecture + guardrails." Most agent failures in production are not model failures — they're tool contract breakage, missing retry logic, unbounded loops, or absence of approval workflows for high-risk actions.
- **The scaffolding is boring and underappreciated.** Orchestration, tool validation, memory, observability, and approval layers are engineering problems, not AI problems. They don't make for impressive conference talks.

## The move

Build these five components before you call your agent production-ready. They can be minimal — they just have to exist.

- **Orchestration layer** manages the agent loop: decide what to do next, call the LLM, parse the response, handle tool calls, detect completion or failure. A basic while-loop with a max-steps guard is fine. LangGraph, CrewAI, or OpenAI Agents SDK are fine if you understand what they abstract. Direct API calls are fine if you re-implement the abstractions yourself.
- **Tool layer** exposes capabilities via MCP or direct function-calling. Each tool needs input validation, output validation, and idempotency guarantees. Make side effects reversible or trackable. MCP (Model Context Protocol) has become the de facto standard — adopted by Anthropic, OpenAI, Microsoft, and Vercel — but tool contracts still need explicit schema validation on both sides.
- **Approval layer** intercepts high-risk actions before execution. Any tool call that writes data, sends messages, or triggers external systems needs a human-in-the-loop gate. This is not optional for agents in regulated environments, and it's wise even for internal tools. The approval can be async — the agent waits.
- **Memory layer** persists context across sessions. Context windows alone don't solve this: they're expensive at scale, attention degrades with length, and weeks of history exceed even 1M-token limits. A tiered memory architecture (working → episodic → semantic → procedural) with Mem0, Letta, Zep, or a custom implementation is the production standard. Letta benchmarks show that even plain filesystem retrieval scores 74% on memory tasks, which outperforms many naive vector-store implementations.
- **Observability layer** makes the agent auditable and debuggable. Log every LLM call, tool invocation, tool result, and agent decision. Without this, you cannot tell whether the agent is doing the right thing for the right reason. Key signals: tool call success/failure rate, LLM call latency, token consumption per task, and behavioral SLOs (did the task actually complete correctly, not just respond).

## Gotchas

- **Picking an orchestration framework without understanding its abstractions.** LangGraph handles state persistence, loop detection, and checkpointing. Calling the OpenAI API directly means you implement all of that yourself. Teams that reach for "simple" and then implement LangGraph-equivalent logic end up with more code and less debugging clarity than if they'd just used the framework with full understanding.
- **Building MCP integration without schema validation.** MCP has no built-in mechanism for tracking tool definition changes or requiring re-approval when tools change. A malicious or simply updated server can silently change tool behavior. Both sides need explicit input/output validation — pass unknown fields, and the agent may not notice the tool is behaving differently.
- **Skipping evaluation because the agent "looks right."** Behavioral regressions in agents are invisible to APM tools designed for crashes. An agent can respond and spend tokens while quietly doing the wrong thing. You need behavioral SLOs: task completion rate, correct-output rate, and error budget consumption tracked separately from uptime.
- **Assuming Anthropic's "simple patterns" means fewer components.** The Anthropic guide is an excellent north star. The five scaffolding components are what it takes to reach it in production. Copying the pattern without the infrastructure produces unreliable agents, not simple ones.
