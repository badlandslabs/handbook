# S-1906 · The Tool Bloat Stack — When Your Agent Has 300 Tools and Can't Decide Which One to Use

You scaffold your agent with the full MCP ecosystem: GitHub, Slack, Notion, Linear, Figma, Gmail, Drive, Calendar, and 295 more. The agent can do anything. The agent does nothing well — spending three steps figuring out which tool to call, calling the wrong one, or running out of context before it even starts the real task. Tool bloat is the new prompt injection: a failure mode that looks like capability.

## Forces

- **Tool definitions consume context before the task starts.** Every tool in an MCP manifest includes a full JSON schema of parameters. At 300 tools, you can burn 50K+ tokens before the agent fires a single relevant action. Anthropic documented this explicitly: direct tool calls load every definition upfront, and context consumption scales linearly with tool count — not with the subset relevant to any given task.
- **More tools means more failure modes at the tool boundary.** A wrong tool call returns an error the agent must recover from. With 300 tools, the search space for "wrong" expands dramatically. Agents trained on tool-calling benchmarks don't generalize to 300-tool manifests; they pick the nearest plausible match.
- **The tool catalog doesn't match the task.** Most tasks need 3-7 tools. The 293 tools the task doesn't need are pure overhead — context tax, latency tax, and confusion tax.
- **Tool ecosystem fragmentation creates integration debt.** MCP was designed as a server protocol — each provider exposes one. But using them together requires a gateway. Monday.com's team built an internal MCP gateway and hit scaling problems that led them to design an entirely new protocol (ATP): the problem wasn't the individual tools, it was managing hundreds of them through a single interface.
- **The alternative pattern is code, not tools.** Anthropic, the ATP team, and several open-source projects have converged on a different answer: give the agent a sandbox to write code that calls APIs, rather than giving the agent pre-defined tool schemas. The tool surface collapses to one or two primitives (code executor, shell) instead of hundreds of discrete tools.

## The Move

**Collapse the tool surface and let the agent write its own API calls.**

- **Start with two tools, not twenty.** One code executor (Python/sandbox), one file system. Everything else the agent needs, it calls via code. This is Anthropic's code-execution-with-MCP pattern — the MCP server provides the execution environment; the agent composes calls in code rather than selecting from a schema.
- **Use deterministic browser primitives before agent reasoning.** When web access is needed, prefer Playwright CDP (Playwright has 78,600+ GitHub stars, 45% QA automation adoption) with structured commands, and add agent screenshot+accessibility-tree reasoning only where the page is genuinely dynamic or unstructured. Don't send screenshots to the model when the URL, element IDs, and action are all known ahead of time.
- **Expose tools as a tool, not as a menu.** Instead of loading 300 MCP tool definitions, expose a "tools" tool that can list, describe, and call any available API. The agent fetches tool metadata on demand, not upfront.
- **Consider ATP (Agent Tool Protocol) for scale.** The team behind monday.com's MCP gateway (hundreds of tools, hundreds of developers) built ATP because MCP's server-protocol design created stateful complexity at the gateway layer. ATP treats OpenAPI specs as the source of truth and gives agents a code-execution runtime to call APIs directly — collapsing the gateway into a spec registry.
- **For persistent memory, use structured retrieval, not raw context.** SQLite-Memory (markdown-based, hybrid retrieval, offline-first) and SQLiteSession (OpenAI Agents SDK) show that vector databases and RAG are not the only path. A well-designed SQLite schema with FTS5 search outperforms a vector store for most agent memory use cases and requires zero infrastructure.
- **Browser automation: use browser-use or Playwright MCP.** The browser-use Python library wraps Playwright with an LLM loop receiving screenshot + accessibility tree. For teams needing hosted infrastructure, Browserbase provides cloud browser sessions. WebMCP (shipped in Chrome 146, Feb 2026) standardizes this further for cooperative websites.

## Gotchas

- **Loading all tool definitions at startup is the default in most frameworks.** LangChain, CrewAI, and the standard MCP client all load the full manifest upfront. You must opt into lazy/on-demand tool loading — it's not the path of least resistance.
- **browser-use agents sound simple but have real failure modes.** Screenshots are expensive (tokens), accessibility trees are noisy, and multi-step browser tasks compound errors. The sweet spot is structured web tasks with known UI patterns — not open-ended browsing.
- **"The agent can call any tool" is not the same as "the agent knows which tool to call."** Without task-relevant tool filtering, a large tool manifest is actively harmful. The agent will waste tokens and take wrong turns.
- **Memory bloat mirrors tool bloat.** Stuffing full conversation history into context doesn't preserve useful context — it buries it. External retrieval with selective context injection outperforms full-history stuffing across all tested model sizes.
