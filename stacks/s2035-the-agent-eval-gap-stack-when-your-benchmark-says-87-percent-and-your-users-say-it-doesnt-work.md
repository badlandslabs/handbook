# S-2035 · The Agent Eval Gap Stack — When Your Benchmark Says 87% and Your Users Say It Doesn't Work

Your agent scored 87% on your eval suite. You shipped it. Three users reported it deleted a staging database. Nobody noticed for six hours because your metrics dashboard showed no errors. Your benchmark only scored the final answer — not the trajectory that burned $340 in tokens, called the delete tool three times, and ignored the confirmation prompt. The benchmark was right. The agent was broken. The fix is not a better benchmark. The fix is evaluating the path, not the destination.

## Forces

- **The unit of evaluation is wrong.** A benchmark scores the last token. A production agent is a system — it plans, calls tools, observes results, recovers, and accumulates cost with every step. Scoring only the final answer misses where failures happen, how much they cost, and whether they were caught.
- **Benchmarks are reproducible but disconnected from production.** Lab benchmarks (MMLU, HumanEval, AgentBench, BIG-bench) use clean inputs and known answers. Production serves ambiguous requests, flaky APIs, adversarial inputs, and constraint-laden tasks. The lab-to-production gap averages 37% on comparable tasks (JobsByCulture, 2026).
- **Standard APM shows 200s while the agent silently fails.** Downstream tool calls returning schema-mismatched responses do not increment error rates — they return 200 and the agent continues confidently wrong. Silent failure propagation is the dominant failure mode in production agents at scale.
- **Two agents with identical accuracy can differ 50x in cost.** Trajectory efficiency — the number of steps, tool calls, and retries to reach the goal — is the dimension that benchmarks never score but that determines whether your agent is economically viable (JobsByCulture, 2026).
- **Constraint decay makes structural requirements invisible to benchmarks.** Agents trained on functional correctness benchmarks degrade sharply when required to satisfy structural constraints. Pass rates drop an average of 30 percentage points as architectural patterns, ORM rules, and database schemas accumulate (Dente et al., arXiv:2605.06445, May 2026).

## The Move

Evaluate the trajectory, not just the destination. Score four dimensions. Build regression from production failures.

- **Trajectory-first eval.** The eval unit is the full execution trace — every LLM call, tool invocation, memory read/write, and state transition. Score whether the path was efficient, whether required steps were present, whether loops or unnecessary retries occurred. Final-answer correctness is necessary but not sufficient.
- **Four-dimension scoring.** Track per-run metrics across: (1) task completion (did the user get what they needed?), (2) tool use quality (right tool, valid arguments, error recovery), (3) trajectory efficiency (step count within budget threshold, no loops), (4) cost efficiency (cost-per-task within tolerance). A per-dimension score tells you *where* the agent regressed.
- **Cost-per-task as primary production metric.** Model selection starts with "what does a finished unit of work cost, and how often does the model stay useful when the task stops looking like a chat prompt?" (WhatLLM / Artificial Analysis v4.1, June 2026). Two agents with identical accuracy can have 50x cost-per-task variance.
- **Regression pipeline from production failures.** Every confirmed production failure becomes an eval case. Vercel builds CI gates from production traces, ordered by cost impact (Vercel engineering, 2026). Oodle.ai reports teams storing all traces without sampling — agent non-determinism makes sampling unreliable for failure detection.
- **LLM-as-judge with judge calibration.** Use a stronger model to score open-ended quality dimensions. Calibrate the judge against human-rated samples: weaker judges produce systematic scoring bias. Budget judge calls for expensive evaluation on a sample, not every run.
- **Constraint-aware eval suite.** Beyond functional correctness, verify structural compliance — does the agent use the specified ORM? Does it respect the architectural pattern? Test with both loose and fully-specified prompts. A drop from loose to constrained specifies your constraint decay margin.

## Evidence

- **Engineering blog:** Vercel evaluates v0 and internal agents through production-like traces, CI gates, checks ordered by cost, and regression tests built directly from confirmed production failures — not from benchmark scores. — [Vercel AI Agent Evaluation Frameworks](https://vercel.com/i/ai-agent-evaluation-frameworks-production)
- **Research paper (arXiv):** Dente et al. systematically document "constraint decay" — capable agent configurations drop 30 percentage points in assertion pass rates from unconstrained to fully-specified multi-file backend generation tasks (80 greenfield + 20 feature tasks, 32 behavioral test requests, 291 assertions). Benchmarks reward functional correctness but miss structural compliance entirely. — [arXiv:2605.06445](https://arxiv.org/abs/2605.06445)
- **Research paper (arXiv):** Pandey identifies seven production failure modes at billion-event scale. Four are completely invisible to standard metrics; the remaining three are detectable only after a multi-cycle evaluation lag. Lab-scale benchmarks (HELM, MT-Bench, AgentBench) were designed for controlled single-session settings and do not address continuous production operation. — [arXiv:2605.01604](https://arxiv.org/abs/2605.01604)
- **Engineering blog:** Langfuse defines four eval dimensions with specific metrics per dimension: trajectory (step count, loops, required steps present), tool use (correct tool selected, argument validity, tool error rate), task completion (boolean judgment at root, resolution score), and cost/latency (p-budget thresholds). Start with one metric per dimension, add cost and latency as secondary signals. — [Langfuse AI Agent Evaluation](https://langfuse.com/resources/engineering/ai-agent-evaluation)
- **Engineering blog:** Harness Engineering observes that teams instrument output success/fail counts but not intermediate execution traces, causing silent failures to propagate undetected for days. Structural observability (nested spans preserving parent-child relationships across multi-agent handoffs) is required to detect the failure modes that error-rate dashboards miss. — [Harness Engineering: Agent Evaluation & Observability](https://harness-engineering.ai/blog/agent-evaluation-observability-in-production-ai/)

## Gotchas

- **A passing benchmark means nothing about production reliability.** A score of 87% on AgentBench predicts task completion on clean academic tasks — not on production traces with ambiguous inputs, flaky APIs, or structural constraints. Treat benchmark scores as necessary but insufficient.
- **Sampling traces loses failure signal.** Agents are non-deterministic — the same prompt produces different trajectories. Sampling 10% of traces means 90% of failure modes are never seen. Oodle.ai reports no-sampling as a design principle for this reason.
- **Error rate is a vanity metric for agents.** HTTP 200 does not mean the agent succeeded. Schema-mismatched tool responses, hallucinated API calls, and confident wrong conclusions all return 200. You need structured trace analysis to detect them.
- **Judge ceiling limits LLM-as-judge reliability.** The judge model must be at least as capable as the agent being evaluated. Using a weaker model as judge systematically underestimates failures — particularly invisible in nuanced quality dimensions like coherence and persona adherence.
- **Eval frequency must match deployment frequency.** Pre-deployment eval alone is insufficient — prompts drift, upstream APIs change, and constraint decay accumulates over time. Continuous production monitoring with trajectory scoring catches regressions before users report them.
