# S-2112 · The Custom-Agent Stack — When Your Framework Costs More Than It Saves

Your team starts a new agent project. You reach for LangGraph or CrewAI. Three months in, you have 14 dependency conflicts, an abstraction leak that makes tracing impossible, and a bug that only manifests inside the framework's internal event loop. Meanwhile, a team two desks over shipped the same agent with 200 lines of direct API calls, four Python files, and a print statement for logging. They finished in six weeks. The tooling ecosystem around agents is maturing fast — but the most successful production deployments are increasingly the ones that use the ecosystem as a component library, not a runtime.

## Forces

- **The MCP ecosystem solved integration, not orchestration.** Model Context Protocol has become the universal tool-integration standard — 97M+ monthly SDK downloads, 5,800+ servers, donated to the Linux Foundation with AWS, Anthropic, Google, Microsoft, OpenAI, and Block as platinum members. You get this for free. But MCP doesn't decide *how* your agent decides. That's orchestration, and it's still yours to own.
- **Frameworks abstract the easy parts and leak on the hard parts.** The happy path — sequential tool calls, simple routing — works beautifully in LangChain/LangGraph/CrewAI. The moment you hit retry loops, multi-agent handoffs with state, partial failures, or non-deterministic tool selection, you're fighting the framework. Teams consistently report that debugging framework internals takes more time than writing the agent logic from scratch.
- **Custom beats framework at production scale.** A systematic study of 20 production case studies found 85% (17/20) build custom in-house implementations with direct API calls; only 3 use external frameworks. Among teams surveyed (n=306), 70% rely on prompting alone — no weight tuning. The majority of agents (68%) operate within 10 steps before human intervention. These constraints make heavy framework overhead unjustifiable.
- **What you actually need from a framework is narrow.** If you extract what production teams actually use: a loop that calls an LLM, decides whether to use a tool, executes it, and feeds the result back — that's 50-100 lines. Anything more is either borrowed complexity or a dependency you'll eventually route around.

## The move

- **Use MCP for tool integration, build the loop yourself.** Let MCP handle the N×M connector problem (5 AI platforms × 10 tools = one MCP server per tool, not 50 custom integrations). Build the agent loop as a simple Python class or module that calls the LLM API directly. MCP clients exist for every platform; the orchestration logic doesn't need a framework.
- **Start with the augmented LLM pattern, not multi-agent.** Anthropic's "Building Effective Agents" research identifies that most tasks are solved by a single LLM augmented with tools, not orchestrated multi-agent systems. Use `mcp-agent` (lastmile-ai, 8.4K GitHub stars) or a direct implementation of the five proven patterns: augmented LLM, router, orchestrator-worker, evaluator-optimizer, and open-ended collaboration. Implement only what your use case actually needs.
- **Limit autonomy scope explicitly.** Production data shows 68% of deployed agents have ≤10 steps before human intervention. Define this in code — a step counter, a confidence threshold, a timeout — not as a emergent property of "the model will stop when done." The agent doesn't inherently know when to escalate.
- **Log trajectories, not just outputs.** The difference between a debuggable and undebuggable agent is whether you can replay the exact sequence of LLM calls, tool invocations, and decisions. Store each step: the prompt sent, the raw response, which tool was called (if any), the tool result, and the final output. This is your eval set, your incident log, and your regression suite.
- **Evaluate with real traces, not benchmarks.** 74% of production teams primarily use human evaluation, but this doesn't scale. The practical approach: collect trajectory traces from production, have humans label a sample (was the task actually completed? was the tool use correct? did the agent recover appropriately from failure?), and use those labels to score automated metrics. Chip Huyen's agent evaluation framework recommends measuring planning quality, tool usage accuracy, error adaptability, and goal achievement — not BLEU scores or perplexity.
- **Treat MCP servers as untrusted third parties.** 43% of published MCP servers have command injection flaws; 10 MCP plugins in a chain creates a >92% exploit probability. Apply zero-trust at the tool layer: validate all MCP tool responses against expected schemas before passing them to downstream systems, sandbox MCP tool execution, and audit the full MCP server list in production.

## Gotchas

- **LangChain's abstraction leaks under load.** When tool calls fail, when retries cascade, when the agent needs to backtrack — you end up debugging LangChain internals, not agent logic. The debuggability advantage of simple code disappears when you're nested inside framework event loops.
- **MCP's security surface is the new supply-chain risk.** The OWASP MCP Top 10 (MCP05:2025) documents command injection via prompt-driven execution, dynamic command construction, and chained tool execution. A Cursor RCE vulnerability (CVE-2025-61591) exploited MCP OAuth flows. Every MCP server you add is a new attack surface.
- **Custom doesn't mean reinvented.** Rolling your own loop doesn't mean ignoring MCP's patterns, LangGraph's state management concepts, or CrewAI's role definitions. Study them, borrow the good parts, but own the runtime so you can debug, profile, and patch it.
