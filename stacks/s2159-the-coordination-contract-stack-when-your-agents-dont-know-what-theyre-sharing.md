# S-2159 · The Coordination Contract Stack — When Your Agents Don't Know What They're Sharing

You have a multi-agent system: a researcher, a writer, and an editor, all operating in parallel. They read from the same shared context, write to the same output store, and occasionally overwrite each other's work. Nobody errors out. Everything looks fine. The final document is incoherent because the researcher and writer were both writing to section 3 simultaneously, and the editor never noticed. This is not a model quality problem. It is a distributed systems problem that nobody told you to solve — and it is the most common reason multi-agent systems fail in production without crashing.

## Forces

- **Agents don't infer what each other are doing.** Unlike human teammates who read body language and infer intent, agents operating on shared state have no implicit coordination. Two agents can write to the same key, overwrite the same file, or claim the same task without either realizing it. The output looks reasonable, so it passes through. — *Jason Brashear, ArgentOS / GitHub Gist*
- **State coordination is absent from most framework discussions.** LangGraph, CrewAI, and AutoGen all handle individual agent capabilities well. None of them natively prevent two agents from silently overwriting each other's work on shared state. This is a classic race condition — but in AI systems, the output looks plausible, so you don't notice it until production. — *Hacker News / paifamily*
- **Chat-style consensus protocols break down under parallel execution.** Agents sharing a conversation thread and trying to resolve conflicts in real time race to add the last word, produce verbose non-decisions, and eventually one agent just agrees with whatever was said last. Consensus is a bad protocol for parallel agents — you need explicit coordination primitives, not conversation. — *Hacker News / formreply*
- **Tool definitions consume context before the agent starts reasoning.** A single MCP server like Playwright can consume ~22% of a 200K-token context window just in tool descriptions. The more agents and tools, the more context is pre-consumed by infrastructure metadata, leaving less room for actual reasoning. — *Turion.ai / Balys Kriksciunas, March 2026*

## The move

Explicit coordination architecture: model multi-agent systems after distributed systems, not human teams.

- **Dispatch contracts, not shared threads.** Before handing work to an agent, create an auditable contract that records: task ID, target agent, timeout, heartbeat interval, expected output type. The orchestrator holds this contract as a gate — if the agent doesn't heartbeat or complete within the window, the orchestrator knows and can reassign or retry. This is a write-ahead log, not a chat message. — *Brashear, ArgentOS*
- **The blackboard pattern for shared state.** All agents read from and write to a shared "blackboard" — a structured store (file, database, Redis) with explicit ownership. Each section/key has one writer at a time. Agents declare their intent to write before writing ("acquiring" the lock), and the blackboard enforces serial access. No agent writes to a section another agent has claimed. — *Orchestration Playbook / p3nchan, GitHub 2026*
- **Task envelopes for stateless agents.** Wrap each task in an envelope containing: input schema, expected output schema, deadline, retry policy, and escalation target. The agent receives the envelope, does its work, and returns to the envelope. The orchestrator never depends on implicit state; it always reads from the envelope's declared contracts. — *Orchestration Playbook / p3nchan*
- **File-based coordination over in-memory state.** Agents communicating via shared files (JSON, SQLite) rather than in-memory objects survive restarts, are observable with standard tooling, and make race conditions visible as file conflicts rather than silent data corruption. — *Orchestration Playbook README*
- **Circuit breakers on per-agent state.** If agent A's output to the shared store fails validation three times in a row, the circuit breaker halts agent A, notifies the orchestrator, and triggers HITL escalation rather than continuing to write potentially bad data into shared state. — *AI Codex / Multi-agent failure handling*

## Gotchas

- **Don't use conversation as a coordination mechanism.** Shared chat threads between agents devolve into verbose non-decisions and last-word-wins behavior. Use structured task contracts and explicit state stores instead.
- **Heartbeat contracts add latency overhead.** Every agent task now has a polling or streaming heartbeat check. Budget 50–200ms of coordination latency per task and measure it — it compounds fast in fan-out patterns.
- **The blackboard becomes a single point of failure.** If your shared state store goes down, all agents halt. Treat it like any other distributed system dependency: replication, backups, and timeouts.
- **Partial outputs in shared state are worse than no outputs.** A truncated JSON write from a timed-out agent can look like valid state to downstream agents. Always validate the schema and completeness of every write to shared state before treating it as canonical.
