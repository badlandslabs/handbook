# S-2910 · The Production Agent Error Stack

When your agent runs for 95 days straight and then takes down a production database at 3 AM — because nobody instrumented the error path, the retry logic hammered a dead service, and the circuit breaker never fired. The fix is not more prompts. It is a resilience architecture that treats agent failures as engineering problems with engineering solutions.

## Forces

- **Non-deterministic failure modes.** Unlike traditional software, an AI agent can fail with an HTTP 200 — the tool returned something, it just wasn't right. A rate-limited API returns a JSON error that the agent interprets as valid output and continues compounding the mistake across 8 more tool calls. Standard try-catch doesn't capture this class of failure.
- **The 86% recoverable illusion.** Research from The Operator Collective found that 86% of agent failures are technically recoverable — but only if recovery logic exists. In practice, most teams discover the 14% unrecoverable failures only in post-mortems, after the damage is done. Recovery is not automatic; it must be engineered.
- **Integration surface dominates failure.** Anthropic's SDK discussion on error recovery (95+ days of multi-agent production experience) confirms it: "The AI model itself rarely causes catastrophic failures. It's the integrations that time out, APIs that return unexpected formats, rate limits hit at 3 AM, context windows that overflow." Teams over-invest in model selection and under-invest in the integration error layer.
- **Stack churn buries reliability.** Cleanlab's 2025 enterprise survey found 70% of regulated enterprises rebuild their agent stacks every 3 months or faster. When the stack changes constantly, error handling is perpetually behind — bolted on after incidents rather than designed in from the start.

## The Move

Build error handling as a first-class architectural layer, not an afterthought. The pattern that works in production combines four techniques:

- **Deterministic tool response validation.** Before the agent sees a tool response, validate it against the expected schema. If the API returns a 200 with an empty body, that is not success — it is a silent failure. Use JSON Schema or Pydantic models to enforce shape. If the response doesn't match, route to the error handler, not the agent.
- **Tiered retry with circuit breakers.** Apply exponential backoff with jitter to transient errors (429, 500, timeout). Trip a circuit breaker after 5 consecutive failures or >30% error rate in a 10-minute window — then stop the agent, alert the coordinator, and switch to a degraded mode or manual fallback. Per the Anthropic SDK discussion: "Our agents achieve 97.8% autonomous recovery" using this layered approach.
- **Timeout budgets per tool and per task.** Hard-cap each tool call at 30 seconds. Hard-cap the entire task at a configurable step limit (e.g., 20 steps). When a budget is exhausted, the agent does not get a do-over — it escalates. NVIDIA's agent evaluation guide emphasizes tracking trajectory efficiency (optimal_steps / actual_steps) as a first-class metric, not a post-hoc analysis.
- **State checkpointing.** Every 5 steps (configurable), snapshot the agent's working memory and tool call history to durable storage. On failure, the agent can resume from the checkpoint rather than restarting from scratch. This is especially critical for long-horizon tasks where a context-window overflow or crash loses hours of work.
- **Shadow mode for new error patterns.** When deploying a new tool or API integration, run the agent in shadow mode: execute the tool call, capture the response, but don't let the agent act on it until a human approves. This catches format drift and unexpected response shapes before they reach the error recovery layer.

## Gotchas

- **Don't retry on non-transient errors.** A 400 Bad Request will fail every time with the same input. Retrying it just burns tokens and latency. Classify errors by type: retry only 429 (rate limit), 500-599 (server error), and timeout. Return immediately on 400 and 401.
- **Don't let the agent decide when to stop retrying.** Hard-code the retry budget. If the agent's reasoning loop decides "maybe one more try will work," it will retry 47 times on a dead service, each time burning tokens and escalating cost. The circuit breaker is a hard stop, not a suggestion.
- **Don't treat context overflow as a success.** When the context window fills, the LLM doesn't error — it silently truncates early conversation turns. The agent continues, but with lost history. Monitor context token usage per step and fail explicitly when approaching the limit, rather than continuing with corrupted state.
- **Don't skip the audit trail.** Without structured logging of every tool call, response, and decision, post-mortems are guesswork. The DataTalks and Replit incidents were only understood because someone had traces to review. If you don't instrument the error path, you can't improve it.
