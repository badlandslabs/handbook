# S-1796 · The Agent Team Stack — When One LLM Call Isn't Enough But Neither Is Chaos

When a single LLM call handles your full task, it works until it doesn't — the moment complexity exceeds what fits in one context window, one toolset, or one reasoning trace. The obvious next move is to add more agents. The non-obvious part is that this introduces a coordination problem that is, in many ways, harder than the original. Multi-agent systems are now production realities, and the patterns that survive contact with real users are narrower than the frameworks suggest.

## Forces

- **Coordination overhead grows faster than capability.** Adding a second agent means managing communication protocols, shared state, role boundaries, and failure propagation. Most multi-agent setups fail not because of the agents, but because of the invisible glue between them.
- **The framework landscape is immature despite high adoption projections.** Gartner projects 70% of organizations will use orchestration platforms by 2028, yet the leading open-source frameworks (LangGraph, CrewAI, AutoGen) each solve different parts of the problem, and a majority of serious production teams report rolling their own anyway.
- **Evaluations for multi-agent systems are fundamentally different from single-agent evals.** Standard benchmarks (MMLU, HumanEval) measure model capability in isolation. Multi-agent evaluation requires trajectory analysis, tool call accuracy, and task success rate across dynamic environments — benchmarks like GAIA, SWE-bench, and WebArena.
- **Context fragmentation is the silent killer.** Each agent in a multi-agent system maintains its own context window. Without deliberate memory architecture, key information from one agent's context never reaches another — and nothing errors, nothing fails, you just get wrong answers.

## The Move

**Architect for coordination first, capability second.** The winning production pattern is not the most sophisticated agent — it is the simplest communication structure that lets agents hand off cleanly.

- **Choose the right topology.** Three patterns dominate: (1) **Orchestrator-workers** — a central agent decomposes tasks and dispatches to specialized workers, best for tasks with a clear root decomposition; (2) **Peer-to-peer** — agents communicate directly, best for systems where any agent might need any other; (3) **Supervisor chain** — a single supervisor agent routes to sub-agents sequentially, simplest to reason about but serial bottleneck risk.
- **Share state through structured channels, not conversation history.** Practitioners on HN (2026) report using shared MongoDB layers with JSON schemas, Postgres with event sourcing, or Redis queues for inter-agent data passing. Passing context through LLM-mediated conversation summaries is lossy and expensive — structured state stores are more reliable.
- **Instrument everything with OpenTelemetry traces from day one.** Multi-agent traces are not optional debugging — they are the only way to understand why a result is wrong when no error fired. Outshift by Cisco (2025) collaborated with Microsoft and Splunk to introduce semantic conventions for agent-to-agent communication into OpenTelemetry. Each agent turn should emit a trace span with its input, tool calls, output, and role.
- **Bound the agent loop formally, not by convention.** The agent loop is "not a casual while-loop wrapped around a language model call — it is a bounded, instrumented control system with formal stability properties" (General AI Models / Agentic Systems Engineering, 2025). Use max iterations, convergence checks, and explicit exit conditions. A July 2025 Claude Code recursion incident burned $16K–$50K in five hours with no error — just agents doing exactly what they were told indefinitely.
- **Evaluate trajectories, not outputs.** NVIDIA's agent evaluation framework (May 2026) benchmarks on Task Success Rate, Tool Call Accuracy, and Trajectory Efficiency — not model perplexity. Multi-agent evals require automated LLM-based judges evaluating each agent's output independently, plus human-in-the-loop spot checks for quality.
- **Start with two agents, not ten.** The most common mistake is over-architecting the team before the communication patterns are proven. A planner + executor pair handles most decomposition needs. Additional agents add coordination cost that exceeds their capability value until the workflow is proven.

## Gotchas

- **Adding agents before proving the workflow is the most expensive form of premature optimization.** Each new agent doubles the failure surface area for coordination failures, deadlock, and state inconsistency.
- **LLM-mediated inter-agent communication is the slowest, most expensive, and most lossy state-sharing mechanism.** Passing information between agents by having one describe it to the other in natural language degrades context and burns tokens. Use structured state stores (DB, event queues) for data, language only for coordination intent.
- **Framework lock-in is a real risk.** AutoGen moved to maintenance in 2026. LangGraph Platform was renamed LangSmith Deployment in October 2025. If you build on a framework, abstract the agent interface so you can swap the underlying orchestration engine without rewriting agent logic.
- **Specification failures account for ~42% of multi-agent failures in production** (Galileo AI analysis, 2025). The spec — not the code — is where multi-agent systems break. Invest in defining agent roles, handoff conditions, and success criteria before writing any agent prompt.
