# S-2542 · The Agent Observability Stack — When Your Agent Returns 200 and Nobody Knows What It Did

Your agent returned HTTP 200 in 340ms. Your APM dashboard is green. Three customers just got routed to the wrong team, a fourth was charged $847 for something they didn't authorize, and your LLM bill is 4x higher than last month. You have no idea which of the eleven tool calls in that session caused it. Your agent worked perfectly in staging. Now it is production, and you are flying blind. This is the agent observability stack: the instrumentation layer that makes a deployed agent a debuggable system rather than a confidence trick.

## Forces

- **Agents fail inside the trace, not at the surface.** The final output can look correct while an intermediate tool call returned hallucinated data, chose the wrong branch, or wrote to the wrong resource. Standard HTTP logging catches the exit; it misses the journey.
- **Multi-agent traces need parent-child relationships.** When a planner agent spawns three workers and one of them calls a tool that corrupts state, you need to see the full tree — not three disconnected logs. Traditional APM gives you flat spans; agents give you nested hierarchies.
- **Cost lives in tokens, not milliseconds.** A 12-second response that makes two tool calls costs $0.003. A 12-second response that loops through 47 reasoning steps and calls a web search 12 times costs $4.71. APM latency metrics are meaningless without token accounting.
- **Only 37.3% of teams run online production evaluations** (LangChain State of Agent Engineering survey). The majority of production agents are unmonitored by any systematic measure.

## The move

**Structured hierarchical tracing as the foundation.** Instrument every LLM call, tool invocation, memory read/write, and state transition as a span with a parent link. This turns an opaque execution into a reconstructable tree.

**The minimum viable observability stack has four layers:**

- **Trace capture** — Every LLM call logs: prompt, completion, model, temperature, token count, cost, latency, and tool arguments. Every tool call logs: tool name, arguments (JSON), response, and whether it succeeded semantically (not just HTTP status). LangFuse, LangSmith, and Arize Phoenix each offer SDK-level decorators that instrument LangGraph, OpenAI Agents SDK, Claude Agent SDK, CrewAI, and Pydantic AI with 2–3 lines of code.
- **Span hierarchy** — Traces must preserve the parent-child relationship across agent handoffs. When a planner agent delegates to three workers, all four traces share a root span. When a worker loops on a tool 12 times, the span tree shows the exact loop count, each iteration's arguments, and the point where the parent finally continued. OpenTelemetry is the standard wire format; LangFuse, Honeycomb, and Datadog all accept OTel spans natively.
- **Semantic scoring layer** — Traces are only useful if someone reviews them or something scores them. The scoring layer uses LLM-as-judge (a separate model, typically GPT-4o or Claude Sonnet, evaluates whether each span achieved its goal) to flag failed or degraded spans. Langfuse's `score()` API and Braintrust's evaluator framework both support this with pre-built templates. Score distributions over time reveal regressions before customers report them.
- **Cost attribution at the trace level** — Every trace gets a cost tag: model used, input tokens, output tokens, calculated cost. This surfaces the token economics that APM misses. The December 2025 incident where an enterprise customer's summarization agent degraded silently for 3 days was caused by a temperature parameter change from 0.1 to 0.7 — detectable in 10 minutes with per-trace token and score dashboards, invisible without them.

**Instrument before you need it.** Add tracing SDK calls at the same time as the agent code. Retrofitting observability onto a live multi-agent system is painful; tracing decorators added to the first build cost two hours and pay dividends indefinitely.

**Gate deployments on span-level metrics.** Route agent traces through the observability plane with OpenTelemetry. Block or flag deployments when critical span-level metrics degrade: tool call success rate below 90%, average reasoning steps exceeding the 95th percentile of the baseline, or cost-per-session exceeding a defined threshold.

## Gotchas

- **LLM-as-judge scoring has false negatives on subtle reasoning errors.** A grader model often approves spans where the agent took a plausible but wrong reasoning path. Complement LLM scoring with deterministic checks where possible — regex validation on tool arguments, schema enforcement on outputs, hard limits on loop counts.
- **High-cardinality trace data bankrupts storage.** A busy agent producing 10,000 traces/day at 50KB/trace = 500MB/day = 15GB/month, and that's before multi-agent trees with hundreds of spans each. Use sampling (log 100% of failures, 10% of successes) or tiered storage (full traces for 7 days, aggregated metrics after 30).
- **Tool calls that succeed technically and fail semantically are invisible without output inspection.** A `database.write()` call that returns HTTP 200 after writing the wrong value looks identical to a correct write in every metric that standard logging captures. The only detection mechanism is semantic validation of the written state — either automated (read-back verification) or human review of flagged traces.
- **Model version upgrades invalidate your baseline.** Every time you switch model versions, your trace distributions shift. Token counts, latency, and even span-level scores change. Retrain baselines before comparing pre- and post-upgrade traces, or instrument model version as a trace attribute from day one.
