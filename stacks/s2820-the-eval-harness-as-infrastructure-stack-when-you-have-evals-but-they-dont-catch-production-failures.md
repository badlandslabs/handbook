# S-2820 · The Eval Harness as Infrastructure Stack — When You Have Evals But They Don't Catch Production Failures

When you have an eval suite, it passes, and your agent still fails in production — wrong answers, broken tool chains, silent regressions. The problem isn't the model. It's that you treated evaluation as a testing task when it should be an infrastructure discipline. The eval harness is the control plane; it needs to be engineered with the same rigor as the agent itself.

## Forces

- **Eval framework proliferation masks a measurement problem, not a tooling problem.** Teams adopt DeepEval, RAGAS, Phoenix, or lm-evaluation-harness expecting coverage, but 33% of LangChain survey respondents identified "quality" as the top barrier to production deployment — suggesting the tooling itself is not the bottleneck. The problem is what you're measuring and whether your harness captures the failure modes that actually occur.
- **Public benchmarks saturate and can be exploited.** UC Berkeley's RDI examined eight agent benchmarks (SWE-bench, WebArena, OSWorld, GAIA, Terminal-Bench, FieldWorkArena, CAR-bench) and found widespread benchmark gaming: "skill duplication" (agents replicate known solutions without genuine capability), environment overfitting, and shortcut exploit detection that doesn't transfer to novel inputs. SWE-bench Verified itself has largely saturated for frontier models — teams now track SWE-bench Pro (Scale AI, 2025) and Terminal-Bench 2.0 for harder, contamination-resistant testing. A passing benchmark tells you your agent handles the known test set, not that it generalizes.
- **Production agents fail in dimensions benchmarks don't measure.** Task success rate (did it complete?) and output quality (is the answer right?) are different axes — and neither captures trajectory quality (was the path sound?), tool call correctness (did it call the right tool with the right arguments?), or graceful degradation (did it fail usefully?). An agent that gets the right answer by skipping a required validation step will pass output-based evals and fail in production.
- **Offline evals and online monitoring are two different systems with a gap between them.** Offline regression suites run in CI against curated datasets and catch known failure modes cheaply. Online shadow, canary, and A/B testing run against real production traffic and catch the gaps mocks never anticipated. Most teams build one or the other; the failure mode is invisible in the gap between them.
- **Eval engineering is under-resourced relative to prompt engineering.** The practitioner consensus is stark: "good eval engineering is now as important as good prompt engineering" — yet teams allocate 10x more engineering time to prompt iteration than to building robust eval infrastructure. The result is agents that score well and behave badly.

## The Move

Build your eval harness as a **three-layer infrastructure system**, not a test suite:

### Layer 1 — Offline Regression Suite (pre-deploy)
- **Golden dataset from production failures**, not synthetic examples. The most valuable test cases come from real failures: that edge-case email your agent misread, the SQL query that returned wrong results, the tool call that timed out. Build your dataset iteratively from production replays.
- **Multiple runs, not point estimates.** Agents are non-deterministic even at temperature zero — tool results vary, upstream models update, context perturbations fan out. Measure distributions: success rate across N runs, p50/p95 latency, cost variance. A single run gives you a number, not a signal.
- **CI gate with a minimum threshold.** Set a CI threshold of ≥0.75 on all metrics before deploy. Treat this as a hard gate, not a suggestion. Track trend lines, not just pass/fail.
- **Use LLM-as-judge for process scoring, not just outcome.** Evaluate trajectory quality: did the agent check its assumptions? Did it validate before acting? An agent that reaches the right answer through the wrong path will eventually fail on a harder variant.

### Layer 2 — Shadow Mode / Canary Evaluation (staged rollout)
- **Run the new version alongside production traffic without affecting users.** Shadow mode evaluates candidate outputs against live queries and compares against the production version — catching regressions in distribution shift before they hit users.
- **Stratified production sampling for online evals.** Sample a representative slice of production trajectories for human review. Run async evaluation on these traces — never block the agent's response path with eval computation. Score on task success, tool correctness, and response quality.
- **Feed failures back into the golden dataset.** Every production failure caught by online evals becomes a new test case. Treat evaluation as a living artifact; the dataset grows with every incident.

### Layer 3 — Continuous Production Monitoring (post-deploy)
- **Track eval scores as time-series, not snapshots.** A score of 0.82 today means nothing without the trajectory: was it 0.92 last week? Alert on score degradation before users notice — a 5-point drop in task success rate is actionable; a 5-point drop discovered from a user complaint is a failure.
- **Set alert thresholds on production quality metrics.** Trigger on-call alerts when success rate drops below threshold, error rate exceeds baseline, or cost-per-task spikes. Correlate with model provider updates — track which version of the model was running when degradation occurred.
- **OpenTelemetry-native tracing for replay.** Use tools like Arize Phoenix or LangSmith with OpenTelemetry instrumentation so you can replay any production trace, inspect the full trajectory, and identify exactly where and why failure occurred. Without replay, debugging is guesswork.

## Gotchas

- **Don't benchmark-worship.** Passing a public benchmark tells you your agent handles a known test set. It tells you nothing about whether it generalizes, whether it will degrade when the model provider updates, or whether your specific toolchain is wired correctly. Use benchmarks as sanity checks, not gates.
- **LLM-as-judge has judge drift.** An LLM judge evaluating another LLM's output introduces systematic bias — judges tend to be overconfident, inconsistent across runs, and prone to length bias (longer answers score higher). Validate your judge against human-labeled samples and recalibrate regularly.
- **Offline evals can't catch distribution shift.** Your golden dataset covers known failure modes. Novel inputs — the thing users actually ask that you never anticipated — will pass your offline evals and fail in production. Online monitoring is not optional; it's where the unknown unknown lives.
- **Metric proliferation without threshold discipline is theater.** Tracking 40 metrics with no CI gate, no alerting, and no trend analysis creates a dashboard that nobody reads. Pick 3-5 primary metrics, set hard thresholds, and alert on deviations. More metrics are not more quality.
