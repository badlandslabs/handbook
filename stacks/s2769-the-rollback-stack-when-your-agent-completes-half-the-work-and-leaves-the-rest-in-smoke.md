# S-2769 · The Rollback Stack — When Your Agent Completes Half the Work and Leaves the Rest in Smoke

*Your agent tasked with a database migration runs a `DROP TABLE` command before confirming the backup exists. Another agent cleaning up old S3 objects misidentifies the partition prefix and deletes six months of logs. A third autonomously refactors a monorepo across 47 files — and the model loses context halfway through, producing broken code. In every case, the agent completed the action successfully. The damage is real and irreversible. This is the rollback problem: agents that can move forward but cannot go back.*

## Forces

- **Agents are fundamentally non-transactional.** Unlike database systems with ACID guarantees, agents execute a sequence of LLM calls and tool invocations where partial success creates inconsistent states that no rollback mechanism was designed to handle.
- **Side-effecting operations commit immediately.** A filesystem write, API POST, or database mutation happens once and cannot be undone by reversing a function return value. The agent may be in the middle of a 12-step workflow when a bad tool call produces a subtly wrong parameter.
- **Sub-agent isolation creates compensation debt.** In frameworks like LangGraph and Claude Code 2.1, spawned child tasks can complete successfully while the parent workflow fails — leaving the system with no built-in mechanism to detect or reverse the child's side effects.
- **Naive max_iterations won't save you.** Retrying a failed agent re-executes every step including the ones that already succeeded, compounding the damage (re-sending an email, re-charging a card, re-deleting the partition).

## The Move

Build rollback capability into the agent scaffold, not the agent logic.

- **Checkpoint before every side-effecting node.** Serialize agent state (not just the prompt — the full thread: tool call history, intermediate outputs, learned corrections) to durable storage (Postgres for transactional guarantees, Redis for low-latency) before executing any node that writes to an external system. LangGraph's built-in checkpointer makes this three lines of code.
- **Use semantic rollback guards, not blind re-execution.** Upon restore from a checkpoint, do not re-execute nodes that already completed successfully. The September 2025 LangGraph issue #6208 (confirmed by framework maintainer Caspar Broekhuizen) documents that naive re-execution of restored nodes can re-trigger interrupts and re-apply side effects. ACRFence (Zheng et al., 2026) formalizes this as a semantic rollback attack surface — an adversary can craft inputs that cause a restored checkpoint to take a different code path than the original.
- **Gate destructive operations with human-in-the-loop checkpoints.** Any tool call matching patterns like `DROP`, `DELETE`, `TRUNCATE`, `rm -rf`, or `force_push` should suspend execution, serialize the current state, present a human-readable diff of intended changes, and resume only on explicit approval. This is the single highest-leverage safety intervention for production agent deployments.
- **Archive compensating transactions, not just state.** For long-running workflows, maintain an explicit undo log: `{step: 4, action: "DELETE s3://bucket/logs/2024*", rollback: "restore from backup snapshots"}`. This gives the agent (or operator) a recovery path that survives across process restarts.
- **Design tool idempotency as a first-class property.** Use idempotency keys on API calls, conditional writes with `if_not_exists` semantics on database operations, and read-before-write checks on filesystem operations. This makes rollback unnecessary for transient failures — the retry simply confirms the state is already correct.

## Gotchas

- **Checkpointing adds latency.** Serializing a full agent thread to Postgres before every tool call can add 50–200ms per node. Profile the overhead and use Redis for low-stakes in-memory checkpoints; reserve Postgres for operations with real compensation cost.
- **Restored state can be stale.** If the external world changed between checkpoint and restore (e.g., a row was updated by another process), rolling back the agent's state to the checkpoint is insufficient — you also need to re-read the current world state before re-executing.
- **LLM drift on re-execution.** Even with the same prompt and checkpoint, re-executing an agent step can produce a different tool call if the model temperature is non-zero or if the underlying model was updated. Treat re-execution as non-deterministic and add assertion checks on the output.
- **The undo log is only as good as its completeness.** A compensating transaction that doesn't cover all side effects is worse than no rollback — it creates false confidence. Audit every side-effecting tool call in your agent's repertoire and ensure each has a corresponding rollback entry.
- **Human-in-the-loop gates kill throughput.** Every approval checkpoint introduces a blocking wait. For low-stakes operations (internal file writes, read-only API calls), skip the gate. Reserve it for operations matching the destructive operation pattern — and make sure the gate doesn't become a bottleneck that trains operators to auto-approve without reading.
