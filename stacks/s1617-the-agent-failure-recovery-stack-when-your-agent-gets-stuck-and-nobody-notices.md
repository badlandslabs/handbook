# S-1617 · The Agent Failure Recovery Stack — When Your Agent Gets Stuck and Nobody Notices

Your agent is still running. The API returns 200 OK. Nothing crashes. But the agent has been calling the same tool with the same arguments for the past 40 minutes, burning $847 in tokens on a task that should have cost $0.03. This is the failure mode that production agents don't warn you about: not a crash, but an undetected loop.

## Forces

- **Agents fail non-deterministically, not deterministically.** A traditional program either works or throws an exception. An agent fails with a confident 200 OK that is subtly, fundamentally wrong — hallucinated tool calls, semantically invalid JSON, or an endless retry loop that silently drains your API budget. Catching this requires classifying failure types before choosing a response.
- **Retry logic that was designed for deterministic systems makes agents worse.** Retrying a 401 authentication error wastes tokens. Retrying a tool that failed because the agent chose the wrong tool just re-executes the same wrong choice. Blind retries amplify cost without improving outcomes.
- **Agents accumulate failure silently.** Unlike a crashed service that pages your on-call engineer, an agent in a loop or a degraded state produces no alerts. It looks like it is working. The cost accrues invisibly until someone notices the billing statement.
- **The right recovery strategy depends on who can fix the failure.** Some failures are fixed by the system (automatic retry on transient errors). Some are fixed by the LLM itself (semantic error corrected by re-prompting). Some require a human. The wrong routing wastes time and money on all three.

## The Move

Classify every failure at the boundary, then route each class to the correct handler. Layer loop detection, budget circuit breakers, and stateful checkpoints as guardrails beneath the classification logic.

**Step 1 — Classify before acting.** Inspect the error type or HTTP status code before deciding what to do. Separate transient errors (retry-eligible) from semantic errors (re-prompt required) from resource errors (payload must shrink) from fatal errors (abort and alert).

**Step 2 — Attach retry policy selectively.** LangGraph's `RetryPolicy` attaches directly to nodes. Configure backoff and jitter per exception type. Do not retry on `AuthenticationError`, `ContentPolicyViolationError`, or 401 — these will not resolve with a retry. Only retry on transient codes: 429 (rate limit), 503 (temporary unavailable), connection timeout, DNS failure. A policy that retries everything is a policy that burns budget on unresolvable errors.

**Step 3 — Detect loops at the tool-call boundary.** Track the hash of `(tool_name, arguments, error_type)` for each step. When the same combination appears 3 or more times in a row, halt the loop. The ai-agent-loop npm library documents this: an agent calling the same tool with the same failing arguments 2,847 times before loop detection was added. NVIDIA AI-Blueprints had an unbounded `while True` where tool-binding failures grew the message state, triggering another model call, which grew the state further — a feedback loop from model output back to message state and then to another call.

**Step 4 — Set dollar and token budget circuit breakers.** Attach a hard ceiling to every agent invocation: maximum tokens, maximum seconds, maximum dollar cost. When the ceiling is hit, stop the agent, log the state, and surface a signal — not a silent hang. LangGraph's `TimeoutPolicy` supports both wall-clock and idle-based caps.

**Step 5 — Use stateful checkpointing for long-running agents.** On failure, resume from the last checkpoint rather than restarting from scratch. LangGraph's `PostgresSaver` or `SqliteSaver` persist graph state between runs. Temporal's engineering blog identifies the core principle: agents should resume, not restart.

**Step 6 — Route to the right fixer.** The Focused.io error classification matrix: transient errors → system retry (automatic); LLM-recoverable errors → inject error into state and loop back to the LLM; user-fixable errors → `interrupt()` and escalate to human; unexpected errors → let them bubble up to developers. Human escalation is non-negotiable for compliance-critical operations in finance, healthcare, or legal domains.

**Step 7 — Audit everything.** LangSmith traces provide an immutable record of every agent decision, tool call, and LLM response. This is not just for debugging — it is the audit trail required for governance. Without it, a compliance officer asking why your agent made a decision has no answer.

## Gotchas

- **Retrying a semantic error just re-executes the wrong choice.** If the agent picked the wrong tool, retrying the same call produces the same wrong result. You must inject corrective context into the prompt or state, not just re-execute.
- **Token budget errors are not recoverable by retrying.** When a request exceeds the context window or hits a cost ceiling, retrying the identical request produces the identical failure. The fix is to reduce the payload (summarize prior results, drop older context, switch to a cheaper model) — not to retry.
- **Circuit breakers must trip on the right granularity.** A circuit breaker at the API level (e.g., OpenAI endpoint) catches infrastructure failures but misses per-agent loops. The loop detection must be at the `(tool, args, error)` triple level to catch the specific pattern that burns budget.
- **Stateful checkpointing without persistence is fragile.** Saving checkpoints to memory works until the process restarts. Use `PostgresSaver` or `SqliteSaver` for durable persistence — not an in-memory dict.
- **LLM-as-Judge for error detection has its own failure modes.** Asking the LLM to evaluate whether another LLM output is correct is circular. Use structural checks (schema validation, output type checks) as the first gate, and reserve LLM-as-Judge for semantic quality assessment — not error detection.
