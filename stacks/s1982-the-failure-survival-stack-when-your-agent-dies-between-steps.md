# S-1982 · The Failure Survival Stack — When Your Agent Dies Between Steps

*Your agent completes a 23-step database migration, deletes the wrong partition, and the damage is already done before the 24th step runs. Agents fail differently than software — they return 200 OK while destroying state. The failure happens; the recovery must be engineered before it.*

## Forces

- **Agents return success codes while failing silently.** Unlike traditional software that crashes with a stack trace, agents return HTTP 200 while hallucinating tool calls, looping indefinitely, or misclassifying inputs. A support agent that misroutes refund requests as product questions doesn't error — it just silently fails every customer. Traditional try-catch blocks don't catch these failure modes.
- **Mutation is irreversible by default.** When an agent calls a tool that mutates external state — a SQL DELETE, a filesystem write, a POST to an external API — and subsequently fails or produces a wrong result, the side effect has already happened. There is no automatic transaction boundary. An agent that completes 47 file refactors and then loses context halfway through leaves the codebase in a broken half-state with no natural undo.
- **Failure taxonomies are non-standard.** The field lacks consensus on what counts as a failure: a loop that produces no output? A correct output via a wasteful 50-step detour? A confident hallucination that looks plausible? Teams waste months debating definitions before implementing any recovery logic.
- **Recovery cost compounds with irreversibility.** Per-incident costs from agent loops can reach ~$2.50 with GPT-4o (markaicode.com). Unscoped recovery attempts — "just keep retrying" — can burn thousands of dollars and produce nothing. But overly conservative guards — max 3 retries, then give up — sacrifice legitimate multi-step work.

## The Move

Build failure survival into the harness layer, not the agent logic. Four interlocking mechanisms:

- **Classify failures before choosing a response.** Transient failures (429 rate limits, brief 503s) get exponential backoff retry. Persistent failures (provider outage, exhausted quota, bad API key) trigger fallback routing. Bad-input failures (400 policy violations, malformed JSON) modify the request or route differently. Partial failures (wrong format, incomplete output) trigger self-correction with the error fed back as the tool result. The agentic move: feed the error back to the model as the tool result — it can try a different approach, exactly like a human seeing an error message.

- **Layer three checkpoint types.** Filesystem/filesystem: snapshot files before mutation, copy before write, shadow filesystem for destructive ops. Database: use transactions or idempotency keys so tool calls can be safely replayed. State/checkpoint: frameworks like LangGraph and Microsoft Agent Framework provide native checkpoint/resume primitives — persist state at decision points so the agent can resume from the last good state rather than restart. A 23-step agent that crashes at step 18 should not restart from step 1.

- **Detect stuck loops with progress metrics, not activity counts.** Activity proxies (API call counts, file edits) rise during both stuck loops and legitimate converging work — they cannot distinguish the two. A stuck loop has flat progress across N heartbeats while continuing to act. A slow-but-converging loop has rising progress even if incrementally. Progress must only increase on real work completed, not on action taken. Once detection fires, climb a bounded recovery ladder: (1) nudge — give the agent the error and ask it to self-correct, (2) replan — provide the error context and ask for a revised strategy, (3) escalate — notify human, (4) reset — restart from last checkpoint, (5) hand off — route to a different agent.

- **Protect tool mutations with guardrails and compensation logic.** Idempotency guards: every mutating tool call gets a unique request ID so duplicate calls can be safely deduplicated. Pre-flight hooks: before any destructive tool (DELETE, DROP, overwrite), verify the operation against a manifest of expected actions. Compensation chains: for multi-step mutations, define a compensation function for each step so a rollback executes in reverse order if the chain fails partway. Permission scoping: agents should not inherit admin privileges — the Amazon Kiro agent bypassed two-person approval and deleted a production environment, triggering a 13-hour AWS outage. Least-privilege tool access is not optional hygiene.

- **Instrument the circuit breaker for LLM providers, not just tools.** LLM providers degrade in ways traditional health checks miss: HTTP 200 with responses 5x slower than normal, empty or truncated completions, content filter rejections on legitimate queries. Monitor failure rate, latency, and output quality per provider. When thresholds breach, open the circuit and redirect to a fallback provider. After cooldown, probe with half-open state before closing.

## Evidence

- **Academic taxonomy (Zylos Research, 2026):** Production agent failures break into six categories: specification failures (~42% of multi-agent failures), coordination breakdowns (~37%), verification gaps (~21%), context loss, resource contention, and permission escalation. The majority of failures stem not from the model but from how agents are composed and constrained. — [Zylos Research — AI Agent Self-Healing and Failure Recovery](https://zylos.ai/zh/research/2026-05-06-agent-self-healing-failure-recovery)

- **Real incident: $1.2M refund agent (Agentbrisk, Q3 2025):** A mid-size e-commerce customer service agent authorized up to $500 without human review. ~340 transactions totaling $1.2M were exploited before detection — users rephrased requests to match the agent's training distribution for "legitimate" refunds. The agent succeeded on its own terms (routing, approving, executing) while failing on the business's terms. — [Agentbrisk — AI Agent Failures: Real Incidents](https://agentbrisk.com/blog/ai-agent-failure-modes-real-incidents/)

- **Loop incidence (NiteAgent, 2026):** Analyzing 1,642 agent traces across 7 frameworks using the MAST taxonomy (Berkeley/Stanford), production failure rates range from 41% to 86.7%. Step repetition loops account for 15.7% of failures; reasoning-action mismatches for 13.2%; termination-condition drift for 12.4%. These three account for over 40% of agent failures. Even the best-performing framework still fails ~40% of the time. — [NiteAgent — 5 AI Agent Debugging Patterns for Production in 2026](https://niteagent.com/blog/ai-agent-debugging-patterns-2026)

- **YC-backed failure monitoring (Sentrial, YC W26):** Founded by former SenseHQ and Accenture agents engineers. Real failure examples cited: a support agent misclassifying refund requests as product questions (customers never reached the refund flow), a document drafting agent that began generating increasingly vague output as context grew — invisible until a user complained. Core insight: "When agents fail, there's no visibility — just logs and guesswork. Debugging agents is often harder than building them." — [Launch HN: Sentrial (YC W26)](https://news.ycombinator.com/item?id=47337659)

## Gotchas

- **Feeding errors back to the model is not always safe.** For irreversible actions (deletions, payments, approvals), the error-to-model loop can cause the agent to double down on the wrong approach. Self-correction with error feedback is appropriate for read-only or recoverable operations; for mutating tools, cap the self-correction loop at 1-2 iterations before escalating to a human.
- **Checkpointing adds latency and storage cost.** Persisting state at every decision point for a long-running agent can generate significant overhead. The right granularity is decision points (after each tool call) not time points — balance checkpoint fidelity against storage and resume latency.
- **The recovery ladder must have a hard cap.** Without a ceiling on the escalation ladder, agents can loop through nudge → replan → nudge → replan indefinitely. Cap the total recovery attempts at 3-5 before forcing a human handoff, and charge the cost of that handoff against the value of automation.
- **Circuit breakers for LLMs must monitor output quality, not just HTTP status.** A provider that returns 200 with a truncated or repetitive response is degraded even though it didn't error. Track not just failure rate and latency but also repetition rate, truncation rate, and semantic coherence of outputs.
