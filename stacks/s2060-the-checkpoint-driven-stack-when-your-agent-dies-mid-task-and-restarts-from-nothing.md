# S-2060 · The Checkpoint-Driven Stack — When Your Agent Dies Mid-Task and Restarts From Nothing

[Your agent was 80% through a 200-step data migration. The context window hit its limit. The session terminated. You restarted and watched it spend 45 minutes re-doing work it had already completed — and making slightly different decisions along the way. The second run's output diverged from the first. You now have two inconsistent results and no way to merge them. This is not a rare edge case. It is a scheduled guarantee.]

## Forces

- **Restarting an agent is not recovery.** A database replays its write-ahead log deterministically — the same writes, in the same order, every time. An LLM agent re-samples from the model on resume, producing a *distribution* of possible next states. Two resumptions of the same interrupted task will diverge unless the state itself — not the conversation history — is the thing being restored. This is decision drift, and it compounds with task length.
- **Conversation history is not the right artifact to checkpoint.** Capturing the message thread preserves what was said, not the agent's reasoning state, intermediate calculations, rejected alternatives, or accumulated constraints. An agent that checkpoints its message history and an agent that checkpoints its decision log are in fundamentally different shape on resume.
- **Every major agent framework has an open issue on this.** The problem is not framework-specific — it is architectural. OpenAI Codex, Claude Code, Google ADK, Microsoft Copilot, and Kiro all have documented GitHub issues tracking context-window-exceeded session death.
- **Context window limits are a feature, not a bug.** As Anthropic's Applied AI team framed it in September 2025: "Long-horizon tasks require agents to maintain coherence, context, and goal-directed behavior over sequences of actions where the token count exceeds the LLM's context window." The window limit is the constraint; checkpointing is the response.
- **Human-in-the-loop approvals create a resume-or-lose situation.** If an agent pauses at step 47 for human approval and the session dies, the team cannot approve the pending step and cannot trust a fresh restart to replicate the pre-approval state.

## The Move

Serialize the agent's *decision state* — not its message history — at step boundaries, and resume from that state on restart.

- **Checkpoint the decision log, not the conversation.** Capture: current step index, completed steps with their outputs, rejected alternatives with reasons, active constraints, and the reasoning chain. The artifact is a structured JSON (or equivalent) that a resumed agent can read to understand where it is and why, without re-executing completed work.
- **Write checkpoints to durable storage at every step boundary.** SQLite is the dominant choice for zero-config, portable, durable storage — used by agent-recall-ai, OpenMemory, and dozens of similar tools. PostgreSQL is used in enterprise deployments where checkpoint history needs to survive infrastructure failures and support audit trails.
- **Design resume to skip completed work, not re-schedule it.** On resume, the agent reads the checkpoint, identifies that steps 1–46 are marked complete with verified outputs, and begins at step 47. The checkpoint is the source of truth for what exists, not a prompt-completion hint.
- **Use deterministic step markers, not LLM output markers.** Completed steps should be marked complete by the orchestration layer (e.g., a state machine or workflow engine), not by the LLM's self-assessment. The agent should not decide whether it succeeded — the system should record the outcome externally.
- **Build a context bridge for new context windows.** When the checkpoint exceeds a single prompt, summarize it into a structured handoff document: "Step 1–46 done. Key constraints: [list]. Next action: [step 47 description]. Non-obvious decisions made: [list]." This is the input to a resumed session's system prompt or initial context.
- **Layer memory types for long-running agents.** The Tsinghua University December 2025 survey identifies three memory categories that production agents implement together: factual memory (what the agent knows about the task), experiential memory (what happened in prior sessions), and working memory (current step state). Checkpointing covers the working memory tier; episodic and semantic long-term memory require a separate retrieval layer.
- **Combine checkpointing with idempotent tool design.** If a resumed agent re-executes a completed step's tools, those tools must be idempotent — or the checkpoint must record outputs as the source of truth for downstream steps, not re-running.

- **Context engineering pattern (Airbyte, December 2025):** Reports that checkpointing "combined with event-history replay and idempotent tool design, transforms brittle agentic pipelines into fault-tolerant, resumable workflows" and that "LangGraph, Temporal, and Dagster all ship first-class checkpoint primitives." — [airbyte.com/agentic-data/context-window-limit](https://airbyte.com/agentic-data/context-window-limit)

Checkpointing addresses working memory; the other layers require retrieval-augmented approaches. — [letsdatascience.com/blog/ai-agent-memory-architecture](https://letsdatascience.com/blog/ai-agent-memory-architecture)

## Gotchas

- **Re-sampling on resume is the silent killer.** An agent restarted from message history will produce different intermediate outputs than one resumed from exact step state. The divergence is subtle — same goal, different execution — and it compounds across steps. Test this explicitly: run a task to 50% completion, checkpoint, restart from the same conversation history, and diff the outputs at step 30. If they match, your checkpoint is working. If they diverge, you have decision drift.
- **Capturing message history is not checkpointing.** The conversation log tells you what was said; it doesn't tell you what was decided, what was rejected, or what constraints were in force. You need a structured decision record, not a transcript.
- **Checkpoint frequency is a trade-off, not a maximum.** Writing a checkpoint after every step maximizes fault tolerance but adds I/O overhead and may trigger repeated summarization of the checkpoint itself for very long tasks. A common pattern: checkpoint on every tool call, summary-checkpoint every N steps, full state-checkpoint on human-approval boundaries.
- **Context bridging introduces a summarization bottleneck.** When the decision log exceeds the new session's context window, it must be summarized. That summarization is itself an LLM operation — it can introduce errors, lose nuance, or drop constraints that seemed minor at checkpoint time but matter at step 100.
- **Idempotency is required downstream from the checkpoint, not just at the step.** If a resumed agent re-executes step 23's tool call and that call is not idempotent, you have double-side-effects. Checkpoints freeze the output state; any tool re-execution must be gated by the checkpoint's record of what already happened.
