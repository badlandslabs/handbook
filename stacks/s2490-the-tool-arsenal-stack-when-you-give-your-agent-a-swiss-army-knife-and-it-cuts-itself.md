# S-2490 · The Tool Arsenal Stack — When You Give Your Agent a Swiss Army Knife and It Cuts Itself

Every agent framework lets you define tools. Few teams design them as a system. The choice between JSON tool calling, MCP servers, CLI tools, and sandboxed code execution is not cosmetic — it determines the agent's action space, failure modes, token cost, and reliability profile. Get it right and the agent operates with precision. Get it wrong and you have a confident operator with a full toolbox and no supervision.

## Forces

- **Token overhead compounds silently.** Each tool definition costs 550–1,400 tokens (Apideck benchmark). Load 20+ tools upfront and you have a hungry context consumer with a shrinking window for actual reasoning.
- **Tool failure is an architectural problem, not a prompt problem.** JSON tools fail silently (succeed or return garbage). MCP has inconsistent error semantics across servers. The agent miscalls the wrong tool, passes wrong parameters, or ignores results — and these failures are invisible until the task is wrong.
- **The context-switching tax.** Each tool has its own interface conventions. Agents regularly misinterpret tool output format — especially for structured responses (JSON, XML) where small formatting deviations cause complete misparses.
- **Stale state is the dominant browser-automation failure mode.** Vision-based agents take a screenshot, reason, then act — but the page moved. The agent is now operating on a ghost. This is not a model problem; it is a synchronization problem.

## The Move

Design the tool arsenal in layers, from infrastructure to domain, with on-demand loading throughout:

- **Layer 1 — Compute primitives first.** Sandboxed code execution (Python/Bash in a container) is the highest-leverage first tool. Anthropic's engineering post documents a 98.7% token reduction (171K → 2.2K tokens) for a Google Drive-to-Salesforce workflow by replacing a 16-step JSON tool chain with one sandboxed code call. CodeAct (arXiv) reports up to 20% gains from letting agents compose small programs instead of issuing long tool-call sequences. One Python snippet that queries, transforms, and formats is cheaper and more reliable than six separate tool calls with retry logic.
- **Layer 2 — MCP as the integration bus, not a tool dump.** Anthropic's MCP code-execution post introduces on-demand tool loading: don't pre-register every tool definition, let the agent request what it needs and return a lightweight result. As of early 2026, MCP has 14,000+ published servers and 97M monthly SDK downloads, with confirmed production integrations from Microsoft, GitHub, Stripe, Atlassian, Figma, and Cloudflare (arXiv:2603.13417). Three protocol primitives remain missing at production scale: identity propagation (who is this request for?), adaptive tool budgeting (how long does this tool get?), and structured error semantics (what should the agent do when it fails?). Design around these gaps.
- **Layer 3 — Browser automation: use accessibility trees, not screenshots.** The Agent Browser Protocol (ABP), a Chromium fork purpose-built for agents, achieves 90.53% on the Online Mind2Web benchmark by keeping the AI synchronized with browser state at every step — no stale screenshots, no ghost DOM. ABP delivers 2× lower token usage, 2× faster runs, and 2× fewer tool calls versus Playwright MCP. Playwright MCP (Microsoft, ~1.5K stars) uses accessibility snapshots instead of CSS selectors — resilient to UI changes that break XPath-based targeting. These beat raw vision-based computer use (Claude Computer Use, OpenAI Operator) for reliability in production.
- **Layer 4 — Domain tools on demand.** The production tool adoption hierarchy, ranked by GitHub stars across the MCP ecosystem: filesystem access (~15K stars), browser automation, web search, database connectors (Postgres, MongoDB), GitHub API integration, Slack/messaging. Each is an MCP server. Each adds tokens per invocation. Load only what the agent's current task actually needs.
- **Layer 5 — Guardrails on every tool.** Implement tool-use budgets: if an agent calls the same tool 3× without task progress, force a reflection step. Implement result validation schemas — don't let a tool's raw output flow into the next step unexamined. The 550–1,400 token overhead of a tool definition buys you nothing if the agent can't interpret the result.

## Gotchas

- **Pre-loading every MCP tool is the default mistake.** It works in the demo and collapses in production. Use on-demand loading — agent requests a tool, harness provides it, result flows back. Tool definitions are not free.
- **CSS selectors are brittle for browser automation.** UI changes break targeting. Use accessibility-tree-based tools (Playwright MCP, ABP) that survive interface changes. Vision-based computer use is powerful but token-expensive and state-sensitive.
- **MCP error semantics are inconsistent across servers.** The agent has no standardized way to understand what went wrong or whether to retry. Wrap every tool call with explicit error classification: retryable, fatal, or requires human input.
- **Code execution is a powerful tool but an attack surface.** Sandboxed execution must be properly isolated. Prompt injection attacks through web content can reach the sandbox. Treat code execution tools with the same guardrails as any other external interface.
