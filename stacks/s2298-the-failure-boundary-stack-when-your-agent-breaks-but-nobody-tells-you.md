# S-2298 · The Failure Boundary Stack — When Your Agent Breaks But Nobody Tells You

Your agent completes steps 1 through 4 of a multi-step workflow, hits a rate limit on step 5, and returns HTTP 200 with a confident-sounding apology that masks the failure. No exception. No traceback. Your pipeline marks it complete. Your monitoring sees green lights. The downstream system gets garbage. This is the core failure mode of agentic AI: agents break silently, and traditional error handling doesn't see it.

## Forces

- **Agents fail without raising exceptions.** The agent is the logic layer. It can behave incorrectly — hallucinate tool arguments, drift from the goal, loop indefinitely — and return a valid HTTP 200 response. No process crashes. No exception thrown. Traditional `try/catch` catches nothing that matters.
- **Partial progress is the default, not the exception.** A 10-step workflow doesn't fail atomically. It completes steps 1–4, then hits a bad tool response, then continues from a corrupted state. The agent has moved on; the pipeline doesn't know it should stop.
- **Agents retry past failure boundaries.** Unlike a microservice that backs off on 503, a language model reasons around failures. If you tell it "the API timed out," it may retry with a slightly different argument — and hit the same rate limit again, and again, and again, until you've burned the budget and the context window.
- **Failure categories differ from traditional software.** Microsoft's 2025 whitepaper on AI agent failure modes identifies six categories unique to agents: tool misuse, context loss, goal drift, retry loops, cascading errors in multi-agent systems, and silent quality degradation. Galielo's 2025 analysis of multi-agent production deployments found specification failures account for ~42%, coordination breakdowns for ~37%, and verification gaps for ~21%.
- **Circuit breakers work differently for agents.** The standard circuit breaker pattern — fail fast, stop calling, retry after timeout — was built for deterministic callers. An agent that reasons around failures won't honor a tripped breaker. AWS Builder Center (July 2026) documents this explicitly: agents need breakers that communicate in a language the model will respect, not just an infrastructure signal.

## The Move

Build explicit failure boundaries around every agent operation. The goal is not to prevent failure — it's to make failure observable, bounded, and recoverable.

- **Classify errors by recoverability at call time.** Distinguish three error classes with different recovery paths: (1) *Environmental errors* — rate limits, timeouts, network failures — appropriate for exponential-backoff retry; (2) *Syntactic/semantic errors* — malformed JSON, bad tool arguments — re-prompt the model with the error inline, no backoff; (3) *Intentional errors* — hallucinated tools, out-of-scope actions — reject immediately, report to human, do not retry.
- **Hard-cap every loop with a step budget.** Set `max_steps` or `max_iterations` as a non-negotiable boundary. A loop cap is not a graceful degradation — it's a fence. The AI Agents Blog (March 2026) recommends `max_retries ≤ 5` for most cases, with exponential backoff base of 1s and max of 60s with jitter. When the cap is hit, stop and escalate — don't let the agent keep trying.
- **Checkpoint state to durable storage after every significant step.** Don't store state in memory. After each tool call completes, write the completed steps and the current context to durable storage (Redis, S3, a database). When the agent crashes, restarts, or loops, it resumes from the last checkpoint rather than from scratch. This is the pattern Temporal and LangGraph's persistence layer implement under the hood.
- **Circuit breakers at agent boundaries, not just service boundaries.** A circuit breaker on the database connection protects the DB; a circuit breaker at the agent boundary protects the system from a looping agent. The AgentCircuit GitHub repo implements CLOSED (calls route normally), OPEN (fallback activates, primary not called), and HALF_OPEN (one test call to check recovery) states for agent functions specifically.
- **Build a fallback chain, not a fallback call.** When the primary LLM fails, route to a smaller/faster model. When that fails, return a cached response or a "try again later" with a request ID. The fallback chain should be defined declaratively and tested via failure injection — not discovered at 3 a.m.
- **Idempotency guards on every state-mutating tool.** Before any tool that writes to an external system, generate or check an idempotency key. This makes retry safe: if an agent retries a tool call that already partially succeeded, the second attempt is a no-op rather than a duplicate write. This is the pattern that prevents the duplicate refund, duplicate email, or double-booking that makes agent failures visible to users.

## Gotchas

- **Treating all errors the same.** A rate limit (retry with backoff) and a hallucinated tool name (reject and escalate) have nothing in common. If you wrap every failure in the same `try/except`, you'll either over-retry (burning budget on bad tool calls) or under-retry (giving up too fast on transient errors).
- **Checkpointing to in-memory state.** If your "checkpoint" lives in a Python variable or a local dict, it disappears when the process restarts. Durable storage means something that survives a crash — Redis, S3, Postgres, a file on a persistent volume.
- **Hard-coding the fallback instead of testing it.** A fallback that has never been invoked in production will fail on first use. Inject failures in staging: temporarily disable the primary LLM, corrupt a tool response, trigger a rate limit. If your fallback chain isn't exercised regularly, it's not a fallback — it's a hope.
- **No monetary guardrails on agents with financial access.** The Agentbrisk incident analysis (March 2026) documents a customer service agent that issued ~$1.2M in unauthorized refunds over 340 transactions before detection — not because of a technical failure, but because no hard monetary threshold triggered a human review. Any agent with access to financial operations needs per-action monetary limits and cumulative spend thresholds, independent of the error-handling layer.
