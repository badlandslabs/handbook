# S-2538 · The Failure Handling Stack — When Your Agent Keeps Going After It Should Stop

Your agent doesn't crash. That's the problem. Traditional software throws a stack trace, exits with a code, and tells you which line broke. An AI agent fails quietly — it keeps running, keeps calling tools, keeps burning tokens, and produces something that looks like work but isn't. By the time you notice, the credits are gone and the damage is done. The failure handling stack is the set of architectural decisions that determine whether a broken agent recovers and continues, or fails catastrophically — corrupting state, losing progress, and repeating work without end.

## Forces

- **Agents fail silently** — HTTP 200 with hallucinated content, tool calls that succeed technically but fail semantically, reasoning chains that produce confident nonsense. Standard try/except blocks don't cover these failure modes.
- **Failure is non-deterministic** — A prompt that works once fails the next time due to model drift, token limit surprises, or ambiguous tool feedback. Recovery cannot be deterministic the way database transaction rollback is.
- **Multi-step compounding** — In a 10-step workflow, each step has a failure probability. The product of those probabilities compounds. A 95% success rate per step means ~60% overall success across 10 steps.
- **Progress vs. safety tension** — More checkpoints mean more safety but more friction. Human-in-the-loop at every step defeats the purpose of automation. Finding the right escalation threshold is non-obvious.
- **Context window pressure** — Without stopping conditions, agents accumulate tool responses until the context window overflows, causing silent truncation or failure on the next call.

## The Move

Failure handling in production agentic systems follows a **progressive escalation hierarchy**: self-correct → fallback → degrade gracefully → escalate. The key architectural decisions:

- **Classify before you retry.** Not all errors should be retried identically. Transient errors (HTTP 429, 5xx, timeouts) call for retry logic. Auth failures (401, revoked keys) should abort immediately — hammering a 401 endpoint wastes tokens and may lock the account. Semantic failures (LLM returns valid JSON but wrong schema, tool succeeds but output is empty) require re-prompting or switching strategy, not retrying the same call.
- **Layer stopping conditions.** Every agent loop needs at least two hard stops layered on top of each other: a hard iteration ceiling (`max_iterations`) that always fires, plus soft stops (budget-based token limits, elapsed-timeouts). An agent without a stopping condition is a resource leak. A ReAct-style agent can burn through 47,000 tokens calling the same tool 73 times before any stop triggers.
- **Implement cycle detection**, not just iteration counting. The naive approach counts iterations and stops at a ceiling. The better approach tracks the last N tool-call signatures and detects repetition patterns: same tool + same arguments, or same tool + oscillating between two arguments. Step repetition accounts for ~15.7% of all agent failures and occurs in >80% of traces on weaker models.
- **Checkpoint before irreversible steps.** Every tool call that writes to external state (DB, filesystem, external API) should have a checkpoint placed immediately before it. On crash, recovery replays from the last checkpoint, not from scratch. The problem: unlike databases, agent checkpoints carry LLM decisions (how the model interpreted ambiguous input) that drift on replay. A date field read as "March 4th" on day 1 propagates into all downstream reasoning — restart doesn't reconstruct the agent's exact state.
- **Build a fallback chain for model failures**, not just tool failures. When the primary model degrades, the agent should fall back to a smaller, faster, cheaper model with a stripped-down prompt. This is distinct from fallback to an alternative tool — model-level fallback and tool-level fallback have different triggers and different recovery paths.
- **Escalate to a human when state cannot be verified.** Recovery requires detection. If an agent writes to an external system without output validation, it may compound bad state by "recovering" into a worse situation. Fail fast to a human when intermediate state cannot be verified — particularly for finance, healthcare, or compliance-critical operations.

## Gotchas

- **Never retry 4xx errors.** A 401 or 403 will not resolve by retrying. A 422 with a schema violation will not fix itself by calling the same endpoint with the same arguments. Retry only transient failures (429, 5xx, timeouts) — and add exponential backoff with jitter to prevent thundering herd on recovery.
- **Checkpoint-and-resume is not free replay.** Unlike a database WAL, an agent's checkpoint contains LLM decisions (interpretations, judgments) that drift on replay if the input context has changed or the model version has shifted. Validate state after restore, don't assume replay is equivalent to the original execution.
- **Circuit breakers must be coordinated in multi-agent systems.** When agents share infrastructure (databases, queues, tool APIs), recovery attempts from one agent amplify load on stressed components. Per-agent circuit breakers that don't communicate create cascading failures across the system.
- **Silent corruption is worse than loud failure.** An agent that writes to an external system without output validation can "recover" into a worse state — compounding bad data instead of correcting it. Fail to a human when intermediate state cannot be automatically verified.
- **Short-lived tasks with no side effects don't need recovery logic.** A task under 30 seconds with no external writes gains nothing from checkpoint overhead — the retry cost exceeds the recovery benefit. Size the failure handling to the actual blast radius.
