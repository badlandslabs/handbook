# S-1730 · The Cascading Silence Stack — When Your Agent Fails and Takes Down the Pipeline

Your multi-agent system has a failure. A single sub-agent times out on an LLM call, but instead of failing cleanly, it retries in a tight loop, generating duplicate sub-tasks, flooding the message queue, and triggering rate limits on the very API it was trying to reach. Within seconds, six other agents that were functioning normally are stuck waiting on a queue that won't drain. Your pipeline didn't crash — it slowly choked. No alarms fired because each individual operation looked fine. You restart everything and the cycle repeats.

You reach for this when your agentic system has no blast-radius containment, when "it handles errors" means "it wraps everything in try-catch," or when you can't tell the difference between a dead agent and a slow one.

## Forces

- **Agents are stateful; retries are not.** Traditional retry logic assumes a failed operation can be re-run from a clean slate. Agents write partial results mid-task — updating shared state, dispatching sub-tasks, appending to trajectories. A naive retry doesn't reset the system; it compounds the problem with duplicate writes and conflicting sub-task dispatches.
- **Fan-out amplifies failure instead of absorbing it.** When an orchestrator fans out to 40 workers and 30 fail simultaneously (LLM provider outage), each retry attempt adds load to the already-struggling provider. Without rate-limiting or backpressure, a transient outage becomes a sustained one.
- **Agentic errors don't look like errors.** The most dangerous failures return HTTP 200. The LLM generated invalid JSON. The tool call succeeded technically but failed semantically. The reasoning chain produced confident nonsense. Traditional observability can't detect these — they look like successful operations.
- **Failure isolation and agent autonomy are in tension.** You want agents to make decisions independently, but independence without boundaries means a failing agent can corrupt shared state that other agents depend on.

## The move

**Contain blast radius at four architectural layers, in order of increasing cost:**

- **Layer 1 — Compute isolation (Kubernetes pods).** Run each agent in its own pod with resource limits. A single agent consuming excessive memory or CPU doesn't starve its neighbors. Set `restartPolicy: Never` on agents that should surface failures rather than self-resurrect indefinitely.
- **Layer 2 — Message-layer partitioning (Kafka consumer groups).** Assign each agent class to its own consumer group. When Agent Class A's queue backs up, Agent Class B continues consuming from its own queue. This prevents a backlog in one pipeline from blocking unrelated pipelines.
- **Layer 3 — State checkpointing (Postgres or Redis).** Every meaningful agent action writes a checkpoint before executing. On retry, the agent reads the last checkpoint and resumes from there — it doesn't restart from zero. This prevents duplicate writes and sub-task duplication on retry.
- **Layer 4 — Circuit breakers at every tool boundary.** Track failure rates per tool or external API over a sliding window. When the failure rate exceeds a threshold (e.g., >50% failures in 30 seconds), open the circuit: fail fast on new requests to that tool, giving it time to recover. Close the circuit after a timeout period and allow a test request through.

**At the agent design level:**

- **Couple agents via data (state), not via execution.** If Agent A fails, Agent B should still be able to run — it may find no data in state to process, which is a clean empty-state, not a crash. Pass work through shared state (Redis streams, Postgres tables, S3 objects) rather than synchronous calls.
- **Distinguish operational failures from cognitive failures.** Operational failures (API timeout, rate limit, invalid JSON) are transient and retryable. Cognitive failures (hallucination, wrong tool selection, reasoning error) are not fixed by retrying — they require a different intervention (prompt revision, tool redesign, eval feedback). Tag every error with its failure class so your retry logic knows which path to take.
- **Instrument the non-errors.** Log every tool call, every state transition, and every LLM response — not just failures. A trajectory that succeeds but takes 47 tool calls when 5 would have sufficed is a signal. Claude Code's team at Anthropic learned this by tracking "inefficient trajectories" as a first-class metric alongside success rate.

## Gotchas

- **Circuit breakers without state checkpointing create phantom recovery.** The circuit opens on failures, closes after timeout, and new requests pour in — but the agent state is still corrupted from the partial writes. The circuit closes into a broken system. Always pair circuit breakers with idempotent or checkpointed state.
- **Setting retry counts too high turns circuit breakers into denial-of-service.** Each agent retry adds load on the failing dependency. If 40 agents each retry 3 times with no coordination, you just generated 120 requests against a service that's already failing. Use exponential backoff with jitter, and coordinate retry attempts across agents via a shared rate limiter.
- **"No errors in the logs" is not the same as "the system is healthy."** A hallucinating LLM that produces confident nonsense will log at INFO level with a 200 response. You need semantic assertions — "did the output conform to the expected schema?" — not just HTTP status checks.
- **Restarting the pipeline without clearing state re-triggers the same failure.** If the root cause was a dependency returning corrupted data (which then poisoned agent state), a restart without state cleanup just re-runs the same poisoned state through the same pipeline. The first step in recovery should be state audit and rollback, not restart.
