# S-2300 · The Tool Surface Stack — When Your Agent Has a Swiss Army Knife and Keeps Picking the Wrong Blade

You gave your agent 47 tools. It can search the web, run code, read files, call APIs, send emails, and manage your database. The agent ignores the search API and tries to scrape the website instead. It calls the email function with the wrong recipient format. It ignores the vector search and re-embeds everything from scratch. The agent has every tool it needs and still makes worse choices than a human with three. Tool abundance is not the problem — unconstrained tool surfaces are.

## Forces

- **Tool cardinality degrades selection quality.** Research from Zylos AI (2026) shows performance measurably degrades at 60–70% context fill, and by 90% fill, structured tool-call quality deteriorates enough to affect task outcomes. The agent isn't running out of conversation space — it's running out of working memory for its tools.
- **MCP created an M×N integration problem.** Before the Model Context Protocol, connecting AI models to external tools meant custom point-to-point integrations. MCP standardizes this via JSON-RPC 2.0 — but the protocol also made it trivially easy to expose hundreds of tools, triggering the "too many tools" problem. Stefano Demiliani (September 2025): "Having too many tools exposed in an MCP server can degrade the performances and the output of your LLM."
- **Tool descriptions are the real interface.** HN commenter JacobArthurs on the "Ask HN: How do you know if AI agents will choose your tool?" thread: "Tool description quality matters way more than people expect. Specify when NOT to use the tool — agents pick confidently when there's a clear boundary, not a vague capability statement. Inline examples beat external documentation."
- **The tool you give determines the task the agent can reason about.** OpenAI's Agents SDK offers five tool categories: hosted tools (web search, file search, code interpreter), local/runtime tools (ComputerTool, ShellTool), function calling, agents-as-tools, and Codex. Anthropic's Computer Use tool gives Claude screenshot + mouse + keyboard control for desktop automation. Claude Code execution runs Python/bash in a sandboxed container. The tool shape determines the agent's action space.
- **Agents-as-tools is the underrated pattern.** OpenAI's SDK lets you expose one agent as a callable tool for another agent — enabling hierarchical decompositions without a full handoff. This is how you get specialized sub-agents (a research agent, a coding agent, a review agent) that the orchestrator calls like functions.

## The Move

**Constrain the tool surface to the minimum viable action set, then make every remaining tool description unambiguous.**

- **Count your tools before you count your features.** If you have more than ~15 tools in a single agent's context, you have a tool surface problem. Group related tools into MCP servers, then give the agent access to server-level namespacing rather than individual tool enumeration. Let the agent search for tools at runtime rather than listing all of them.
- **Write tool descriptions that specify exclusion cases, not just capabilities.** "Use this tool when X, not when Y." Agents reason by pattern-matching against descriptions — a description that only states what a tool does leaves the agent guessing about boundaries. The Frigade/pancomplex approach (HN, ~26 days ago) auto-generates MCP servers by watching what API calls an authenticated app makes — the tool description is generated from live traffic, making it grounded rather than abstract.
- **Prefer MCP servers over hardcoded tool definitions.** MCP (modelcontextprotocol/servers, 89k+ GitHub stars, 16k+ active servers as of late 2025) standardizes tool discovery and invocation. Build your tool as an MCP server — it gets interoperability, tooling, and discoverability for free. The registry at registry.modelcontextprotocol.io publishes production servers.
- **Use agents-as-tools for hierarchical decomposition.** Instead of giving one agent 15 tools, give it 3 sub-agents, each with 5 focused tools. The orchestrator agent calls sub-agents as functions, receiving structured responses. CyberArk Engineering (October 2024) describes this as the core advantage of LangGraph over LangChain Agents: "Divide the process into smaller, focused prompts, each responsible for a specific task, allowing task-specific LLM assignment."
- **Instrument tool selection, not just tool execution.** Track which tools the agent considers (not just which it calls), what context pressure exists at each decision point, and how tool selection quality changes as context fills. Comet ML's context window guidance (2025): "Track token usage at each workflow step. Where is context accumulating? Which tools are adding the most tokens?"
- **Expose scoped tools, not raw APIs.** A raw REST API with 40 endpoints is not a tool — it's a liability. Wrap it in a tool with a narrow description, a single responsibility, and explicit input/output schemas. The Hacker News "MCP Defender" project (gsundeep, May 2025) emerged precisely because exposed MCP tool surfaces became attack surfaces — the same discipline that makes a tool safe makes it agentable.

## Gotchas

- **Adding a tool is easy; removing one is political.** Tool proliferation happens incrementally. Each individual tool makes sense in isolation. The aggregate surface is what destroys selection quality. Treat tool additions as inventory with carrying cost.
- **The agent's tool selection is not observable by default.** You see what tool the agent called. You don't see what it considered and rejected, or what it almost picked. Instrument the selection layer explicitly, not just execution outcomes.
- **MCP tool discovery at runtime is not the same as loading all tools at startup.** MCP's tool search feature lets the agent find tools dynamically — but you still need to define the search space. A poorly scoped search space returns noise. A well-scoped one returns signal.
- **"Agents as tools" requires trust boundaries, not just API contracts.** When one agent calls another agent as a function, the calling agent assumes the sub-agent is a reliable function, not an autonomous agent. If the sub-agent can loop, drift, or fail silently, those failure modes propagate up the call stack. The failure-boundary patterns from S-2298 apply here.
