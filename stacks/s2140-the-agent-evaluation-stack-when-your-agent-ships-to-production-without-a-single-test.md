# S-2140 · The Agent Evaluation Stack — When Your Agent Ships to Production Without a Single Test

Your agent scored 85% on its eval suite. You deployed it Monday. By Friday it was regressing silently — answering confidently wrong, selecting the wrong tool, and failing to recover from the same error that was caught in testing last month. Nobody noticed because there was no regression gate. The eval suite was a notebook someone ran once. This is not a model problem. It is an evaluation architecture problem: you built a system that acts autonomously but measures nothing continuously.

## Forces

- **Agents are non-deterministic but shipped like deterministic software.** Traditional unit tests assume identical inputs produce identical outputs. Agents produce different trajectories each run — the same prompt can yield five different tool sequences. You cannot test them the way you test a calculator.
- **The benchmark crisis makes standard benchmarks unreliable.** UC Berkeley RDI research demonstrated that all eight major agent benchmarks (SWE-bench, WebArena, OSWorld, GAIA, Terminal-Bench, FieldWorkArena, CAR-bench, SWE-bench Pro) can be gamed to near-perfect scores without solving a single task. A `conftest.py` pytest hook scores 100% on SWE-bench Verified. A fake `curl` wrapper gets 100% on Terminal-Bench. Navigating to a `file://` URL reads the gold answer directly from the task config on WebArena. — [UC Berkeley RDI, April 2026](https://rdi.berkeley.edu/blog/trustworthy-benchmarks-cont)
- **Multi-step trajectories compound failure.** A 98% reliable agent × 5 sequential steps = 90% end-to-end reliability. One wrong tool call at step 3 can cascade into a completely wrong final answer. You cannot evaluate only the output — you must evaluate the path.
- **Production failures are your best test cases.** The highest-value regression dataset is not handcrafted — it comes from real failures. Every production failure hands you an authentic edge case, a real input distribution, and a concrete definition of what "broken" looks like for your specific system. — [Arthur.ai, June 2026](https://www.arthur.ai/column/regression-test-datasets-ai-agents-production-failures)
- **Static benchmarks don't measure what matters in production.** Task success rate, latency, cost per task, token efficiency, and graceful recovery from tool failures are the operational metrics that determine whether an agent actually works in production. Standard benchmarks measure none of them continuously. — [InfoQ, March 2026](https://www.infoq.com/articles/evaluating-ai-agents-lessons-learned)

## The move

Build a three-layer evaluation architecture: **offline golden datasets** for regression, **trace-driven production analysis** for discovery, and **LLM-as-judge scoring** for the outputs that defy exact-match rules.

### Layer 1 — Golden dataset with deterministic and programmatic graders

- Collect test cases with known inputs and expected outputs or behaviors. For tool-calling agents, define pass/fail by whether the correct tool was invoked with correct parameters, not by the final text output. For coding agents, use unit tests as the grader — the agent passes if the test passes. — [Anthropic Engineering, January 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Categorize test cases by failure mode: tool selection error, parameter error, planning failure, recovery failure, safety violation. Tagging enables targeted regression — you know exactly which capability regressed when a suite fails.
- Wire the golden dataset into CI/CD as a regression gate. A PR that drops accuracy below the established baseline should fail the build. The eval harness should return `pass`/`fail` — not a score you'd have to interpret manually. — [jbelnick/llm-judge-evals, GitHub](https://github.com/jbelnick/llm-judge-evals)
- Prioritize building tests from **production failures first**. Turn a failing production trace into a test case, the test case into a regression entry, and the regression entry into a CI gate. Every failure cycle makes the next release safer. — [Arthur.ai, June 2026](https://www.arthur.ai/column/regression-test-datasets-ai-agents-production-failures)

### Layer 2 — Trace-driven production observability

- Instrument agents to capture full execution traces: every prompt, tool call, model call, and response with timing and cost metadata. Do not log only the final response — the final output rarely reveals which step caused the failure. — [Braintrust, 2026](https://www.braintrust.dev/articles/agent-tracing-debug-ai-agents-production)
- Run agents in production or a simulated environment and capture traces. Score overall success, trajectory coherence, and robustness against ground truth. — [Braintrust, 2026](https://www.braintrust.dev/articles/agent-tracing-debug-ai-agents-production)
- Search across traces to find patterns: which tool fails most often, which step introduces the most latency, which failure mode is most common. Aggregate trace data reveals systematic problems that individual test runs miss.

### Layer 3 — LLM-as-judge for subjective and ambiguous outputs

- Use an LLM judge (typically a stronger model) to score outputs that have no single ground truth: research quality, communication tone, response completeness, contextual appropriateness. The judge applies a rubric — a structured set of criteria — rather than giving an arbitrary score. — [Anthropic Engineering, January 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Combine model-based grading with deterministic guards. Let the LLM judge rate the quality of a research agent's answer on a 1–5 scale, but gate on whether it cited sources and avoided known-hallucination topics with an exact-match check. This catches the judge being fooled by fluent-but-wrong output. — [jbelnick/llm-judge-evals, GitHub](https://github.com/jbelnick/llm-judge-evals)
- Evaluate safety independently from task success. An agent that completes 90% of tasks but violates safety constraints 5% of the time is more dangerous than one that completes 70% of tasks safely. Safety and capability are orthogonal dimensions and must be tracked separately. — [Neel Mishra, 2026](https://neelmishra.github.io/blog/mlops/llm-agents/agent-evaluation.html)

## Evidence

- **Engineering Blog:** Anthropic's "Demystifying Evals for AI Agents" defines the core taxonomy — task (a test with inputs and success criteria), trial (each attempt), grader (the scoring logic). Recommends a **dual-layer grader approach**: programmatic graders for deterministic aspects (did the test pass? was the correct tool called?), model-based graders for subjective aspects (is the response well-structured?). — [Anthropic Engineering, January 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- **Academic Research:** UC Berkeley RDI published the most comprehensive attack on agent benchmarks — an automated agent built exploits that score 100% on SWE-bench Verified (pytest hook injection), 100% on Terminal-Bench (binary trojanization), ~100% on WebArena (config file leak), 73% on OSWorld (direct answer download). The researchers released BenchJack, an automated benchmark attack tool, and recommend production teams use their own domain-specific eval sets instead of relying on public benchmarks. — [UC Berkeley RDI, April 2026](https://rdi.berkeley.edu/blog/trustworthy-benchmarks-cont)
- **Industry Survey:** InfoQ's analysis of production agent evaluation found that traditional LLM metrics (BLEU, ROUGE) and single-turn accuracy do not capture an agent's ability to plan effectively, recover from failures, maintain long-term context, control costs and latency, or remain resilient against adversarial inputs. Recommends four evaluation categories: task completion, trajectory quality, operational constraints, and safety. — [InfoQ, March 2026](https://www.infoq.com/articles/evaluating-ai-agents-lessons-learned)
- **Open Source:** Multiple GitHub repos (jbelnick/llm-judge-evals, mizcausevic-dev/agent-eval-arena) implement the golden dataset + CI gate pattern. The core insight: an eval harness that cannot fail a build is not an eval harness — it is a score sheet.
- **Thoughtworks:** Recommends five evaluation dimensions for production agents: tool selection accuracy, task completion rate, planning quality, failure recovery, and multi-agent coordination. Notes that there's no single metric or tool that can fully evaluate an AI application — effective evaluation requires a framework approach. — [Thoughtworks Australia, June 2026](https://www.thoughtworks.com/en-au/insights/blog/machine-learning-and-ai/Evaluating-AI-agents-in-production)

## Gotchas

- **Eval data rots.** An eval set built in March reflects the input distribution of March. By June, users may be asking differently, using new tools, or hitting different edge cases. Re-annotate and refresh golden datasets quarterly, or pull test cases continuously from production failures. An unmaintained eval suite is worse than no eval suite — it gives false confidence.
- **The LLM-as-judge can be fooled.** A fluent-but-wrong answer can fool a judge that rates based on writing quality rather than factual accuracy. Always pair model-based grading with deterministic guardrails for safety-critical and factual requirements. — [jbelnick/llm-judge-evals](https://github.com/jbelnick/llm-judge-evals)
- **Sample size matters for non-deterministic agents.** A single trial is meaningless for a stochastic agent. Run each task across 5–10 trials and report pass@k (probability at least one of k attempts succeeds). A 70% single-trial pass rate might represent a 99.99% pass@10 — or a 70% pass@10, depending on whether failures are correlated.
- **Evaluating the research agent is the hardest case.** Unlike coding agents where unit tests provide binary pass/fail, research agents produce outputs (reports, answers, analysis) that have no single correct form. You must define quality criteria per task type and accept that evaluation will be relative, not absolute. — [Anthropic Engineering](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
