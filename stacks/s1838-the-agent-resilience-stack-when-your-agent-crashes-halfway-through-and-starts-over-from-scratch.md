# S-1838 · The Agent Resilience Stack — When Your Agent Crashes Halfway Through and Starts Over From Scratch

Your document-processing agent has been running for 47 minutes through 500 files. It hits an OpenAI 429 rate limit, exhausts its naive retry loop, and crashes. Without checkpointing, all 47 minutes are gone — it restarts from file 1. This is the agent resilience gap: the gap between agents that work in demos and agents that survive production chaos. The fix is not a smarter model. It's the engineering discipline of building for failure from day one.

## Forces

- **Every production agent failure is recoverable — until you throw away the state.** 86% of agent failures are recoverable, yet teams treat resilience as an afterthought. The ones who get it right treat checkpointing and error handling as first-class architecture, not debugging patches. — *[The Operator Collective, 2025](https://theoperatorcollective.org/blog/ai-agent-error-handling-production-guide)*
- **Retry logic without state persistence is a fake safety net.** Naive retry loops restart the same step, not the whole task — but if you haven't saved what completed before the crash, retrying means redoing. Every long-horizon agent that skips checkpointing eventually has a very expensive restart. — *[EngineersOfAI, 2025](https://engineersofai.com/docs/agentic-ai/long-horizon-planning/checkpointing-and-recovery)*
- **Agents fail on their integrations, not their intelligence.** The AI model rarely causes the catastrophic failure. It's the API that times out, the rate limit that hits at 3 AM, the context window that overflows, and the tool call that silently returns nothing. These are distributed-systems problems wearing an AI costume. — *[The Operator Collective, 2025](https://theoperatorcollective.org/blog/ai-agent-error-handling-production-guide)*
- **Distributed systems patterns apply directly — but agents add a twist.** Circuit breakers, idempotency keys, and retry policies all transfer from traditional backend engineering. The twist: an agent's side effects (emails sent, records updated) must be handled idempotently because the retry might re-execute a step that partially succeeded. — *[I Am Stackwell, 2025](https://iamstackwell.com/posts/how-to-make-ai-agents-idempotent)*

## The Move

A layered resilience architecture with five co-dependent components:

- **Checkpoint state at task boundaries, not every step.** Save completed work (file results, tool call history, task graph status) after each meaningful unit of work — not after every token or every LLM call. The EngineersOfAI guide recommends saving after every task for completed results, tool call history, and task graph status. — *[EngineersOfAI](https://engineersofai.com/docs/agentic-ai/long-horizon-planning/checkpointing-and-recovery)* In LangGraph, attach a checkpointer at compile time: `graph = workflow.compile(checkpointer=SqliteSaver.from_conn_string(":memory:"))`. Every super-step writes a checkpoint keyed by `thread_id`; resuming reloads from that point. — *[Zylos Research, 2026](https://zylos.ai/research/2026-03-04-ai-agent-workflow-checkpointing-resumability)*
- **Idempotent tool design — same request, same result, no matter how many retries.** Derive idempotency keys from business intent, not random UUIDs. Good: `send_email:user_123:welcome_v2`. Bad: a new UUID on every retry. — *[I Am Stackwell](https://iamstackwell.com/posts/how-to-make-ai-agents-idempotent)* Without this, any retry after a crash sends the welcome email twice.
- **Structured error classification with targeted recovery paths.** Not all errors are equal. A missing field in a PDF requires user intervention; a timeout on an external API calls for exponential backoff retry. A custom error hierarchy with typed exceptions (e.g., `MissingFieldError`, `APITimeoutError`, `RateLimitError`) lets the orchestration layer make the right recovery call. — *[C# Corner, 2026](https://www.c-sharpcorner.com/article/custom-error-hierarchies-in-enterprise-langgraph-multi-agent-systems/)*
- **Circuit breakers that stop cascading failures.** When an LLM backend degrades, naive retry amplifies the problem — every pending request hammers the failing service. A circuit breaker tracks failure rates and opens (stops calling) when a threshold is crossed, giving the backend time to recover. — *[agentguard-llm GitHub, 2025](https://github.com/maheshmakvana/agentguard-llm)* The library wraps this with LLM-aware retry: 429 errors get intelligent backoff; 500s get exponential backoff with jitter; connection errors get a different strategy.
- **Loop detection with escalating interventions.** Agents running 100+ iterations inevitably encounter states where they repeat without progress. The detection stack: deterministic step-count limits, semantic loop detection (same tool call + same args within N steps), and escalating interventions. crewAI found that injecting "you appear to be repeating" works ~40% of the time — but changing the agent's available tools when a loop is detected works better. — *[crewAI GitHub Issue #4682](https://github.com/crewAIInc/crewAI/issues/4682)*

## Gotchas

- **Checkpointing too granular tanks performance.** Saving state after every LLM token or tool call generates massive overhead. Checkpoint at meaningful boundaries (completed tasks, sub-agent handoffs, batch processing milestones) and accept that the worst case is re-running the last unit. — *[EngineersOfAI](https://engineersofai.com/docs/agentic-ai/long-horizon-planning/checkpointing-and-recovery)*
- **Retry without idempotency creates duplicate side effects.** The most common mistake: retry logic that re-sends the email, re-creates the ticket, or re-charges the card because the original action succeeded but the confirmation was lost. Every tool call that has side effects must carry an idempotency key derived from the business intent. — *[I Am Stackwell](https://iamstackwell.com/posts/how-to-make-ai-agents-idempotent)*
- **Graceful degradation is more valuable than perfect recovery.** Not every failure mode needs to retry until success. A document analysis agent that hits a corrupted PDF should skip it, log it, and continue to the next — not halt the entire pipeline. Define which errors are fatal vs. recoverable per tool. — *[The Operator Collective](https://theoperatorcollective.org/blog/ai-agent-error-handling-production-guide)*
- **You can't observe what you don't trace.** Every decision, tool call, and intermediate state needs to be logged. The Operator Collective recommends storing complete trace logs with timestamps, tokens consumed, tool responses, and error codes. A LangGraph agent silently looping for 20 minutes consuming $200 is invisible without tracing. — *[Markaicode, March 2026](https://markaicode.com/langgraph-production-agent)*
