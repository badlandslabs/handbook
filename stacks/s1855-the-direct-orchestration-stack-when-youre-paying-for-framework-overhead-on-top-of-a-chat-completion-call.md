# S-1855 · The Direct Orchestration Stack — When You're Paying for Framework Overhead on Top of a Chat Completion Call

Every framework conversation about "agentic orchestration" comes back to the same schism: teams that spent months building on LangChain, CrewAI, or AutoGen and now want out, versus teams that never touched a framework and shipped faster by calling the API directly. The teams that actually ship in production have converged on a rule of thumb that keeps getting repeated across HN, Reddit, and engineering blogs — start with the simplest thing, reach for orchestration tooling only when you can articulate why you need it.

## Forces

- **The abstraction tax** — every framework layer means you're one surprise update from a breaking change that lives three stack frames away from your actual prompt
- **Debugging distance** — when something breaks in a framework-authored pipeline, you're reading framework internals, not your code
- **Production failure modes differ from demos** — a framework that feels ergonomic in a notebook can become an opaque box in production
- **The multi-agent temptation** — splitting work across agents sounds like parallelism, but introduces handoff failure, context fragmentation, and coordination overhead that single-agent loops often avoid

## The Move

**The pattern that consistently wins in production: direct LLM API calls with minimal, purpose-built orchestration.** Not zero orchestration — you still need the structural pieces. But built by you, for your problem, without the framework tax.

- **Build on the augmented LLM, not the agent** — Anthropic's "Building Effective Agents" (Dec 2024) introduced this as the foundational unit: an LLM with tools, memory, and data connected directly. Every successful production system they observed started here and added complexity only when demanded by the specific problem. ([Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents))
- **Use workflows for predictable sequences, agents only where the LLM must dynamically direct its own path** — Anthropic draws a sharp line: workflows have predefined code paths and deterministic execution; agents are for tasks where the LLM needs to choose its own tools and order. Teams that conflate these pay in debuggability.
- **Reach for LangGraph (not LangChain) when you genuinely need graph-based state** — LangGraph models state machines explicitly: nodes, edges, and typed state that you can inspect and replay. CrewAI and AutoGen were built for ergonomic prototyping. The tradeoff from production teams is consistent: CrewAI's role-abstraction simplifies initial build but obscures execution flow in production debugging. LangGraph's explicitness costs more upfront and pays back in reliability. ([AI Workflow Lab, 2026](https://aiworkflowlab.dev/article/building-multi-agent-ai-systems-2026-architecture-patterns-mcp-production-orchestration))
- **Adopt MCP for tool connectivity, not a proprietary tool registry** — Model Context Protocol (MCP), open-sourced by Anthropic and adopted by OpenAI (March 2025) and Google Gemini, standardizes how agents connect to external tools. Rather than writing custom tool integrations per framework, teams connect once to MCP servers and reuse across any MCP-compatible runtime. GitHub: `lastmile-ai/mcp-agent` (Show HN, 80 points, Jan 2025). ([HN item #42867050](https://news.ycombinator.com/item?id=42867050))
- **For multi-agent systems, the orchestrator/worker pattern dominates** — a central planner decomposes tasks and delegates to specialists. Five established patterns: orchestrator/worker, pipeline, fan-out/fan-in, peer debate, and specialist routing. Pipeline and orchestrator/worker handle most production use cases; peer debate adds reliability for high-stakes outputs but doubles cost. ([ExplainX, June 2026](https://explainx.ai/blog/multi-agent-orchestration-patterns-guide-2026))
- **65% of teams that adopt a full agent framework hit a wall within 12 months and rewrite** — this figure, reported across multiple framework-comparison analyses, is the strongest signal that the upfront framework choice has long-term consequences. The teams that avoid this are the ones who asked "why do I need a framework?" before picking one. ([Gheware DevOps Blog](https://devops.gheware.com/blog/posts/langgraph-vs-crewai-vs-autogen-comparison-2026.html))

## Evidence

- **Anthropic Engineering (Dec 2024):** "The most successful implementations use simple, composable patterns rather than complex frameworks." After working with dozens of teams building LLM agents across industries, the pattern that consistently succeeded was direct LLM API calls with augmentation layers built for the specific problem — not general-purpose framework abstractions. — [https://www.anthropic.com/engineering/building-effective-agents](https://www.anthropic.com/engineering/building-effective-agents)

- **Hacker News discussion (June 2025, 543 points, 88 comments):** Thread on Anthropic's "Building Effective Agents" post generated a consistent signal: developers shared stories of removing LangChain/LangGraph from projects after finding them "literally worthless" for production use. One commenter: "It's insane that people use whole frameworks to send what is essentially an array of strings to a webservice." Another: "We've removed LangChain and LangGraph from our project... [the complexity] made simple things complicated and debugging meant being three layers of abstraction away from the actual prompt." — [https://news.ycombinator.com/item?id=44301809](https://news.ycombinator.com/item?id=44301809)

- **OpenAI Developer Community (Sep 2025):** A developer asking whether to replace LangChain with OpenAI's Agents SDK for a knowledge assistant got a response that captures the field's evolving consensus: "If you're building an agent, you're already far ahead of the bell curve. There isn't one [proven pattern]. Design your workflow explicitly." Teams moving away from LangChain cited opaque debugging, constant breaking changes, and abstractions that solved problems they didn't have. — [https://community.openai.com/t/thoughts-on-replacing-langchain-with-native-orchestration-and-doubling-down-openai-apis-directly/1360207](https://community.openai.com/t/thoughts-on-replacing-langchain-with-native-orchestration-and-doubling-down-openai-apis-directly/1360207)

## Gotchas

- **MCP is for tool connectivity, not agent-to-agent communication** — Anthropic's MCP and the emerging A2A (Agent2Agent) protocol solve different problems. MCP connects agents to external tools/data; A2A (backed by Google, SAP, and others, announced April 2025) handles inter-agent communication protocols. Confusing them leads to overengineering the wrong layer.
- **Multi-agent is not automatically better than single-agent** — the reasons to split across agents are concrete: context window overflow, independent parallelism, domain specialization, or fault isolation. If none of these are pressing for your use case, a single augmented LLM with a well-structured prompt will outperform a multi-agent system that spends tokens coordinating.
- **LangGraph's explicitness is a cost, not just a benefit** — modeling your workflow as a state graph requires upfront design work and produces more code. Teams that adopted it for simple linear workflows found the overhead outweighed the benefit. Reserve graph-based orchestration for workflows with meaningful branching, cycles, or parallel states.
- **AutoGen is in maintenance mode** — Microsoft's guidance is to use Microsoft Agent Framework for new builds. If you're starting a new project and considering AutoGen, this is a dependency risk worth factoring in.
