# S-1963 · The Programmatic Constraint Stack — When Your LLM-Based Guardrails Bend but Don't Break

When you give an agent a browser, a shell, and full API access, then rely on a system prompt to keep it from misbehaving — and discover that the gap between "do not delete production data" and "will not delete production data" is exactly one confident hallucination wide.

## Forces

- **LLM reasoning is a suggestion, not a guarantee.** A system prompt that says "never delete records" holds until the model is tired, confused, or adversarially prompted. Programmatic constraints don't tire.
- **General-purpose agents need general-purpose tools.** But general-purpose tools — shells, browsers, code execution — have destructive capabilities that can't be soft-banned through prompting alone.
- **The safety-security gap.** Most agent frameworks ship with "guardrails" that are really output filters on the LLM's response. These catch obvious violations but fail on novel combinations, indirect paths, and adversarial inputs that a code-level policy engine would block instantly.
- **Constraint enforcement at the tool layer is invisible to the agent.** A tool that silently returns an empty result, or that throws a typed exception, forces the agent to handle the error gracefully. A tool that returns the destructive output and relies on the agent to self-correct is a design error.
- **The operational security problem compounds when agents interact.** An agent that wouldn't delete a database when acting alone might do so if another agent asks it to, or if it infers a higher-priority goal from context drift. Code enforces boundaries; prompts negotiate around them.

## The Move

The core move is **moving the boundary of safety from the LLM layer to the tool layer** — making it structurally impossible for the agent to take certain actions, rather than hoping it chooses not to.

- **Typed tool rejection, not soft warning.** Instead of a tool that returns `{"status": "warning", "message": "This action is destructive"}` and lets the agent proceed, use a tool that throws a structured exception (`ActionDeniedError`) that the agent must handle. The agent can retry with modified parameters, escalate, or give up — it cannot bypass the rejection.
- **Scope-gated credentials.** Tools get credentials scoped to the minimum required permission set. A browser-automation tool gets read access to URLs and no write access to the filesystem. A code-execution tool runs in a container with no network egress. The tool layer enforces this; the agent never sees credentials it doesn't need.
- **Pre-execution policy evaluation before any tool call.** A policy engine (e.g., OPA/Rego, Cedar, or a custom decision tree) evaluates every tool call against the current session context — user identity, task scope, risk classification — before the call executes. This is a hard gate, not a soft prompt injection.
- **Escalation hooks at defined risk thresholds.** When a tool call crosses a risk threshold (delete operations, financial transactions, credential exposure), the policy engine triggers a human-in-the-loop pause. The agent waits; the human approves or rejects. This is not a suggestion — it's a structural requirement.
- **Deterministic fallback for ambiguous inputs.** When the agent asks a tool to act on something it doesn't understand (a modal dialog, an unexpected error state), the tool should fail fast and deterministically with a typed error — not return garbage that the agent then confidently misinterprets. The agent should never have to guess whether a result is valid.
- **Audit trail that survives the agent's context window.** Every policy decision, tool call, and rejection is written to an append-only log outside the agent's memory. When the agent loops or degrades, the log remembers what was denied and why.

## Gotchas

- **Typed rejection can create a retry loop.** If a tool always throws `ActionDeniedError`, a sufficiently determined agent may retry the call with slightly modified parameters 50 times until it finds a bypass. Policy evaluation should be stateful — tracking denial history and escalating on repeated attempts.
- **Scope-gated credentials require operational discipline.** The principle is simple; the implementation is not. As the "MCP Supply Chain Integrity" stack documents, 40+ CVEs in MCP servers have emerged from the assumption that tool implementations are trusted. Scope-gating the agent's credentials is correct; trusting that every tool server correctly implements its own scope is not.
- **Pre-execution policy adds latency.** Every policy evaluation is a synchronous gate. For low-stakes, high-volume tool calls (a spell-check, a lookup), the overhead may outweigh the benefit. The fix is risk-tiered policy: instant allow-lists for known-safe calls, full evaluation only for calls in the configurable risk band.
- **Audit trails are only useful if someone reads them.** Append-only logs that nobody monitors are not a safety measure — they're a post-incident forensics resource. Programmatic constraint only completes the safety story when the audit trail feeds into an active alerting pipeline.
- **The agent may work around programmatic constraints by treating them as environmental noise.** If the tool always returns an error the agent doesn't understand, the agent may suppress the error and continue. The constraint design must include interpretable error messages that give the agent enough information to reason about what was blocked and why — not just a code and a stack trace.
