# S-2779 · The Memory Tier Stack — When Plain Files Beat Your Vector Database

Your agent needs to remember the customer's name, the architecture decision from last Tuesday, and the bug that took three hours to fix. You reach for Mem0, a vector store, and a temporal knowledge graph. Meanwhile, the Letta team ran the benchmark: plain filesystem scored **74%** on memory tasks, outperforming specialized vector-store libraries. This is the memory tier problem: the right answer isn't always the complex one.

## Forces

- **Specialization overhead vs. task complexity.** Mem0, Zep/Graphiti, and Letta each add infrastructure — vector DB connections, API keys, schema migrations. If the agent's memory task is "remember what we decided about the database," a CLAUDE.md file does it for free. The overhead is only justified when the memory demands genuinely exceed what files can handle.
- **"Memory" is not one problem.** Working memory (current session scratchpad), episodic memory (past conversations), semantic memory (persistent knowledge), and procedural memory (learned behaviors) each have different retrieval requirements. A single tool — whether a vector store or a markdown file — cannot optimally serve all four. Teams that pick one tool for all memory needs end up with one tier done well and three tiers done poorly.
- **Retrieval quality is not proportional to retrieval complexity.** Redis Labs documented that vector similarity search frequently returns stale or irrelevant results when facts change over time. A flat file with a smart retrieval prompt sometimes outperforms a RAG pipeline built on an embedding index. The added infrastructure buys retrieval speed, not retrieval accuracy.
- **Memory infrastructure compounds failure surface.** Every memory layer is an attack surface. The MemGhost attack (S-2752) exploits the write path of long-term memory stores. A flat file with append-only semantics is easier to audit than a vector upsert API. More memory infrastructure means more places for corruption, injection, and inconsistency.
- **Context window constraints push teams toward memory systems prematurely.** Redis Labs documented that teams often reach for external memory because context windows feel small. But stretching the context window doesn't give you cross-session continuity — it just delays the session reset problem. A purpose-built memory layer solves the actual problem that external memory is needed to solve.

## The move

**Map your memory problem to a memory tier before picking a tool. Add complexity only when the simpler tier demonstrably fails.**

1. **Start at working memory.** Use in-context scratchpad / conversation buffer for the current session. This is free, zero-latency, and correct. It doesn't survive session reset — that's intentional. Don't try to make working memory do long-term memory's job.
2. **Graduate to flat file memory for semantic/procedural facts.** CLAUDE.md-style markdown files, `.env`-like config files, or a JSON state file solve ~70% of cross-session memory needs at zero infrastructure cost. Letta's benchmark proves this empirically. If the memory task is "remember X is true about this project," a file works.
3. **Reach for Mem0 when you have multi-user, multi-session memory at scale.** Mem0's strength is managing memory across many agents and many users simultaneously — entity tracking, user preferences, conversation summaries — with a managed API. Use it when file-per-project doesn't scale and you need memory that follows the user, not the codebase.
4. **Reach for Letta when you need the MemGPT-style memory architecture — core + archival tiers with LLM-controlled memory management.** Letta exposes an explicit memory-block API where the model decides what to promote from working to long-term memory. Best for agents that need to autonomously manage their own memory budget across long-running tasks.
5. **Reach for Zep/Graphiti when temporal relationships matter.** Zep's temporal knowledge graph tracks how facts change over time — not just that "user lives in Berlin" but when that became true and what it superseded. Use it when agents need to reason about event sequences, not just fact retrieval.
6. **Use vector stores for semantic search only after the above fail.** Qdrant → Weaviate → pgvector → Pinecone is the settled vector DB hierarchy (per Perea.ai 2026 survey). If you need keyword-agnostic, embedding-similarity-based retrieval and flat files aren't cutting it, reach for this tier. But benchmark it against flat files first — the bar is 74%.

## Gotchas

- **Premature memory infrastructure.** Teams add Mem0 or a vector store before proving flat files don't work. Letta's benchmark is a direct rebuttal: complexity is not quality. Start simple.
- **Treating memory as one tier.** A single vector store cannot optimally serve working memory, episodic recall, semantic knowledge, and procedural rules simultaneously. Pick the tier that matches the memory type you're actually storing.
- **Memory becomes stale and contradictory.** Facts change ("user moved from Berlin to Munich") but vector retrieval doesn't know when the old fact was superseded. Zep's temporal knowledge graph addresses this explicitly. Without it, you get confident retrieval of confidently-wrong facts.
- **Context window vs. memory are different problems.** Redis Labs documented that bigger context windows don't give you cross-session continuity. A 1M-token window still forgets everything on session reset. Don't trade memory infrastructure for a larger context window.
- **Memory write paths lack gates.** S-2752 (MemGhost) documents how adversarial content gets committed at write time but harms at retrieval time — potentially weeks later. A flat file with append-only semantics is auditable. An upsert API with embedding pipelines is not.
