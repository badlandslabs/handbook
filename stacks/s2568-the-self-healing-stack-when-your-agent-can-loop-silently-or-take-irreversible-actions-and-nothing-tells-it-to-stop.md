# S-2568 · The Self-Healing Stack — When Your Agent Can Loop Silently or Take Irreversible Actions and Nothing Tells It to Stop

Your agent is running. It has been running for 47 minutes. The logs show continuous activity — tool calls, LLM invocations, nothing erroring out. But it is not making progress. It is executing a plan that became invalid 38 minutes ago, re-executing a failed step with the same wrong parameters, and has already burned through 58,000 tokens. Meanwhile, another agent on the same system is spawning redundant subprocesses that are quietly contending for the production database. Neither agent raised an exception. Neither crashed. This is the stack for building the architectural resilience layer that makes agents recoverable without human intervention — before they loop, before they cascade, before they act irreversibly.

## Forces

- **Agents fail qualitatively differently than conventional software.** A web service crashes and logs a stack trace. An AI agent may silently loop for 35 minutes, spawn redundant subprocesses contending for shared resources, accumulate context until the model halts, or take an irreversible action before a human can intervene. The failure modes require qualitatively different remedies.
- **Standard retry logic breaks down with generative AI.** Retrying a prompt that fails due to a hallucinated tool argument is not the same as retrying a network timeout. Standard patterns assume the failure is the same each time — it isn't. Model outputs can be non-deterministic, token limit violations can corrupt subsequent steps, and hallucinations can cause downstream parsing failures that don't appear until three steps later.
- **The agent is the logic layer, and it can behave incorrectly without raising any exception.** The LLM decides what to try next, so retrying under its own guidance can re-produce the same failure. You need enforcement mechanisms that run orthogonal to the model's own decision-making.
- **Partial failures are the most dangerous.** When a 12-step plan breaks at step 9, the wrong responses are: stop entirely (losing all progress) or blindly retry from step 9 (which usually fails the same way). The right response is: checkpoint state, assess what is still valid, try a different strategy.

## The move

Implement a five-layer resilience architecture that handles the full failure taxonomy of AI agents — from infrastructure errors through agent-level plan breaks to cascading multi-agent failures.

**Layer 1 — Taxonomy before tooling.** Classify failures into four distinct types before choosing a response. Infrastructure failures (API rate limits, timeouts, network errors) are retryable with backoff. Tool failures (schema mismatches, missing credentials, permission errors) require tool-level fixes. Agent failures (plan breaks, hallucinated tool calls, context overflow) require strategy changes. Cascading failures (one agent's error propagates through shared state) require isolation. Mixing these up is the root cause of most failed recovery attempts.

**Layer 2 — Orthogonal enforcement mechanisms.** Do not rely on the LLM to judge when it has failed. The agent that is looping is also the agent deciding to keep trying. Implement step-counting (hard limit on tool calls per task), state checkpointing at each decision boundary (so recovery resumes from the last valid state, not the start), and process-level timers (wall-clock limits that interrupt even a "running" agent). These mechanisms run outside the agent's reasoning loop.

**Layer 3 — Per-tool circuit breakers with tuned thresholds.** Configure circuit breakers individually per tool, not globally. Critical tools (payment processing, database writes, auth operations) should trip immediately on failure (failure_threshold=1, recovery_timeout=120s). Resilient tools (web search, document retrieval) can tolerate higher thresholds before opening. This prevents one degraded tool from poisoning the entire agent's capability without blocking necessary recovery attempts.

**Layer 4 — Fallback chains, not fallback singletons.** When a primary tool fails, degrade to a carefully designed fallback chain rather than returning empty. The chain should progress: specialized tool → general-purpose tool → retrieval-augmented response → structured "cannot handle" admission with escalation path. A degraded response is almost always better than no response, and a fallback that returns "I couldn't do this — escalating to human" is a successful outcome, not a failure.

**Layer 5 — Dead letter queues with failure-type routing.** Send failed tasks to typed DLQs by failure mode, not one generic queue. Token limit violations go to a queue that splits the task. Hallucinated tool arguments go to a queue with re-prompted tool schemas. Timeout failures go to a retry queue with exponential backoff. DLQ workers should have their own smaller LLM prompts optimized for recovery, not the full task prompt. Tasks that exhaust all recovery strategies route to human review with full context preserved.

**Bonus — Supervisor pattern for multi-agent systems.** Deploy lightweight supervisor agents that monitor worker agents asynchronously. Supervisors track task progress, enforce time budgets, and can interrupt workers with strategic redirects (rather than just kill/restart). This is the pattern that handles cascading failures across distributed agent pipelines where no single agent has global state visibility.

**Bonus — Strategy-level checkpointing beyond crash recovery.** Checkpoint not just on crash, but on decision points. When an agent commits to a strategy (e.g., "I will solve this via file search"), save that state. If the strategy fails, the supervisor can restart from the decision point with a different strategy rather than losing all progress. This transforms failure from "start over" into "try the other approach."

## Gotchas

- **Treating resilience as infrastructure, not architecture.** Teams add logging and monitoring after building the agent, then wonder why the agent still loops. Resilience must be designed into the agent's execution loop from the start — checkpoint placement, circuit breaker thresholds, and fallback chains need to be co-designed with the agent's logic, not stapled on afterward.
- **Global circuit breaker thresholds.** Setting the same failure threshold for all tools means either tripping too fast on resilient tools or allowing critical tools to damage production before tripping. Tune per tool based on blast radius.
- **Designing fallback responses too late.** Fallback chains are only as good as the degraded responses they return. Designing "sorry, I couldn't do that" as the terminal fallback is not a recovery — it is a failure with extra steps. The terminal fallback should always produce an escalation artifact: structured failure context that a human or supervisor can act on.
- **Ignoring partial failures.** When a multi-step plan partially succeeds, the temptation is to either restart entirely (losing valid work) or continue blindly (into cascading failures). Checkpointing at each decision boundary is what makes partial recovery possible. Without it, you have no recovery options beyond "start over" and "give up."
