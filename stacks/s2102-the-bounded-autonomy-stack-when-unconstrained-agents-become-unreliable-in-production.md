# S-2102 · The Bounded Autonomy Stack — When Unconstrained Agents Become Unreliable in Production

You give your agent 47 tools and full decision authority. It loops. It calls the wrong API first, the second time it calls the right one but with stale data, and on the third attempt it gives up and hallucinates an answer. No error fired. The task appeared to complete. Your users didn't complain — until three weeks later when the downstream system ingested bad data and nobody could trace where it came from.

This is the bounded autonomy failure: agents without explicit scope, tool-curation discipline, and trajectory visibility will find the worst possible interpretation of "figure it out."

## Forces

- **The tool-proliferation trap.** More tools mean more failure modes. Every tool is an additional API to fail, a permission boundary to mishandle, and a decision branch the agent must correctly route through. Tool count and reliability are inversely correlated in production.
- **Context window is not memory.** Even frontier models with 200K+ token windows reset after every API call. Agents that need to carry state across sessions require purpose-built memory infrastructure — this is not a model problem, it's an architecture problem.
- **Evaluation measures answers, not trajectories.** A task-success metric hides the path. An agent that reaches correct output via 12 tool calls, two loops, and a dead-end recovery scores the same as one that calls the right tool once. Only trajectory-level metrics catch the difference.
- **The "agentic" label has no consensus.** Practitioners disagree on whether a system with hardcoded routing is "agentic." This matters because it determines how much reliability engineering gets applied. A system called "workflow automation" gets rigorous testing; one called "AI agent" sometimes ships without it.
- **Unbounded loops are the most expensive failure mode.** A looping agent burns tokens at maximum rate until a rate limit or timeout stops it. Unlike a crashed service, it returns a result — making the failure invisible until the bill arrives.

## The Move

Constrain autonomy structurally — at the architecture level — rather than hoping prompting discipline holds in production.

**1. Design tool sets as constrained interfaces, not open-ended toolboxes.** Anthropic's engineering guidance recommends starting with the simplest possible tool set and expanding only when a specific capability gap is demonstrated, not anticipated. Shopify Sidekick hit a "tool complexity wall" at ~50 tools where routing accuracy degraded and tool-call errors compounded — solved not by smarter routing but by reorganizing the tool taxonomy into hierarchical namespaces.

**2. Layer memory explicitly rather than relying on context windows.** Production systems use three distinct tiers: working memory (current session, in-process), short-term (session-persistent, days), and long-term (cross-session, user preferences, learned facts). Redis's AI memory architecture identifies that context windows and memory serve different purposes — windows provide throughput for current tasks; memory provides recall that persists across sessions. The Mem0 2026 benchmark report shows 21 frameworks and 20 vector stores now filling this space, with LoCoMo (1,540 questions) and LongMemEval (500 questions) as the leading evaluation benchmarks.

**3. Checkpoint state at every decision boundary.** LangGraph's checkpointing model — derived from Google's Pregel — serializes agent state (tool calls made, intermediate results, conversation history) to durable storage at each graph node transition. This enables resume-from-failure rather than restart-from-scratch. The framework reached 1.0 in October 2025 with zero breaking changes, processes 40M+ monthly PyPI downloads, and powers production agents at Uber, LinkedIn, Klarna, BlackRock, JPMorgan, and Cisco.

**4. Build a verifier layer for semantic correctness, not just technical success.** Preporato's error taxonomy identifies that agents fail in ways traditional try-catch cannot catch: tools that return HTTP 200 with semantically wrong results, JSON that parses but violates schema, API calls that succeed against the wrong endpoint. The pattern: pipe tool outputs through a small "verifier agent" whose only job is to confirm the output actually answers the query. If it doesn't, trigger a self-correction loop as if it were a hard error.

**5. Instrument trajectory, not just outcome.** Stripe's agent benchmark methodology (for evaluating AI-generated Stripe integrations) uses deterministic test suites with deterministic graders — not LLM-as-judge — across three components: a full coding environment, deterministic test execution, and binary pass/fail outcomes. "A mostly correct integration is a failure; payments require 100% accuracy." This mirrors how Stripe approaches all payment reliability: no probabilistic quality gates for financial accuracy.

**6. Cap loop depth explicitly.** Every agentic loop needs a hard maximum step count. When the cap is hit, escalate — either to a human reviewer, a simplified fallback path, or a failure signal. The HN practitioner consensus (2024 Ask HN on agentic production systems) is that most agent failures in production are invisible loop-hunting: the agent keeps trying variations until something sticks, and nobody notices because the task eventually completes.

## Gotchas

- **Calling it an "agent" lowers reliability expectations.** Teams apply less rigorous testing to systems labeled "AI agents" than to "workflow automation." The Shopify pattern — treating the agentic system with the same engineering rigor as any production service — is the exception, not the norm.
- **Memory and context windows solve different problems.** Adding more context window tokens does not substitute for a memory architecture. Agents with access to large context but no persistent memory still treat every new session as brand new.
- **LLM-as-judge evaluation introduces drift.** Using a second LLM to evaluate agent outputs compounds the reliability problem rather than solving it. Stripe's deterministic test-suite approach is the more rigorous alternative for tasks with binary outcomes.
- **Loop-capping without trajectory logging loses the failure signal.** If you cap the loop but don't record what happened inside it, you've bounded the cost but lost the diagnostic data. Checkpoint state AND cap depth.
- **Tool descriptions are prompt injection surface.** The more tools an agent has access to, the more surface area for adversarial or accidental tool-description manipulation. Tool registries need the same input-validation discipline as any API endpoint.
