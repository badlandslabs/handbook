# S-2483 · The Agent Eval Stack: When Your Agent Scores 92 on Benchmarks and You Cannot Explain Why Users Are Complaining

Your agent passes every benchmark. Your test suite is green. Your team shipped with confidence. Six weeks later, support tickets are piling up, NPS is dropping, and you have no idea where the failure is. Benchmarks measure what they can measure — not what your users actually experience. This is the agent eval gap, and it is the most expensive blind spot in production AI today. Only 5% of engineering teams have AI agents in production, and fewer still have evaluation systems that actually catch degradation before users do.

## Forces

- **Benchmarks reward averages, users experience tails.** A 78% benchmark score masks the 22% of cases where the agent is confidently wrong — and those are the cases users escalate.
- **Evals are an afterthought, not an architecture.** Most teams build the agent first and bolt on testing later, if at all. The eval surface area never catches up to the agent complexity.
- **Traditional LLM metrics (BLEU, perplexity) measure generation quality, not task completion.** Agents take actions, invoke tools, recover from errors — none of which map to text-similarity scores.
- **The cost of undetected failure compounds.** A Stanford HAI 2025 report found 63% of teams deploying multi-agent systems experienced major reliability issues post-launch that didn't appear in sandbox testing. Gartner projects 40%+ of agentic AI projects will be cancelled by end of 2027.
- **Evals create a development flywheel — without them, iteration is guesswork.** Teams without evals rely on "vibe checks" that consistently miss regressions a prompt tweak introduced.

## The move

Shift evaluation from a post-launch QA activity to a first-class production system with three layers: node-level precision, session-level outcomes, and system efficiency. Treat evals as a continuous pipeline, not a one-time suite.

- **Measure trajectories, not just outcomes.** Track the full execution path — tool selections, parameter correctness, step sequencing, and intermediate decisions — not just whether the final output looks right. A correct answer via wrong reasoning is a latent bug.
- **Run LLM-as-Judge with calibrated skepticism.** Use a separate model to evaluate agent outputs, but acknowledge known failure modes: position bias (judges favor the first or last option), verbosity bias, and self-preference. Cross-validate against human judgment on a sample. The NVIDIA Judges Verdict study found real gaps between claimed judge accuracy and measured human agreement.
- **Instrument at three layers.** System efficiency: token cost, latency, tool call counts. Session-level: task success rate, trajectory quality, step count. Node-level: tool selection accuracy, parameter validity, semantic correctness of tool outputs.
- **Close the benchmark-to-production gap with domain-specific datasets.** Public benchmarks (MMLU, HumanEval) are baselines, not proxies for your domain. Elite teams curate production interaction logs into eval datasets, creating a feedback loop where real failures become regression tests.
- **Add observability into the eval loop.** Log every decision point, tool invocation, and intermediate state. Correlate eval failures with production signals — error rate spikes, support ticket themes, user abandonment points. Splunk and Microsoft both document this as the minimum viable observability surface for multi-agent deployments.
- **Trigger evals on code change, not just deployment.** Integrate eval runs into CI/CD so that a prompt change or tool definition update is evaluated against the full regression suite before it reaches production. Run progressive canary deployments against live eval traffic.

## Gotchas

- **A high benchmark score is a local maximum, not a launch signal.** Benchmarks measure performance on curated test cases. Real inputs are noisier, adversarial, and out-of-distribution. If your eval suite doesn't include production interaction logs, you're measuring a proxy of a proxy.
- **LLM-as-Judge has known biases — don't treat it as ground truth.** Position bias and self-preference (judging your own outputs more favorably) are documented failure modes. Use judge outputs as a signal, not a verdict, and spot-check against human annotators.
- **Evals that only measure final output miss the most expensive failure modes.** An agent that reaches the right answer via a dangerous or inefficient path is not reliable — it's lucky. Trajectory-level evaluation is where you catch tool misuse, hallucinated API parameters, and silent context drops.
- **Without observability, evals are a snapshot, not a system.** Running an eval suite once at deploy time creates a green-light illusion. Continuous eval monitoring against live production traffic is what catches regressions that emerge from data drift, API changes, or model updates.
