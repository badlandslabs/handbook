# S-1701 · The Tool Augmentation Stack — When Your Agent Needs Hands

An agent without tools is a very expensive autocomplete. Give it the wrong tools and you have an expensive autocomplete that also deletes your production database. The craft is not in the number of tools — it is in choosing tools that match the agent's actual decision radius, managing token overhead from tool definitions, and building the execution layer that turns tool calls into real-world actions. The evidence from 2025–2026 practitioner threads converges on three non-obvious lessons: the canonical tool set is smaller than you think, tool definitions are the hidden token killer, and the "code as tool" pattern cuts costs by an order of magnitude.

## Forces

- **More tools degrade performance, not just cost.** Anthropic's engineering blog documented that 58 tool definitions from a multi-server MCP setup consume ~55K tokens before the agent has read a single user prompt. Adding Jira alone adds ~17K tokens. Teams that give agents 30+ tools routinely see worse tool selection accuracy — the agent becomes overwhelmed by options and picks the wrong tool or wrong parameters.
- **The canonical tool set is remarkably thin.** Across Anthropic's Claude Agent SDK, OpenAI's Agents SDK, Google's ADK, and open-source stacks like Smolagents, the standard tools developers actually give agents in production are: bash execution, file read/write, web search, and glob pattern matching. Not 50 tools. Not a full API integration library. Four primitives that map to what developers actually do.
- **Tool definition quality matters more than tool quantity.** A well-described tool with a clear docstring, explicit parameter types, and a description of failure modes outperforms five loosely-described tools. The model uses the description to select and parameterize — vague descriptions create two failure modes: wrong tool selection and wrong parameters (e.g., `notification-send-user` vs. `notification-send-channel`).
- **Browser/computer use reshapes what "tool" means.** The 2025–2026 shift from text-only agents to screen-based agents (OpenAI Operator, Claude's computer use, browser automation tools) introduced a new class of tools that observe and act on graphical interfaces rather than APIs. This fundamentally changes what operational work is automatable — and introduces new failure modes around UI fragility.

## The move

**Start with the four canonicals. Add tools only when you can describe the failure mode.**

- **Bash execution** — the universal tool. Agents that can run shell commands have the broadest possible action surface. Sandboxed, time-limited, with a clear output boundary. This is the tool most production coding agents converge on (Claude Code, Codex, etc.).
- **File read/write** — agents that modify code or configuration need structured file access. Operations are idempotent when possible (write with a hash-check, read before write). Treat as a git-aware operation, not raw disk I/O.
- **Web search** — for agents that need current information. Treated as a read-only retrieval tool with a rate limit. The agent's job is to synthesize, not to browse indefinitely.
- **Glob + grep** — for codebase navigation. Agents that work on existing codebases need to find files and patterns before touching them. This separates "find the right file" from "modify the file," reducing the blast radius of each tool call.
- **MCP as the integration layer** — MCP (Model Context Protocol) is the de facto standard for connecting agents to external tools as of 2025–2026. It replaces bespoke API integrations with a unified RPC layer. Use the Streamable HTTP transport for production. Register tools dynamically at request time, not at initialization, to avoid loading all tool schemas on every call.
- **Dynamic tool loading over upfront registration** — Anthropic's advanced tool use features (November 2025) introduced a "tool search tool" that lets the agent discover and load tool definitions on demand. This cuts the initial context cost from ~55K tokens to near zero for tasks that don't need most tools. The agent calls the tool search tool with a description of what it needs; the system returns the matching tool definitions.
- **"Code as tool" for high-tool-count scenarios** — when an agent connects to hundreds of tools, present them as code APIs rather than individual function calls. The agent writes a short program to call multiple MCP tools in sequence, passing data between them. Anthropic benchmarks show 90–98.7% token reduction on tool overhead. The code execution runtime acts as a local router — tools call other tools without round-tripping through the model.

## Gotchas

- **Loading all tools at initialization is the default and it is wrong for any agent with more than ~10 tools.** It is not a production-ready pattern. Every MCP client worth using supports dynamic or lazy tool loading. If yours doesn't, swap clients.
- **Browser automation tools are fragile in production.** UI elements change, selectors break, and the agent may spend more time recovering from broken selectors than doing useful work. Prefer API access over browser automation when available. When browser automation is necessary, implement screenshot verification after key actions — confirm the expected state before continuing.
- **Bash execution needs strict sandboxing.** An agent with unrestricted shell access is a remote code execution vulnerability. Use time limits (60s hard cap), environment variable allowlists, network egress restrictions, and filesystem path allowlists. Treat the agent's bash tool like you would a less-trusted service account.
- **Tool descriptions are prompts.** If the agent picks the wrong tool, 90% of the time the description was ambiguous or the parameters were poorly typed. Invest in docstrings and Pydantic parameter schemas the same way you invest in your agent's system prompt.
- **Adding a tool adds failure modes.** Every new tool is a new way for the agent to fail. The tool count decision is a risk decision, not a capability decision. Each addition should come with a documented failure mode and a recovery strategy.
