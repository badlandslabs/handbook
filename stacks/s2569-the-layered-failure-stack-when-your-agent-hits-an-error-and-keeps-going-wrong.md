# S-2569 · The Layered Failure Stack — When Your Agent Hits an Error and Keeps Going Wrong

You shipped the agent. It ran for 47 minutes. It submitted four fraudulent refund requests, deleted a staging database, and sent apologetic emails to the wrong customers — each step "correct" within its local context, each error cascading silently into the next. The problem is not that your agent fails. The problem is that your failure handling is a single retry loop, and failures in production agents are not singular — they propagate.

## Forces

- **Error propagation is the central bottleneck.** A single failure cascades through planning, memory, and action modules. Without explicit error taxonomy, the agent cannot distinguish a transient blip from a structural failure, and treats both identically.
- **Agents operate at machine speed past the point of recovery.** By the time a human notices something is wrong, the agent has already executed the downstream consequences of the error. Speed and autonomy are in tension with safety.
- **Simple retry loops are not resilience.** Transient errors (network blips, rate limits) respond to retry. Systematic errors (bad tool output, prompt injection, corrupted memory state) amplify under retry. Most teams implement one pattern and call it done.
- **Failure mode visibility is often absent entirely.** HN threads in 2025-2026 consistently surface that teams have no trace of what the agent did step-by-step, no audit trail for post-mortems, and no cost tracking — making failure diagnosis retrospective archaeology.

## The Move

Implement a layered defense architecture that treats each failure class differently. The stack from production teams:

- **Layer 1 — Retry with exponential backoff + jitter.** For transient errors: network timeouts, 429 rate limits, temporary service unavailability. Add jitter to prevent thundering herd. Typical: 3 retries, delays of 1s → 2s → 4s with ±20% jitter. Latency impact: +1-5s.
- **Layer 2 — Fallback model or tool.** When the primary model/tool consistently fails for a category of input, route to a fallback. Examples: primary LLM times out → smaller/faster model as fallback; primary search API fails → vector search fallback. Fail gracefully, log the divergence.
- **Layer 3 — Circuit breaker.** When a downstream dependency is degraded (external API returning errors above a threshold), stop hammering it and return a safe default. Prevents cascading failures from propagating backward through the system. Set thresholds based on error rate, not just error count.
- **Layer 4 — Structured error taxonomy with routing.** Explicitly classify errors: `TRANSIENT`, `RATE_LIMIT`, `TOOL_FAILURE`, `CONTEXT_OVERFLOW`, `PROMPT_INJECTION`, `IRREVERSIBLE_ACTION`. Map each class to a recovery strategy. A prompt injection is not a rate limit — they need different handlers.
- **Layer 5 — Self-healing runtime guardrails.** Systems like VIGIL inject checkpoints between agent actions, evaluating whether the proposed next action violates safety constraints before execution. Claims: 24%+ improvement in task success rates when combined with layered recovery. Human-in-the-loop approval gates for high-stakes actions (financial transactions, data deletions, external communications) — not as a blocking human-in-every-step bottleneck, but as a conditional gate based on action classification.
- **Layer 6 — Observability and audit trail.** Every agent action should emit a trace event: what was decided, what tool was called, what output came back, what the agent concluded from it. Platforms like AgentShield, LangSmith, or custom instrumentation provide execution traces, cost tracking per action, and risk detection on outputs. Without this, post-mortems are guesswork.

## Gotchas

- **Treating all errors as retryable.** Transient failures respond to retry. Systematic failures (prompt injection, tool returning corrupted data, memory state corruption) amplify under retry — the agent replays the same bad reasoning with the same bad context. Separate error classes before choosing a strategy.
- **No action classification before execution.** Not all actions are equal risk. Refund requests, database writes, external API calls, and customer-facing messages need pre-execution gating; read-only queries and draft operations do not. Classify actions, then apply proportional safeguards — not uniform safeguards, which either over-constrain safe actions or under-protect risky ones.
- **Gating everything with human approval.** The opposite extreme: requiring human sign-off on every agent action makes the agent unusable at scale. Effective teams gate conditionally based on action risk classification, not uniformly. The goal is human oversight, not human-in-every-step.
- **Missing the gap between "finished running" and "finished correctly."** ashutoshtripathi (Principal ML Engineer) reported discovering their agent completed tasks at 95% rate but was only actually correct in 70% — the agent was finishing without errors while producing wrong outputs. Final-error-rate metrics miss this entirely; you need trajectory-level tracing and output verification against ground truth.
