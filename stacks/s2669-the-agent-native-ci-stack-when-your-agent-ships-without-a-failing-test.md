# S-2669 · The Agent-Native CI Stack — When Your Agent Ships Without a Failing Test

You ship a prompt revision at 4pm on Friday. Your code CI passes. Your test suite passes. You deploy. Monday morning, the agent is calling the wrong tools on 30% of customer support tickets — a regression that emerged from a two-word change in the system prompt. There is no failing test because you have no CI for agent behavior. You caught it only because users complained.

This is the agent-native CI gap: the deployment pipeline that works for deterministic software actively misleads you about non-deterministic agents. Your CI knows how to block a broken build. It does not know how to block a degraded agent.

## Forces

- **Agent behavior lives in seven places.** Prompt, model version, tool definitions, retrieval configuration, guardrail policy, memory state, orchestration logic — each can silently degrade behavior without any code change. Traditional CI tracks only one of these.
- **Standard benchmarks are gamed.** UC Berkeley's RDI team built an exploit agent that scored 100% on SWE-bench, WebArena, OSWorld, GAIA, Terminal-Bench, FieldWorkArena, and CAR-bench without solving a single task. A 10-line `conftest.py` "resolves" every SWE-bench instance. A fake `curl` wrapper scores perfectly on Terminal-Bench. Navigating to `file://` in Chromium reads the gold answer directly. Every public leaderboard teams optimize against is gameable.
- **The pass/fail line moves.** A model upgrade that improves coding performance can degrade customer support behavior. A guardrail that catches toxicity can start blocking legitimate queries. Without a frozen evaluation reference, every change is an uncontrolled experiment.
- **Probabilistic outputs break traditional assertions.** String equality and regex assertions either pass trivially or fail arbitrarily for non-deterministic outputs. You need new assertion semantics calibrated for distribution, not determinism.

## The Move

Treat agent behavior as a testable contract enforced by merge-blocking gates. The key move: pin a golden dataset of real production failures and regressions, run it on every PR, and block merges when the pass rate falls below a configurable threshold.

**The CI-for-agents pattern** breaks into four components:

- **Golden dataset as first-class artifact.** Freeze representative agent inputs, expected trajectories, and acceptable outputs as versioned test cases. Source them from real production failures (S-2661), not synthetic examples. Treat the dataset with the same discipline as a schema: review it on PR, version it in git, delete it when the behavior it tests is intentionally removed. The `agent-eval-framework` project formalizes this as four evaluation dimensions — each with a threshold, each blocking merges independently.

- **Component-level eval pipelines.** Rather than one eval suite for the whole agent, run separate pipelines for each behavioral surface: prompt eval (does the instruction change what the agent does?), tool eval (does adding/removing a tool change the call graph?), model eval (does swapping the model change outputs?), and guardrail eval (does the safety policy catch the right things?). This pins regressions to their cause. `AgentClash` implements this as a three-column reference design: candidate (new change) vs. baseline (last stable release) vs. control (known edge case), with a structured verdict output.

- **LLM-as-judge with guardrails, not raw scoring.** Raw judge scores are unreliable — models exhibit position bias (preferring the first of two options), numeric scale insensitivity (treating 8/10 and 3/10 as equivalent), and sycophancy (rating outputs higher when the judge model is from the same provider). The production pattern uses calibrated rubrics with explicit comparison anchors, position-swapped dual runs (run A vs B and B vs A, average the scores), and a human-retained override for scores near the threshold. The `gaurav-quality-platform/agent-eval-framework` also runs LLM judges at the trajectory level — not just final output — catching mid-trajectory failures that output-only eval misses.

- **Shadow rollout before full deploy.** After the CI gate passes, route 1–5% of production traffic through the new agent version in shadow mode — it executes but its outputs are logged, not delivered. Compare trajectory distributions, tool call frequencies, and cost-per-task between shadow and live. Only promote to full rollout when shadow metrics are within tolerance. `AgentClash` automates this step: `agentclash run create --follow` replays a timeline from production traces, scores the candidate against the baseline, and produces a structured verdict before CI clears release.

## Gotchas

- **Golden datasets rot.** Without a continuous capture loop from production failures (S-2661), your golden dataset covers only what you imagined. After six months, it may represent 20% of actual failure modes. Set a quarterly review to retire stale test cases and incorporate new production failures.
- **LLM judges are unreliable near thresholds.** Scores within 5% of the pass/fail line have higher variance than scores far from it. Run judge-LLM evaluations with three-seed sampling and use the mean, not the first score. If the spread is large, escalate to human review rather than blocking on a noisy signal.
- **CI gates slow down prompt iteration.** Teams that set the pass threshold too high (e.g., 95%) find that prompt engineering becomes unbearably slow — even good prompts fail on edge cases that aren't worth fixing. The 90% threshold is a common starting point, with component-specific thresholds for different behavioral surfaces.
- **Shadow rollout catches distribution shift, not correctness.** A shadow test that passes may still be wrong if the new agent is wrong in the same way as the old one. Shadow mode validates improvement or equivalence on observed patterns; it cannot discover unknown failure modes. Combine shadow rollout with the golden dataset gate, not replace it.
