# S-2325 · The Privilege Boundary Stack — When Your Agent Has More Access Than It Needs, and So Does Everyone Else

Your security team reviewed the agent's permissions. Reader role on the CRM, no delete rights, scoped to the user's own data. That check passed. What the check missed: the maker mode connector runs on the creator's admin credentials regardless of who invokes it. A user with zero CRM access can invoke the agent and read everything. The agent is working exactly as designed. Your access controls were bypassed without a single technical violation.

## Forces

- **Configuration authority ≠ effective authority.** The OAuth resolution at runtime can silently widen what the configuration layer scoped narrow. A connector scoped to "read" at config time may carry write permissions after token resolution — leaving a gap that configuration-time review never catches.
- **Agents are first-class principals that IAM wasn't built for.** Traditional IAM assigns permissions to humans or service accounts with known, bounded jobs. Agents plan, chain actions across multiple SaaS apps, and operate continuously without human oversight. No traditional IAM program treats the agent itself as the risk-bearing identity.
- **90% of enterprise agents hold more access than they'll ever need.** This is not a misconfiguration — it's the default state of agentic AI deployment in 2026. The number stays high because the architectural reason (maker mode credential inheritance, broad tool bindings) is invisible to standard security reviews.
- **Toxic combinations make medium-severity findings critical.** An over-permissioned agent alone is a medium risk. Pair it with org-wide accessible invocation, maker mode on admin credentials, or an orphaned creator account — and the blast radius becomes critical. Single-factor scoring misses this.
- **The tool authorization gap.** Tool permissions live in the space between IAM and application security, and that space has no owner. IAM owns user identity. AppSec owns API contracts. Nobody owns the authorization model for what an agent can call, when, and on whose behalf.

## The move

Treat every agent as a first-class security principal with its own identity, scope, and tool binding — not as an extension of its creator's credentials.

- **Define agent identity explicitly** before autonomy expands. Agents need their own identity model (e.g., Microsoft Entra Agent ID) with explicit scoping, separate from the creator's identity. Pair this with tool authorization middleware that enforces allowlists at the call site, not just at configuration time.
- **Scope three dimensions: resource, data, and operation.** Constrain permissions by resource boundary (tenant, workspace, site), data boundary (collection, label, sensitivity), and operation boundary (read/write/export/admin). Do this at provisioning and re-review when workflows or the deployment environment change materially.
- **Separate duties at the tool level.** When a workflow includes both evidence gathering and remediation, use different roles or tools for read versus write. Gate high-impact actions — delete, export, privilege changes — behind step-up approvals or human-in-the-loop checkpoints.
- **Implement action classification with escalating gates.** Classify agent actions by impact level. Route medium-impact calls through synchronous confirmation. Route high-impact calls through a separate approval workflow with an audit trail. The agent proceeds asynchronously on low-impact work; the human gates the rest.
- **Score toxic combinations, not individual factors.** Flag critical scenarios: shadow agent + org-wide scope + sensitive data; maker mode + admin credentials + public invocation URL; orphaned creator account + active MCP connections to unregistered domains. These combinations create blast radii that no single-factor check surfaces.
- **Re-evaluate when the environment changes.** Any request to widen a grant should be treated like a production change: state the use case, identify the new trust boundary, replay recent agent actions under the proposed grant, verify the blast-radius caps still hold, and record the approval.

## Gotchas

- **Configuration-time scoping stops at the OAuth resolution boundary.** If your review checked what the connector is configured for but not what it resolves to at runtime, you've reviewed the wrong thing. Validate effective authority inside each connected application.
- **Maker mode is the default in many platforms** and was designed for maker productivity, not security. Until recently, blocking maker-provided credentials required no admin action — meaning most deployments ran with it enabled silently. Check your platform's default before assuming a safe baseline.
- **Sandbox boundaries are defined by the evaluator, not the model.** The OpenAI incident occurred during a controlled security test, but the test's assumptions about the environment's perimeter were wrong. "Isolated" is a property of your topology, not a property you can declare.
- **Indirect prompt injection doesn't require user action.** When an agent processes external content (email, documents, web pages), injected instructions execute with the agent's full privilege context. Content filtering at ingestion time is necessary but not sufficient — authorization at the action level must hold regardless of where the instruction originated.
