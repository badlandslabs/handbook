# S-2030 · The Semantic Silent Failure Stack — When Your Dashboard Is Green But Your Customers Are Leaving

Your agent's success rate looks fine. 94% task completion. Average latency under 2 seconds. No error logs. You found out it was silently failing 12% of the time only when a customer complained — the agent had been sending incorrect policy information to users for two weeks, fully completing its task while being completely wrong. Standard observability caught the crash cases. It never caught the semantic ones.

## Forces

- **Traditional monitoring sees errors; it cannot see wrong answers.** Error rate, latency, and token count are proxy metrics for quality — they tell you the agent ran, not whether it ran correctly. A support agent can complete every conversation with low latency and consistently recommend the wrong refund amount.
- **The evaluation lag is your worst enemy.** Offline eval suites are always behind production. By the time you build a test case for the failure mode your users hit, dozens more have experienced it. Real input drift (new user behaviors, edge cases nobody anticipated) makes offline suites permanently stale.
- **Trajectory failures look like successes from the outside.** The agent reached the right destination through the wrong tool sequence, ignored a constraint that didn't bite this time, or made a lucky recovery. Final-output evaluation misses all of this.
- **The JADEPUFFER lesson applies here too.** An agent that silently drifts into dangerous territory — wrong policy, data corruption, unauthorized action — can cause damage for days before anyone notices. Silent failure at scale is a security and operational risk.

## The Move

The pattern that production teams converge on has four layers, from post-hoc detection to real-time prevention:

- **Trace-level semantic auditing.** Rather than monitoring aggregate metrics, scan every agent trace against the agent's own instructions using an LLM judge. Does the trace's final action align with the stated policy, constraints, and intent? This catches cases where the agent completed the task but violated a boundary. Lemma (YC F25) was built specifically for this: "catches the silent, semantic failures your observability tools miss, where your AI agent looks like it worked but didn't." They surface recurring failure patterns across traces and route them to Slack with P0/P1 triage.
- **Online evaluation on live traffic.** Route a statistical sample of production traces through an LLM judge continuously — not a one-time test before shipping. The eval runs in production alongside the agent, scoring every Nth interaction. This closes the eval lag problem: new failure modes get detected the day they appear. Lemma automates this by creating an "online eval" for every deployed fix — if the same issue reoccurs, it fires immediately. A super-majority of YC agent builders report that keeping offline eval suites up to date is practically impossible; online evaluation on live traffic is the practical alternative.
- **Structured trace instrumentation with OpenTelemetry.** Before you can audit traces, you need traces worth auditing. Chatwoot's "Captain" support agent had zero visibility into why it randomly responded in Spanish — they didn't know which documents were retrieved, which tool calls fired, or what the exact input/output was at each step. The HN consensus (144 points, 2025) is that OpenTelemetry is becoming the standard for agent observability, providing the structured span data needed for trace-level evaluation. The alternative — vendor-specific instrumentation — creates fragmentation that makes cross-team auditing impossible.
- **Agent-as-a-judge for trajectory evaluation.** Standard LLM-as-a-judge scores the final output. Agent-as-a-judge evaluates the entire trajectory — it can observe intermediate steps, use tools to verify claims against ground truth, and give granular feedback about *which* step went wrong and *why*. The arXiv paper (2610.10934) benchmarked agent-as-a-judge against LLM-as-a-judge and human evaluation: it "dramatically outperforms LLM-as-a-Judge and is as reliable as our human evaluation baseline." Applied to production monitoring, this means a judge agent can catch mid-trajectory failures a simple output scorer would miss.
- **Human-in-the-loop for high-stakes actions.** For agent actions with real-world consequences (database writes, API calls, financial transactions), require human approval before execution or route to a human for spot-checking. AgentShield (mentioned in HN discussion, 2026) provides risk detection on outputs with a 2-line integration into LangChain, CrewAI, and OpenAI Agents SDK. This doesn't replace automated monitoring — it layers on top for the cases where automated monitoring is insufficient.

## Gotchas

- **Metric-green, semantic-red is the dangerous combination.** If your dashboard shows 98% success but you have no trace-level audit, you are flying blind on the 2% that matters. Always instrument traces before you rely on aggregate success metrics.
- **LLM-as-a-judge has known failure modes on its own outputs.** Using the same model that produced the output to judge it creates confirmation bias. Use a different model for evaluation, or use agent-as-a-judge which at minimum has tooling access to verify claims against ground truth.
- **Sampling rate matters for cost/quality tradeoff.** Evaluating every trace is expensive. A representative sample (stratified by task type, user segment, or risk level) catches most failure modes at a fraction of the cost of full-coverage evaluation.
- **Eval suites go stale; the production loop doesn't.** Offline test sets capture failures you already know about. Production-derived evals (cases surfaced by trace audits) capture the failures you don't. The feedback loop has to run continuously, not just at deploy time.
