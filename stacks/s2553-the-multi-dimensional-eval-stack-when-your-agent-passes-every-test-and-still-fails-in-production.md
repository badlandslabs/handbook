# S-2553 · The Multi-Dimensional Eval Stack — When Your Agent Passes Every Test and Still Fails in Production

*Your agent scores 94% on task accuracy. It also costs $4.70 per task (vs. a $0.12 alternative with 91% accuracy), fails silently on 30% of edge cases, and hallucinates confident errors that look identical to correct outputs. Accuracy is one dimension of agent quality. The stack is the rest.*

## Forces

- **Accuracy is necessary but not sufficient.** A 90% accurate agent that costs 40x more, requires 3 retries per task, and produces unrecoverable errors on the remaining 10% is not a 90% useful agent — it's a liability. Existing agent benchmarks measure accuracy; they don't measure cost, reliability, latency, or safety.
- **Standard software testing breaks for agents.** Agents are non-deterministic, stateful, and tool-dependent. Unit tests with fixed inputs produce different outputs on different runs. Output quality is context-dependent, not binary. You can't assert `expected == actual` when `actual` is a free-form plan that might succeed or fail three steps downstream.
- **Single-dimension optimization is a trap.** Teams that optimize only for accuracy end up with agents that are expensive, slow, and brittle. Teams that optimize only for cost end up with agents that are cheap and wrong. Multi-dimensional evaluation is not optional — it's the difference between a demo and a product.
- **Eval quality compounds.** A good eval framework catches regressions before they ship, surfaces real failure modes from production, and provides signal that improves the agent over time. A bad eval framework gives false confidence and passes broken agents.

## The move

Build a multi-dimensional evaluation pipeline that treats accuracy, cost, reliability, latency, and safety as co-equal first-class metrics. Combine golden-dataset scoring, LLM-as-judge evaluation, and production trace collection into a unified pipeline that gates releases and continuously grows the test corpus.

- **Define 5 evaluation dimensions, not 1.** The CLEAR framework (Cost, Latency, Efficacy, Assurance, Reliability) captures what accuracy-only metrics miss: cost-per-task and token efficiency, end-to-end latency under load, task completion correctness with environment-grounded verification, safety and policy compliance, and consistency across multiple runs. An agent that scores 60% on a single run but 25% on 8 consecutive runs is not reliable — pass@k and variance are as important as pass@1.
- **Use golden datasets as regression gates, not aspiration targets.** OpenAI's data agent team treats golden question-answer pairs as "unit tests that run continuously during development" and "canaries in production." Every prompt change, model swap, or tool modification runs against the golden dataset and fails the build if scores regress. Golden pairs are not benchmarks — they are owned, versioned, production infrastructure.
- **Build the golden dataset from production failures, not imagination.** The highest-signal regression cases are real failures that happened in front of real users. Arthur's playbook: production failure → trace capture → test case extraction → golden dataset → CI gate. This surfaces edge cases no engineer would have invented and grows the test corpus continuously. Synthetic prompts cover what the team thought of; production traces cover what users actually did.
- **Wire LLM-as-judge for trajectory evaluation, not just output grading.** Static outputs can be graded by checking against a reference answer. Agent trajectories — the full sequence of tool calls, reasoning steps, and intermediate states — require a judge that can observe process, not just outcome. Agent-as-a-judge uses a secondary LLM agent to monitor the primary agent's action log, give granular feedback on each step, and catch failures that only manifest mid-execution. Critically: use a different model family for the judge than for the agent to prevent the agent from learning to game the judge.
- **Integrate evals into CI/CD as release gates.** An eval harness that nobody runs has no value. The GitHub `agent-eval-arena` project models the right pattern: versioned golden datasets, multi-scorer execution, regression detection across model versions, and a gate that returns `pass`/`fail` for canary promotion. Eval is not a notebook — it's a pipeline stage.
- **Track human signal to validate automated scores.** Automated evals don't replace user feedback. Track session abandonment, thumbs down, escalations to human agents, and correlate these with automated scores. If your LLM-as-judge scores don't track user satisfaction signals, recalibrate the judge rubric.

## Evidence

- **arXiv study (2025):** Systematic analysis of 12 agent benchmarks found that 85% of enterprise teams evaluate only on accuracy, ignoring cost (50x variation for similar precision), reliability (performance drops from 60% single-run to 25% over 8 runs), and safety. Proposes the CLEAR framework to close these gaps. — [arXiv:2511.14136](https://arxiv.org/html/2511.14136v1)
- **Anthropic engineering blog (2026):** Defines the eval vocabulary (task, trial, grader, harness) and the core insight that agents are systems, not models — evaluating them requires outcome-grounded grading (did the flight reservation actually exist in the database?) and trajectory-level observation, not just transcript inspection. — [Demystifying Evals for AI Agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- **MAP study (arXiv, 2026):** First large-scale study of 86 deployed AI agents across 26 domains found that 73% of teams cite productivity as the primary driver — and productivity is inherently multi-dimensional (time savings + cost + reliability). Latency is a manageable friction, not a hard stop. Evaluation challenges are the top reported obstacle. — [Measuring Agents in Production (MAP)](https://arxiv.org/html/2512.04123v1)
- **InfoQ article (2026):** Hybrid evaluation (automated + human) is non-negotiable for production agents. Operational constraints — latency, cost per task, token efficiency, tool reliability, policy compliance — are first-class evaluation targets, not afterthoughts. Classical metrics (BLEU/ROUGE) don't capture agent failure modes. — [Evaluating AI Agents in Practice: Benchmarks, Frameworks, and Lessons Learned](https://www.infoq.com/articles/evaluating-ai-agents-lessons-learned)

## Gotchas

- **Using the same model as both agent and judge.** If your application LLM and your judge are the same model or from the same family, the agent may learn to produce outputs that score well without being genuinely correct. Use a different model family for judging when possible.
- **Single-run pass@1 as the only metric.** Agent outputs are stochastic. A single successful run doesn't mean the agent is reliable. Track pass@k across 5-8 trials and flag agents with high variance — they will fail unpredictably in production.
- **Golden datasets that never grow.** A static golden dataset becomes stale as the agent evolves and user behavior shifts. Treat the golden dataset as a living artifact: mine production failures, add edge cases on every regression, and retire cases that no longer represent the target behavior.
- **Accuracy optimization at the expense of cost.** The CLEAR study found that optimizing purely for accuracy produces agents 4.4–10.8x more expensive than cost-aware alternatives with comparable performance. Define a cost-efficiency floor below which the agent is not viable at your target scale.
- **Eval results that nobody acts on.** An eval framework without a CI gate is a report, not a quality system. If the eval can fail but the deployment proceeds anyway, the eval is theater. Make the gate mandatory for all production releases.
