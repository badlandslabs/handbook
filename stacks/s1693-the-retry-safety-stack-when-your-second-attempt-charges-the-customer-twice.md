# S-1693 · The Retry Safety Stack — When Your Second Attempt Charges the Customer Twice

Your agent calls `charge_card`. The API takes 35 seconds. Your timeout is 30 seconds. The agent retries. The API processed both requests. The customer is charged twice. HTTP 200. No exception thrown. The agent reports success. Nobody finds out until the refund request arrives. This is not a model hallucination — it is a retry safety failure: your agent's retry logic has no understanding of whether the underlying operation already happened.

Agents fail mid-run. Networks flap. Tool calls time out. Standard practice says: retry. But retrying a non-idempotent operation is not a recovery — it is a multiplication of side effects. And unlike conventional microservices, agents decide dynamically which tools to call and how many times, which means the retry surface grows unpredictably. A single timeout on a single tool can cascade into 47 retried operations across a single conversation, burning $83 in tokens before the team notices the API returned a 200 error that was anything but.

## Forces

- **Agent retries are more expensive than service retries.** A microservice retry costs one HTTP round-trip. An agent retry resubmits the entire conversation context — potentially tens of thousands of tokens — to the LLM before it even re-executes the tool. One team measured 200x cost difference between an uncontrolled 3-retry policy and a circuit-broken equivalent.
- **Agents complete workflows even when they shouldn't.** A conventional service returns an error. An agent returns a confident HTTP 200 that encodes a degraded outcome. The agent has no signal that `charge_card` returned timeout — it sees a non-200, retries, succeeds silently on the second call, and reports completion. The double-charge lives in the payment processor, not in your logs.
- **Retry budgets compound at the wrong layer.** Setting `max_retries=5` per tool call sounds safe. But if the agent's reasoning loop calls that tool 10 times before giving up, you have 50 retries, not 5. Without a global retry budget across the entire agent run, per-call budgets create a false sense of safety.
- **Retry storms amplify downstream failures.** When an external API degrades, naive retry logic sends every concurrent agent instance back to that API simultaneously. The retries from 50 agents can knock over a service that would have handled 50 healthy requests. In agentic systems this is called a "retry storm" — a cascading failure triggered by the retry logic itself.

## The move

Design retry safety as a first-class property of every tool, not as a generic wrapper around agent calls.

**1. Make every action tool idempotent by design.** Every tool that produces a side effect — payments, emails, DB writes, API mutations — must support idempotent replay. The standard pattern is an idempotency key: generate a UUID before the first attempt, store it with the request, and on retry, submit the same key. The server returns the cached result of the original operation instead of re-executing. MCP provides a hint field for declaring idempotency, but no enforcement mechanism — you must implement the pattern yourself.

**2. Implement a three-layer stopping hierarchy.** Layer 1 (hard stop): `iterations >= max_iterations` — always present, non-negotiable. Layer 2 (cost stop): `tokens_spent >= max_tokens_budget` — prevents runaway token consumption. Layer 3 (time stop): `elapsed >= max_seconds` — enforces latency SLAs for user-facing agents. All three must be independent and enforced at the orchestration layer, not inside the agent's reasoning loop where it can be prompted away.

**3. Route errors to type-specific recovery paths.** Do not catch all errors with the same retry logic. A rate limit (HTTP 429) calls for exponential back-off. A timeout (30s) calls for circuit-breaking, not retry. A 401 calls for re-authentication, not retry. A semantic failure (the tool succeeded but returned wrong data) cannot be caught by HTTP status codes at all — it requires output validation before the agent acts on the result. Classify the error type, then branch to the appropriate recovery path.

**4. Add a circuit breaker at the external dependency level.** When an API's error rate exceeds a threshold (e.g., 50% failures over 10 requests), open the circuit: stop sending traffic to that dependency for a cool-down period (e.g., 30 seconds), and return a graceful error or fallback immediately. This prevents the retry storm problem where hundreds of agents compound a partial outage into a total one. The `agent-fuse` MCP server and `agent-watchdog` GitHub projects implement this pattern as a framework-agnostic guard.

**5. Set a global retry budget per agent run, not per tool call.** Track total retry attempts across all tool calls in a single execution. When the global budget is exhausted, halt the agent and surface a structured error with the state at failure — not a silent degraded outcome. The most dangerous pattern is per-call retry budgets that multiply undetected across the agent's reasoning iterations.

## Gotchas

- **MCP's idempotency hint is not idempotency enforcement.** The MCP protocol surfaces whether an operation is idempotent, but the agent runtime still decides whether to retry. You must implement the actual deduplication logic in your tool wrapper or server-side.
- **Timeout is not circuit breaker.** Setting a 30-second timeout per API call still allows the agent to retry that timed-out call indefinitely. A circuit breaker actively stops sending traffic to a failing dependency — a timeout only stops waiting.
- **Cost alerts fire after the damage.** Monitoring dashboards that flag high spend are useful for auditing, not for prevention. The $83 bill appeared in the morning; the $47,000 11-day conversation loop went undetected until someone checked the billing dashboard. Hard budgets (token caps, iteration caps) prevent; alerts report.
- **Idempotency keys require server support.** The Stripe idempotency-key pattern works only if the external API accepts and honors an idempotency key header. Internal tools and custom APIs can implement this trivially; third-party APIs with no idempotency support require a different mitigation (e.g., polling for existing state before writing, or accepting the risk with explicit human approval for high-stakes operations).
