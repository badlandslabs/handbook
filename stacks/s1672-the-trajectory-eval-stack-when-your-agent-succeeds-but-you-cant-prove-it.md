# S-1672 · The Trajectory Eval Stack · When Your Agent Succeeds But You Can't Prove It

When you need to measure whether an agent is actually working — not just whether it looks like it worked — and all your old metrics (BLEU, ROUGE, final-answer accuracy) tell you nothing useful.

## Forces

- **Outcome and process are different axes.** An agent can reach the right answer via a broken path (wasted tokens, wrong tools, hallucinated args) and score green on a final-answer check. Or it can fail the final answer despite a clean, sensible trajectory. Final-answer pass/fail hides both failure modes.
- **Agents are non-deterministic.** The same task run 100 times produces different trajectories. A single eval run tells you almost nothing; you need distributions, not singletons.
- **Traditional software testing doesn't translate.** Code-based assertions fail when the "correct" behavior is ambiguous, path-dependent, or context-sensitive. You need evaluation methods built for probabilistic systems.
- **Academic benchmarks measure the wrong thing.** MMLU, GSM8K, and HumanEval test base model capability, not the behavior of an agentic system with tools, memory, and multi-turn loops. An agent that scores 90% on HumanEval can still silently call the wrong database 30% of the time.
- **Production failures are your best test data.** Hand-crafted test cases miss the input distribution that actual users generate. Every production failure is a case you could not have invented — but most teams don't capture them.

## The Move

The core discipline: evaluate **trajectories**, not just outputs. Score the whole sequence of steps — tool calls, arguments, retries, intermediate results — against the question "did it get there sensibly and efficiently?" alongside "did it get there at all?"

### The three-layer eval stack

- **Layer 1 — Final-answer score:** Did the agent reach the correct end state? Check the resulting database, file system, API response, or downstream system state — not just the final text. tau-bench pioneered this by verifying both the answer and the resulting DB state. This is the minimum bar, not the whole story.
- **Layer 2 — Trajectory score:** Was the path correct? Did it call the right tools in the right order with the right arguments? Were there unnecessary loops, retried failures, or tool calls that should have been avoided? Score the sequence of steps, tool selections, and reasoning traces.
- **Layer 3 — Per-turn production classifier:** Did anything bad happen mid-trajectory? Use lightweight automated checks on every production turn: policy violations, tool errors, hallucinated tool arguments, drift from task scope. This catches silent failures that a final-answer check never sees.

### Build a golden dataset from production, not from imagination

- Capture real inputs from production traffic (shadow mode if needed — run the agent in parallel without affecting users).
- Every production failure becomes a trace; every trace can become a test case. The highest-value regression test case is one you could not have invented.
- Supplement with synthetic edge cases generated by the LLM itself (with human verification), but treat synthetic data as coverage expansion, not the foundation.
- Size guidance from practitioners: a 50-case golden set targeting your most common task types can block the majority of tool-routing regressions in the first 48 hours of implementation.

### Run evals in CI/CD, not just manually

- Add eval triggers on every commit that changes agent behavior: prompt updates, model changes, tool modifications, configuration changes.
- Set pass-rate thresholds as merge gates. A regression in task success rate below your threshold blocks the merge.
- Tier evals by cost: fast deterministic checks (tool-call schema validation, argument type checks) belong in CI and should complete in minutes. Expensive multi-turn scenarios and LLM-as-judge evaluations on large datasets belong in nightly or pre-release pipelines.
- Without CI/CD gates, prompt changes go out "hoping it helps" — with them, you measure whether it actually helps.

### Choose metrics that measure agents, not just language

The six metrics that carry most of the weight, from multiple independent sources:

| Metric | What it measures |
|--------|-----------------|
| **Task success / completion rate** | Did the agent reach the correct end state? |
| **Tool-call accuracy** | Right tool, right arguments, right order |
| **Step / loop count** | Efficiency; flag repeated idleness or circular reasoning |
| **Token cost per task** | Cost efficiency; catch runaway token usage |
| **Latency per run** | Total wall-clock time from start to completion |
| **Recovery rate** | Did the agent gracefully recover from errors, or did it fail silently? |

### Use LLM-as-judge carefully

- An LLM judging another LLM's output bootstraps initial labels fast, especially for subjective quality dimensions (tone, helpfulness, policy compliance).
- Target 0.80+ Spearman correlation with human judgment before treating a judge as authoritative.
- LLM-as-judge has known failure modes: positional bias (prefers first answer), verbosity bias (rewards longer outputs), and self-preference bias (judges outputs from the same model more favorably). Use with guardrails and human spot-checks.
- For structural correctness (tool calls, argument schemas, loop detection), code-based evaluators are more reliable than LLM judges.

### Instrument full tracing from day one

- Log complete traces: every prompt, every tool call, every response, every token. Without traces, post-mortems are guesswork.
- Tools used in practice: LangSmith (broad agent framework support, Insights Agent for automated failure analysis), Arize Phoenix (open source, self-hostable, 9k+ GitHub stars), TruLens (pluggable feedback functions, OpenTelemetry integration), AgentShield (execution tracing, risk detection on outputs, cost tracking per agent).
- Production monitoring catches the problems that offline evaluation misses: gradual performance drift, new input distributions, third-party API changes. Set alert thresholds for task success rate drops (e.g., below 85%), token cost spikes, and latency regressions.

## Gotchas

- **A held-out pass/fail can be green while the trajectory was a mess.** If you only check the final answer, you miss three wasted tool calls, two hallucinated arguments, and a policy drift that somehow produced the right answer anyway.
- **Success rate is a distribution, not a number.** A single eval run is noise. Run the same scenario 20+ times to get a meaningful success distribution. Single-run pass/fail tells you almost nothing.
- **Non-determinism compounds with trajectory length.** The longer the agent's task (more steps, more turns), the wider the variance in success rate. A 10-step task will have substantially lower reliability than a 2-step task on the same agent.
- **Model updates invalidate evals.** GPT-4 showed measurable behavior changes across versions — tasks at 97% accuracy in March 2023 dropped to 87% by June 2023 on the same benchmark (Chen et al., arXiv). Re-run your golden dataset after every model version change.
- **Human validation is not optional.** LLM-as-judge bootstraps labels fast but has documented biases. At minimum, spot-check a random sample of judgments against human evaluation. Treat the judge as a force multiplier for human review, not a replacement for it.
- **Offline evals miss production-only failures.** Third-party API changes, input distribution drift, network failures during tool calls, and user behavior patterns that don't appear in test data all only surface in production. Your eval pipeline is incomplete without production monitoring.
