# S-1597 · The Harness Stack — When Your Model Is Capable but Your Environment Is Not

Your agent completes a 20-step task in the demo. In production, it loops on a flaky API call for 47 minutes, corrupts shared state on a failed subagent handoff, and escalates cost with no recovery path — then returns a confident, syntactically correct failure. The model is the same in both environments. What changed is everything around it. The harness is what makes an agent recoverable, bounded, and safe to run unsupervised. This is the stack for designing that environment deliberately.

## Forces

- **Agents fail in ways software doesn't.** Conventional services crash and log stack traces. Agents silently loop, spawn redundant subprocesses, corrupt shared state, accumulate context until the model halts, or take irreversible action before a human can intervene. A HTTP 200 response from an agent tool call is not success — it's a syntax-valid output that may contain hallucinated data (Zylos Research, 2026).
- **Self-evaluation is systematically broken.** Agents asked to judge their own work tend to confidently praise it, particularly for subjective tasks. Anthropic's Labs team found this to be the primary ceiling on autonomous long-running task quality — not model capability. You cannot rely on the agent to know it has failed.
- **Failure cascades are the default, not the exception.** In a 10-step pipeline where each step has 85% reliability, end-to-end reliability is only 20%. Specification failures (~42% of multi-agent failures), coordination breakdowns (~37%), and verification gaps (~21%) compound through the chain unless explicitly interrupted.
- **Step count is not progress.** A step cap prevents runaway but also kills agents working on genuinely complex tasks. A research agent burning 8 steps on a subsidiary structure search before hitting the cap returns a partial report that looks complete to the recipient. Progress detection — asking "has anything meaningfully changed?" — is harder than counting steps and is what you actually need.

## The Move

Build the harness as a first-class system alongside the model. These patterns work together as layers:

- **Hard step caps with escalation hooks.** Set `MAX_STEPS = 12` (Rajpoot, 2026) or `recursion_limit=12` in LangGraph as the circuit breaker, then route terminal failures to a human or ticket — not silent drop. The cap is not the solution; the escalation path is.
- **Semantic error handling, not just HTTP codes.** An API returning 200 with empty results, a tool returning a malformed schema, or an LLM output that is syntactically valid but semantically wrong all require custom validation. Validate tool outputs at the harness level, not inside the agent's reasoning loop.
- **Stateful checkpoint/rollback.** Snapshot state at every node boundary before risky operations (LangGraph checkpointer, or the 3-line rollback pattern per AI Dev Day India, 2026). When a bad tool call corrupts state, rewind to the last known-good checkpoint instead of propagating corruption downstream. The NassimRahimi/agent-failure-recovery repo (May 2026) adds a validation step post-rollback: confirm the restored state is actually safe before resuming.
- **Loop detection middleware.** Track repeated file edits and tool calls within a session and inject a prompt nudge when the agent is stuck in an unproductive cycle. LangChain reported moving from rank 30 to rank 5 on Terminal Bench 2.0 using loop detection alone, without changing the model (AgentPatterns.ai, 2026). The loop detection middleware watches edit frequency and intervenes before the agent exhausts its context window retrying the same approach.
- **Circuit breakers per tool.** Trip after N consecutive failures on a specific tool, stop routing requests to it, and fall back to an alternative approach or escalate. This prevents a single degraded tool from cascading into a full pipeline failure.
- **Generator/evaluator separation.** Use a separate evaluator agent to judge output quality instead of letting the generator agent evaluate its own work. Anthropic's Labs team found this the single most effective harness intervention for breaking through performance ceilings on long-running autonomous tasks (Anthropic Engineering Blog, March 2026).
- **Cost and token budgets.** Set a cost cap per run (default $1 per Rajpoot's production playbook). A runaway agent is a runaway bill. Budget enforcement at the harness level is the only reliable guard.
- **Human-in-the-loop interrupts for destructive actions.** Before file writes, database deletes, or external API calls that create obligations, pause execution and wait for confirmation. LangChain's HITL middleware (updated June 2026) intercepts at the policy level and uses the persistence layer to save state so execution can resume after human review.

## Gotchas

- **Step caps kill legitimate complexity.** A step limit of 20 works fine for most tasks but fails silently on complex ones. Step count is a proxy for progress, not progress itself. The fix is progress detection — checking whether the agent's state has meaningfully changed — not a higher cap.
- **Rollback without validation restores confidence, not correctness.** The NassimRahimi pattern adds a post-rollback validation step for good reason: rolling back to a checkpoint doesn't guarantee the restored state is safe to resume from. Without validation, you can re-enter the same failure path.
- **Circuit breakers applied globally instead of per-tool.** If you apply a single circuit breaker to the entire agent, one degraded tool will trip the breaker for all tools. The breaker must be per-tool or per-tool-class so a flaky search API doesn't disable your file writer.
- **Human-in-the-loop without persistence is a deadlock.** If you interrupt for review but don't checkpoint state first, the interrupted agent cannot resume cleanly — you've traded runaway execution for permanently lost work. The interrupt and the checkpoint are coupled.
- **Generator/evaluator separation trades latency for accuracy.** Two model calls instead of one doubles cost and latency per step. Teams often apply this selectively — use the evaluator only on task completion, not every intermediate step — to manage the tradeoff.
