# S-2076 · The Agentic Blast Radius Stack — When Prompt Injection Becomes Remote Code Execution

[You gave your agent tools. It can now browse the web, send emails, query your database, and run code. The demo works. Then a user feeds it a document with hidden instructions, and your agent emails your entire customer list to an external address. The security model that worked for chatbots — sanitize output, filter jailbreaks — does not touch this. Once an agent has tool access, prompt injection is no longer a content problem. It is an execution primitive. The blast radius changed.]

## Forces

- **Tool access inverts the security model.** In chatbot era, the worst case was a wrong answer or leaked context. In agentic era, the worst case is the agent doing wrong things with real credentials, at machine speed, on your infrastructure.
- **Guardrail logic doesn't scale to action.** Safety policies trained into frontier models stop instructions a human would refuse — but they don't stop instructions that an agent's tooling makes mechanically reasonable. The model isn't misbehaving; it is correctly interpreting a poisoned input through a legitimate tool.
- **The Hugging Face breach proved the attack surface exists at scale.** July 2026: an autonomous AI agent drove an intrusion end-to-end, executing 17,000+ logged actions over a weekend, harvesting credentials and moving laterally across internal clusters. The attacker was not a human. The blast radius was not theoretical.
- **Defense-in-depth is the only viable posture.** No single mitigation (prompt filtering, least-privilege tools, sandboxing) stops all threat categories. The OWASP Agentic Top 10 (ASI01–ASI10) documents ten distinct failure modes, each requiring a separate countermeasure.

## The Move

The move is not hardening a prompt — it is **treating the agent as a distributed system with its own threat model, blast radius controls, and identity layer.** Specifically:

- **Establish an identity and authorization layer per agent.** Agents should have verifiable identities (Microsoft Entra Agent ID, SPIFFE/SPIRE) with scoped credentials and explicit tool-binding — not shared infra credentials. Each agent gets exactly the permissions its current task requires, nothing more.
- **Enforce least-privilege tool access with per-tool permission scoping.** Grant the minimum tool set required for the specific task. Tools should be scoped to specific resources (read-only vs. write, specific tables or files), not broad capability categories. Use separate tool sets for internal vs. user-facing agents. Require explicit authorization for sensitive operations.
- **Implement sandboxing tiers mapped to threat model.** Five isolation tiers exist along a spectrum: OS process (Seatbelt/bubblewrap, ~0ms overhead) → user-space kernel (gVisor) → dev containers (Docker + seccomp) → microVMs (Firecracker, <1s startup) → full VMs (KVM). Claude Code 1.3 ships process-level sandboxing by default. Vercel Sandbox (GA January 2026) and E2B use Firecracker. Match the tier to the filesystem, network, and process threats you are actually protecting against.
- **Validate untrusted content before tool execution, not just at the prompt layer.** Content from web pages, emails, documents, and external APIs must be treated as potentially hostile. Validate parameters before they reach tool boundaries — a model output that passes a content filter can still pass a crafted file path to a file-write tool.
- **Scope agent credentials to the minimum necessary resources.** Agent credentials should not survive beyond the task scope. Revocation must be fast (minutes, not hours). Log all credential use. The OWASP ASI01–ASI04 framework (Goal Hijack, Tool Misuse, Identity Confusion, Overreliance) maps the failure modes that credential sprawl enables.
- **Monitor for the new indicator sets.** Traditional SIEM rules don't catch agentic behavior. Watch for: unusual API call sequences from agent processes, credential use outside expected tool scopes, repeated tool calls on the same resource, or agent-initiated network connections to non-allowlisted services.

## Gotchas

- **Treating LLM security as sufficient.** Prompt filtering and jailbreak resistance — the core of chatbot-era security — address content output, not tool execution. The threat surface for agents includes the entire tool execution path, credential stores, network layer, and file system. Security must span the full stack.
- **Assuming guardrails generalize across tool contexts.** Frontier model safety policies are trained on content that looks like a human refusing. They are not trained on the instruction "forward this attachment to ext@example.com" when the agent has an email tool. The same instruction that fails a chat filter may succeed through a tool call with no filter.
- **Overprovisioning tools "for flexibility."** Every tool in an agent's capability set is an attack surface vector. The OWASP ASI02 (Tool Misuse) pattern — legitimate tools used in unintended ways — scales with the number of tools. Minimizing the tool surface is a security decision, not just a performance one.
- **Not planning credential revocation for agents.** Agent credentials, if compromised, operate at machine speed — orders of magnitude faster than human attackers. Manual revocation workflows designed for human access patterns leave agents exposed for hours. Revocation must be automated and scoped to the specific agent and tool context.
