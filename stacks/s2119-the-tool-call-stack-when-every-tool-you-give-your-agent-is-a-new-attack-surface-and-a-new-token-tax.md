# S-2119 · The Tool Call Stack — When Every Tool You Give Your Agent Is a New Attack Surface and a New Token Tax

The model can reason. The model can plan. Then you give it tools — and suddenly you have a new attack surface, a new token overhead problem, and a new failure mode you didn't have before. The teams that deploy agents successfully have learned to treat tool provisioning as a deliberate discipline, not a feature checklist.

## Forces

- **Capability and attack surface grow together.** Every tool is a privilege escalation path. Code execution, filesystem access, AWS APIs, browser control — these are not bounded by the model's safety training. Strands Agents explicitly flags its tool collection as experimental for production use precisely because of this.
- **Tool registration is a token tax.** Loading all tool definitions upfront — the standard MCP pattern — means an agent with hundreds of tools can spend 150,000+ tokens on definitions before reading a single user request. Anthropic's research found filesystem-based on-demand loading reduces this to ~2,000 tokens — a 98.7% reduction.
- **Browser automation compounds failure modes.** browser-use has 91k+ GitHub stars and an 89.1% success rate on the WebVoyager benchmark, but production deployments require clean separation between reasoning (LLM), execution (browser), and infrastructure layers. Without it, agents compound errors across steps.
- **The M×N integration problem is real.** Direct API integrations require bespoke authentication, tool descriptions, and retry logic per agent-to-service pair. At scale, this is unmaintainable.
- **Tool discovery differs from tool definition.** Giving an agent 500 tools is different from giving it a way to find the right tool. Filesystem-based tool trees let agents navigate by domain before drilling down — a pattern that matches how they already explore codebases.

## The Move

**Provision tools minimally, connect them via MCP, and load them on-demand.**

- **Start with the minimal viable toolset.** The tool categories that appear across virtually every production deployment: web search, code execution (sandboxed), file read/write, and API calls. Every additional tool is a deliberate, justified decision — not a default.
- **Use MCP as the integration standard.** MCP has won. The SDK crossed 300 million monthly downloads in early 2026, adopted natively by Anthropic (Claude Desktop, Claude Code), OpenAI (Responses API, early 2025), Microsoft (Azure Foundry, VS Code Copilot), and Google. Write once, use across every major client. Anthropic donated the protocol to the Linux Foundation's Agentic AI Foundation in December 2025.
- **Load tool definitions on demand, not upfront.** Instead of registering all tools at session start, store each tool definition as a file in a directory tree organized by service. The agent reads the directory structure, finds what it needs, and loads only that tool. Filesystem navigation is native to LLMs — no special orchestration required. Target: load 2,000 tokens of definitions instead of 150,000.
- **Separate reasoning, execution, and infrastructure layers.** Browserless's production architecture separates the LLM (reasoning), Playwright (execution), and infrastructure (session management, scaling) into distinct tiers. Each changes at a different rate and has different failure characteristics. Mixing them produces systems that are hard to debug and impossible to scale.
- **Wrap browser automation behind a task layer.** The teams getting durable value from browser agents treat them as a navigation layer feeding deterministic downstream processes — not as a complete solution. Browser agents fill forms, extract data, navigate flows. What happens next is a structured workflow.
- **Tool definitions need descriptions the model can reason about.** Vague tool names ("getData") force the model to guess. Specific descriptions with parameter semantics, error conditions, and expected output shapes reduce hallucinated tool calls. Anthropic's code execution post notes that 98.7% token reduction is only useful if the tools still work — descriptions must survive compression.

Anthropic ships MCP natively in Claude Desktop and Claude Code. — [anthropic.com/engineering/code-execution-with-mcp](https://www.anthropic.com/engineering/code-execution-with-mcp)

Browserless.io documents the three-layer architecture (reasoning/execution/infrastructure) required for production deployments, noting that teams that "deploy the agent and expect the rest of the system to follow" consistently fail. — [decisioncrafters.com](https://www.decisioncrafters.com/browser-use-autonomous-web-automation-91k-stars/), [browserless.io](https://www.browserless.io/blog/building-autonomous-browser-agents-with-playwright-claude-opus-4-5)

## Gotchas

- **Sandboxing is non-negotiable for code execution.** Strands Agents explicitly warns that code execution, filesystem access, and AWS API calls carry real security implications. Docker container escapes (runc CVE-2019-5736, gVisor CVE-2021-41190) have been exploited in the wild. See S-2118 for the isolation tier stack.
- **Browser agents fail silently in ways code agents don't.** A failed code execution returns an error. A browser agent on step 7 of a 10-step flow may silently land on a 404, a cookie-expired login page, or a captcha. Browser agents need explicit step-count limits, screenshot verification at key milestones, and dead-end detection.
- **More tools ≠ better agent.** Every additional tool increases token overhead (even with on-demand loading), adds failure modes, and makes the agent's decision surface harder to evaluate. The teams winning are the ones who started with three tools and added one when they had a specific, justified need.
- **Tool descriptions drift from tool behavior.** When a backend API changes but the MCP tool definition doesn't, the agent confidently calls a tool that no longer works. Versioning tool definitions alongside the services they wrap is an operational discipline most teams skip until it bites them.
- **Context window inflation hides the real cost.** 150,000 tokens on tool definitions looks like "the model is just loading tools." But that's $X per session before the model has done any useful work. On high-volume deployments, this is the largest line item in the cost breakdown that nobody tracks.
