# S-2375 · The Agent Tool Repertoire Stack — When Your Agent Doesn't Know What to Reach For

You built an agent with 23 tools. It uses 4 of them reliably, misfires 7 others into silence, and the remaining 12 have quietly become debugging liabilities that nobody touches. Meanwhile, the agent that actually ships has 5 tools and handles 80% of the same cases. The tool repertoire problem isn't about capability — it's about knowing which tools earn their place and which ones are causing failures you haven't found yet.

## Forces

- **More tools amplify failure surface, not capability.** Each tool introduces its own error mode: parameter mismatches, API drift, silent timeouts, auth expiry. The cumulative failure rate grows with every tool you add, and most failures are silent — the agent proceeds as if the tool succeeded.
- **Tool design assumptions go both ways.** Developers design tool interfaces for human ergonomics; agents need descriptions optimized for parameter correctness and failure self-correction. These are different optimization targets, and the mismatch causes a disproportionate share of real-world failures.
- **Browser tools are powerful but expensive.** Real-browser automation gives agents genuine web interaction, but token costs, DOM complexity, and element instability make them the highest-maintenance tool category. The alternative (HTTP API tools) is cheaper but limits the agent to pre-built integrations.
- **Code execution is the sharpest knife in the drawer.** Agents that can run shell commands or execute Python have enormous reach — and enormous risk. Sandbox or no sandbox? Root access? Network access? The security posture determines whether the tool is usable or a liability.
- **Agents keep going after tools fail.** The dominant production failure mode isn't hallucination (~12%) — it's tool errors (~28%), and most of those errors don't crash the agent. The agent wraps the failure in a plausible-sounding explanation and continues. Silent failures compound.
- **The industry is moving away from heavy frameworks toward tool-centric design.** Anthropic's canonical guidance recommends "simple, composable patterns" over agentic frameworks. The practical implication: focus on what your tools do, not how the agent orchestrates them.

## The move

**Start with the minimum viable tool set. Add tools only when you have a specific capability gap you can name.**

The agent tool repertoire is not a feature list — it is a reliability surface. Every tool you add is a new failure mode you own.

- **Tier 1 — non-negotiable baseline.** A filesystem tool (read, write, list), a shell/terminal tool (execute commands with stdout capture), and a code interpreter (Python REPL or similar). These three cover the vast majority of knowledge-work tasks. They are well-understood, predictable, and their failure modes are obvious.
- **Tier 2 — production essentials.** A web search tool and a web fetch tool. Separate them — search for discovery, fetch for retrieval. A retrieval tool over your internal documentation or codebase. These extend the agent's reach without introducing browser complexity.
- **Tier 3 — evaluate before shipping.** Browser automation (Playwright-based, with element refs for stability), database query tools, API integrations (GitHub, Slack, etc.). Each of these has significant operational overhead: auth lifecycle, rate limits, schema drift, element instability in the case of browsers. Measure their actual contribution to task completion before committing.
- **Design tool schemas for agent self-correction.** Include parameter descriptions that explain what valid values look like, not just their types. Include what errors the agent should expect and how to recover. A tool that returns `{"error": "invalid_parameter"}` without context teaches the agent nothing. A tool that returns `{"error": "invalid_parameter", "expected": "ISO 8601 date string YYYY-MM-DD", "received": "06/25/2025"}` lets the agent self-correct without a human in the loop.
- **Wrap external tool calls with structured validation.** Before returning tool output to the agent, validate the response shape. Catch silent failures — HTTP 200 with a null body, a list that returned 0 results when there should have been results, an API response that succeeded but the action was never committed. These are the failures that don't look like failures.
- **Separate retryable from non-retryable errors.** Infrastructure failures (rate limits, timeouts, network unavailability) warrant retry with backoff. Parameter errors, auth failures, and schema mismatches will not self-resolve. Route the error type to the agent along with a recovery signal: either "retry this" or "you need to fix the call."
- **Use MCP (Model Context Protocol) for tool discovery and composition.** MCP standardizes how agents find, load, and describe tools. A well-designed MCP server gives you vendor-neutral tool definitions, automatic schema validation, and a growing ecosystem of pre-built tool servers (filesystem, GitHub, SQLite,HN, etc.). For production, the MCP approach reduces per-agent-per-tool integration overhead from N×M to N+M.
- **Instrument every tool call.** Log: which tool was called, with what parameters, what the response was, how long it took, and whether the agent's next action was consistent with the result. A tool that is called but never influences the agent's next step is either redundant or the agent is ignoring its failures.

## Evidence

- **Anthropic engineering guidance:** The canonical recommendation is to "find the simplest solution possible, and only increase complexity when needed." The hierarchy is: single LLM calls → workflows (prompt chaining, parallelization) → routing → agents as a last resort. Frameworks that push agents by default are optimizing for impressiveness, not reliability. — [Building Effective AI Agents](https://www.anthropic.com/engineering/building-effective-agents)
- **Production failure statistics:** Tool errors account for ~28% of agent failures in production, compared to ~12% for hallucination. The dominant errors are parameter mismatches (20–40% of tool call failures), API schema drift, and silent failures where HTTP 200 is returned but the action was never committed. Pilot stall rate before reaching production is 60–72%. — [Presenc AI: AI Agent Failure-Mode Statistics 2026](https://presenc.ai/research/ai-agent-failure-mode-statistics-2026)
- **Open-source agent with local tool repertoire:** gptme (4,379 stars, active since 2023) ships with filesystem, shell/terminal, web browsing, Python REPL, and vision as its core tools. Configurable via `gptme.toml`. Provider-agnostic (Anthropic, OpenAI, Google, xAI, DeepSeek, local llama.cpp). The README explicitly frames these as "local tools" — the value proposition is that the tools run in the user's environment, not in a sandboxed cloud service. — [gptme GitHub](https://github.com/gptme/gptme)
- **Specialized browser tool for agents:** The agent-browser project (Vercel Labs, ~40k GitHub stars) is a Rust-based CLI with 50+ commands specifically designed for AI agents. Key design decisions: compact text output (fewer tokens than JSON), ref-based element selection (deterministic, not selector-based), and built-in video recording for debugging. 100% native Rust. — [agent-browser](https://agent-browser.dev/) and [GitHub](https://github.com/vercel-labs/agent-browser)
- **Production tool call failure rates:** Real-world production agents show 12–18% tool call failure rates compared to near-zero infrastructure failures assumed in benchmark scaffolds. The arXiv paper (2601.16280) establishes a 12-category error taxonomy across four phases: initialization, parameter handling, execution, and result processing. A subsequent paper (2607.04686, ToolFailBench at ICML 2026) introduces a diagnostic benchmark specifically for tool-use failures across 1,000 tasks in finance, medicine, law, cybersecurity, and real estate. — [ToolFailBench arXiv](https://arxiv.org/abs/2607.04686), [AgentMarketCap](https://agentmarketcap.ai/blog/2026/04/10/agent-tool-call-retry-failure-mode-handling-production-2026)
- **HN community consensus on frameworks:** A 543-point HN thread on Anthropic's agent guidance surfaced strong consensus against heavyweight orchestration frameworks. The most-upvoted comments favored direct API calls and simple composable patterns over LangChain-style abstractions. The critique: frameworks simplify low-level tool calling but hide the failure modes that matter in production. — [HN Discussion on Building Effective AI Agents](https://news.ycombinator.com/item?id=44301809)

## Gotchas

- **Adding a tool is not the same as solving the problem.** If a tool is returning results the agent can't use, the fix is usually in the tool's output schema — not in adding another tool.
- **Browser tools fail silently in the most expensive way.** DOM element instability, dynamic content, and JavaScript rendering mean the agent may be acting on a stale page snapshot. Always validate that the page state matches the expected action.
- **HTTP 200 is not success.** The most dangerous production failures return a valid HTTP 200 with a body that indicates failure or partial execution. Validate the response semantics, not just the status code.
- **Code execution without sandboxing is a production security incident waiting to happen.** If your shell tool runs as the agent's user, a malformed command can delete files, exfiltrate credentials, or pivot to other systems. Define explicit allowlists for permitted commands or use containerized execution.
- **Parameter error rates are higher than you expect.** The Berkeley Function-Calling Leaderboard (BFCL) shows significant variance across models on multi-step tool composition. Even frontier models struggle with parameter correctness in complex, interdependent tool chains. Design tools to be forgiving at the parameter boundary — validate and coerce inputs before passing them to the underlying API.
