# S-2235 · The Agent Evaluation Stack — When Your Agent Passes All Tests and Still Fails in Production

Your agent scores 97% on your internal benchmark. You ship it. Three users find a failure mode your tests never caught, and by the time you've traced the bug, the agent has run 4,000 times. Evaluating agents is not the same as evaluating language models. The test harness must capture trajectories, tool calls, error recovery, and cost — not just final output quality. Most teams build the wrong harness, then trust the wrong numbers.

## Forces

- **Agents are systems, not functions.** A single accuracy score on the final output says nothing about whether the agent took the right path, recovered from a bad tool call, or spent $4 on a task that should have cost $0.40.
- **Non-determinism breaks deterministic testing.** Agents operating with the same input can follow different execution paths due to LLM sampling, environment state, and tool latency. A test that passes once may fail the next three runs.
- **Benchmarks lie.** Public leaderboard scores — SWE-bench, WebArena, GAIA — measure curated tasks with clean ground truth. They don't capture your specific domain, your tool chain, or your users' actual behavior. UC Berkeley research in 2026 found single-character changes gamed 890 benchmark tasks to near-perfect scores without genuine task completion.
- **Trajectory failures cascade.** A single wrong step in a 40-step workflow can produce a correct-looking final output that is subtly or catastrophically wrong. Detecting this requires step-level instrumentation, not just end-to-end checks.
- **Safety is orthogonal to success.** A correct agent that violates safety constraints 5% of the time is more dangerous than an agent that safely completes 70% of tasks. Most eval frameworks don't evaluate these dimensions independently.

## The Move

Build a multi-level evaluation pipeline that measures trajectory, task completion, and operational properties — not just final output quality. Wire it into CI/CD with automated LLM-as-judge scoring and human review gates for high-stakes deployments.

**Trace before you score.** Instrument every agent execution as a trace — a structured record of every LLM call, tool invocation, tool response, and state transition. Tools like Langfuse, Phoenix (by Arize), and LangSmith capture these automatically. Without traces, you cannot debug failures, identify which step broke, or reason about why the agent made a particular choice. This is the foundation everything else builds on.

**Separate outcome metrics from trajectory metrics.** Outcome metrics answer: did the agent complete the task? Trajectory metrics answer: did it take a reasonable path? These are independent. An agent can succeed at the task while burning through 12 unnecessary tool calls, looping on a failed API, or making unsafe intermediate decisions. Rate task success and step efficiency separately, then investigate whenever both are not high together.

**Define domain-specific success criteria first.** Before choosing benchmarks or writing rubrics, answer: what does success actually look like for this agent in this domain? For a code-editing agent, success is a passing test suite. For a customer support agent, it is resolution rate plus conversation length. For a data extraction agent, it is schema conformance plus groundedness. Generic benchmarks measure the wrong thing. Build a golden dataset of 20–50 real production inputs with known-good outputs, and evaluate against that before trusting public benchmarks.

**Use LLM-as-judge with calibration, not raw scores.** Asking an LLM "is this response good?" produces a 0–10 score that is uncalibrated and inconsistent. A well-calibrated LLM judge requires: a written rubric with specific pass/fail criteria for each dimension, scoring at the trajectory level (evaluate each step, not just the final answer), and validation against human-labeled examples targeting ≥0.80 Spearman correlation. The gap between a naive judge and a calibrated one is wide enough to produce opposite conclusions about agent quality.

**Evaluate at three levels.** End-to-end: did the final output meet the user's goal? This is what users care about. Trajectory-level: was the path efficient and correct? Did the agent recover from failures, avoid loops, and call the right tools? Component-level: which specific tool or reasoning step caused the failure? Confident AI's DeepEval (open-source, 26K+ GitHub stars) provides built-in metrics for task completion, step efficiency, argument correctness, hallucination, and tool selection accuracy — composable at each level.

**Measure operational properties alongside quality.** Cost per task (tokens + API calls), latency per step and end-to-end, tool call success rate, and retry frequency. An agent that achieves 95% task success at 3× the cost or latency of a baseline may not be an improvement. Langfuse's score analytics let you track these over time and set alerting thresholds.

**Integrate evals into CI/CD with three trigger types.** Commit-triggered: run the full eval suite on every code change to catch regressions before merge. Scheduled: re-run periodically against fresh production-traffic samples to catch drift as the environment changes. Event-driven: trigger on production anomalies (spike in error rate, cost anomaly, user feedback) to capture the failing trace and add it to the golden dataset. This closes the loop between production failures and eval improvements.

**Validate against public benchmarks, then move on.** SWE-bench Verified, WebArena-Verified, and GAIA are useful for comparing agent scaffolding architectures and identifying ceiling effects. But they do not predict production performance for your specific agent. Use them to decide between LangGraph vs. Pydantic AI vs. CrewAI scaffolding, then immediately shift to domain-specific evaluation.

## Gotchas

- **Benchmark scores ≠ production performance.** SWE-bench Verified measures file-editing skill from GitHub issues, not multi-turn conversational task completion. Pick benchmarks that match your agent's actual task type, then immediately supplement with domain-specific golden datasets.
- **Passing the eval once means nothing.** Agents are non-deterministic. A single run can pass while the same configuration fails 7 out of 8 runs. Use pass@k metrics — the probability that at least one of k attempts succeeds — to capture reliability, not just single-run success rate.
- **LLM judges amplify prompt bias.** A judge model will favor outputs in the style it was trained on, penalize minority viewpoints, and show position bias (preferring earlier options in lists). Calibrate by running the judge against known-human-labeled examples before trusting its scores.
- **Tracing without scoring is a hobby, not evaluation.** Capturing traces in Langfuse or Phoenix is valuable for debugging, but traces without structured scoring and regression thresholds tell you nothing about whether the agent is getting better or worse over time. Add scores to traces, not just logs.
- **Domain-specific eval requires human validation.** For high-stakes domains — legal, medical, financial — automated judges cannot capture the nuanced correctness that expert human reviewers can. Plan for a human-in-the-loop gate on any eval that affects regulated or safety-critical decisions.
