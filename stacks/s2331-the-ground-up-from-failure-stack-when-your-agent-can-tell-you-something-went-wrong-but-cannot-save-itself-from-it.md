# S-2331 · The Ground-Up-From-Failure Stack — When Your Agent Knows It Failed but Can't Save Itself

When your agent produces confident nonsense for 20 minutes, completes the task "successfully," and you only find out three weeks later — or never.

## Forces

- Agents fail silently in the most dangerous way: HTTP 200, no exception thrown, a confident completion message. Standard circuit breakers catch HTTP errors and network timeouts, not semantic failures where the model reasons confidently in the wrong direction.
- The failure taxonomy for agentic systems is fundamentally different from traditional software — syntax errors become hallucinated JSON, runtime exceptions become tool calls that succeed technically but fail semantically, and stack traces are replaced with reasoning chains producing confident nonsense.
- Error propagation is the central bottleneck: a single failure cascades through planning, memory, and action modules in a way that traditional try-catch cannot contain. Eighty-eight percent of AI agent pilots never reach production — and of those that do, many fail silently completing tasks, returning responses, and delivering wrong results without triggering a single error code.
- LLMs are poor at self-correction: research shows agents catch 26% more errors when an external source surfaces them than when the agent must identify the error itself — a phenomenon called the self-correction illusion. LLMs flag identical claims as errors far more readily when those claims appear under an external source label.
- Shipping checkpoint systems have blind spots: Claude Code's `/rewind` doesn't capture bash commands, subagent edits, or symlinked paths — so even tooling marketed as "recoverable" has gaps teams don't discover until production.

## The move

Build recovery from the ground up in five concentric layers:

**Layer 1 — Hard step caps.** The single most critical guardrail. Stop execution after a fixed step count before the cost spiral starts. `recursion_limit=12` in LangGraph, or a loop counter wrapping the main agent loop. A step cap on a $2 task costs you a retry; no cap on a 47-minute runaway costs you $1,847.

**Layer 2 — Tool-level retries with exponential backoff + jitter.** Handle transient failures (network hiccups, rate limits, brief API unavailability) at the tool level, not the agent level. A 429 from an API should trigger backoff and retry, not a re-plan. Jitter prevents thundering-herd retry storms when multiple agents hit the same rate limit simultaneously.

**Layer 3 — Semantic error formatting.** When a tool call fails, the error message returned to the model matters as much as the fact of failure. Raw exception dumps ("ConnectionRefusedError: [Errno 111]") give the model nothing actionable. Rewrite errors into the model's context: what went wrong, what the model was trying to do, and what a successful retry would look like. This is the difference between self-correction working and the agent looping on the same broken assumption.

**Layer 4 — Checkpoint and resume, not crash-and-retry.** For tasks exceeding ~1 minute of work, save state after each significant step. LangGraph's Checkpointer, agentckpt (git-style content-addressable snapshots with branching and rollback), or agent-state-checkpoint (atomic JSON writes with schema versioning) — pick one. The key architectural choice: Postgres for transactional consistency, Redis for low-latency resume, object storage for cheap long-term snapshots. Checkpoint on durable storage *before* any irreversible action (write, delete, API call that cannot be undone).

**Layer 5 — Human-in-the-loop escalation, not approval gates everywhere.** Three patterns, in order of throughput: sampling-based HITL (agent runs autonomously, random/risk-stratified sample reviewed after the fact — audit, not governance); escalation-triggered HITL (agent runs until a risk signal fires — confidence below threshold, cost exceeds budget, action targets a protected resource — then pauses for human review); and approval-gate HITL (agent proposes, human approves before action — slowest, most common early mistake). Start with risk-stratified escalation and add approval gates only where the cost of a wrong action exceeds the cost of the wait.

## Gotchas

- **Approval gates everywhere is the most common early mistake.** Teams that put a human checkpoint before every action end up with an agent that is slower than manual work and still requires human attention. Use risk-stratified escalation instead — let the agent run autonomously and only pause when a signal fires.
- **The self-correction illusion will fool your evals.** Your agent can appear to self-correct in demos because you're watching closely and intervening. In production, it silently continues on wrong reasoning. You need external validation (a Verifier Agent, output schema enforcement, or ground-truth spot checks) — not self-reported confidence.
- **Checkpointing without idempotency is half-measured.** If your agent retries a step after a crash but the first run already partially mutated external state (sent a partial email, wrote partial data, called an API with non-idempotent semantics), resuming from checkpoint re-executes the mutation. Every tool call in a recoverable workflow needs idempotency keys or a check-for-existing-result guard.
- **Circuit breakers that only watch HTTP codes miss the worst failures.** An agent getting HTTP 200 from a RAG system that returned hallucinated text is not a circuit-breaker event. Your breaker needs semantic awareness — either a Verifier Agent checking output quality, or a schema validator enforcing output structure before the next step runs.
