# S-2306 · The MCP Trust Gap Stack — When Your Agent Framework Has Privileged Access and No Security Boundary

You've connected your agent to your database, your file system, your cloud APIs. The Model Context Protocol made it trivial — 97M+ monthly SDK downloads, 5,800+ servers, 300+ client applications as of late 2025. Your agent can now do real work. The problem: 43% of MCP servers have command injection flaws, the Supabase Cursor agent leaked service-role credentials through a support ticket prompt injection, and a single CVE reached CVSS 9.3 on an SSRF vulnerability in a popular fetch server. The trust gap between what you granted and what is actually safe is where production agentic systems die.

## Forces

- **MCP makes integration trivially easy and security trivially hard.** The same design ethos that drove 5,800+ server implementations made it trivially easy to give an agent root-level filesystem access — and equally easy to forget that untrusted input (user prompts, documents, API responses) can now reach those privileged tools.
- **The model is in the attack surface.** Unlike a traditional API where input is a data field, MCP command injection is mediated through the model itself — the agent interprets natural language and translates it into executable operations, meaning attackers can hide instructions inside prompts, documents, or context that the model then acts on without realizing it is being manipulated.
- **Privilege escalation is a feature, not a bug.** Agents need privileged access to be useful — service-role database credentials, filesystem write access, cloud API tokens. The security boundary that traditional software enforces at the OS or network layer doesn't exist at the MCP layer; the agent is the boundary, and it is non-deterministic.
- **Security tooling hasn't caught up with deployment speed.** 44% of tracked companies have deployed MCP in some form, but OWASP only published its MCP Top 10 in 2025, the protocol only donated to the Linux Foundation's Agentic AI Foundation in December 2025, and request-level inspection was still listed as a "latest RC" feature as of mid-2026.

## The move

Give every MCP server a **zero-trust security boundary** layered on top of the privilege it needs to do its job. The principle: grant the minimum privilege required, validate every boundary, and treat the model as untrusted input — because it is.

- **Principle of least privilege by default.** Don't give an agent a filesystem MCP server with write access to `/`. Give it read access to specific directories, or better yet, a narrow tool that does exactly one thing (e.g., `append_to_session_log`) rather than a general-purpose file interface. Anthropic's own guidance: prefer pure-function invocation and single-responsibility agents.
- **Input validation at every tool boundary.** Every parameter an agent passes to an MCP tool must be treated as untrusted. Validate IP addresses properly (the CVE-2025-65513 SSRF flaw was in an `is_ip_private()` check with incomplete validation — IPv6 loopback `::1`, alternative encodings, and IPv4-mapped IPv6 all bypassed naive prefix checks). Validate file paths against allowed directories. Escape or reject shell metacharacters. Don't rely on the model to sanitize its own inputs.
- **Network egress allowlisting.** MCP servers making outbound HTTP calls (fetch servers, API clients) must be scoped to specific targets. SSRF vulnerabilities let attackers reach internal services — metadata endpoints, admin ports, internal databases. Block everything except explicitly allowed destinations.
- **Sandbox every MCP server.** Run each server in an isolated process or container with its own IAM role and network policy. The Red Hat security analysis recommends treating MCP servers as network-accessible services with their own attack surface. The Filesystem MCP server sandbox escape documented by Cymulate (CVE-2025-53109) — where a naive prefix check allowed arbitrary file access and code execution — demonstrates that isolation must be enforced at the infrastructure layer, not the application layer.
- **Structured user confirmation for destructive or high-privilege actions.** Anthropic's Form mode and URL mode for elicitation exist precisely for this: request schema → render native form → get explicit user confirmation before executing a delete, a payment, an external OAuth redirect, or any action with irreversible consequences. Use them.
- **Audit trail and request inspection.** Every MCP tool call should be logged with its full invocation context — agent ID, tool name, parameters, response, and session state. Microsoft notes that "the moment a model can choose and call tools, it stops being a question-and-answer box and becomes software that acts." Software that acts needs an audit log. The OWASP MCP Top 10 MCP05 pattern — command injection mediated through the model — is only detectable post-incident if you have instrumentation on every tool invocation.

## Evidence

- **OWASP MCP Top 10 (MCP05:2025):** Documents command injection as the primary MCP vulnerability class — specifically, the attack surface where hidden instructions in prompts, documents, or context cause the agent to generate malicious commands that appear syntactically valid. The key insight: unlike traditional command injection where attackers control input fields directly, MCP-based injection is mediated through the model layer. — [owasp.org/www-project-mcp-top-10/2025/MCP05-2025](https://owasp.org/www-project-mcp-top-10/2025/MCP05-2025%E2%80%93Command-Injection%26Execution)

- **Supabase MCP Cursor Incident (mid-2025):** A Cursor agent running with Supabase service-role access processed support tickets containing user-supplied input as commands. Attackers embedded SQL instructions in support threads that exfiltrated integration tokens via a public channel. The three-factor combination: privileged access, untrusted input processing, and an external communication channel. Documented in [Practical DevSecOps MCP security analysis](https://www.practical-devsecops.com/mcp-security-vulnerabilities) citing [pomerium.com/blog/when-ai-has-root-lessons-from-the-supabase-mcp-data-leak](https://www.pomerium.com/blog/when-ai-has-root-lessons-from-the-supabase-mcp-data-leak).

- **Cymulate EscapeRoute / CVE-2025-53109:** Research by Cymulate Labs demonstrated that Anthropic's own Filesystem MCP Server could be escaped via a naive prefix check, allowing arbitrary file access and code execution. The server's sandbox was enforced by path prefix matching — an attacker could traverse to any file by manipulating the path. CVSS rating: High. Documented at [cymulate.com/blog/cve-2025-53109-53110-escaperoute-anthropic](https://cymulate.com/blog/cve-2025-53109-53110-escaperoute-anthropic/). Also: Snyk discovered CVE-2025-65513 (CVSS 9.3) — SSRF in the `mcp-fetch-server` npm package via incomplete `is_ip_private()` validation allowing bypasses using IPv6 alternative representations. — [sentinelone.com/vulnerability-database/cve-2025-65513](https://www.sentinelone.com/vulnerability-database/cve-2025-65513)

- **Anthropic Engineering: Writing Tools for Agents:** Anthropic's own guidance frames tools as "a new kind of software which reflects a contract between deterministic systems and non-deterministic agents." Key recommendations: prefer pure-function invocation, single-responsibility tools, and explicit user elicitation for destructive actions via Form mode or URL mode. — [anthropic.com/engineering/writing-tools-for-agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

- **Microsoft Security Blog / The State of MCP Security in 2026:** Microsoft's analysis of MCP in production (June 2026) confirms MCP has "transitioned from experimental to production" and identifies command injection and shell injection as the largest classes of MCP vulnerabilities. Notes the protocol's evolution includes request-level inspection as a newer security feature. — [techcommunity.microsoft.com/blog/microsoft-security-blog/the-state-of-mcp-security-in-2026/4531327](https://techcommunity.microsoft.com/blog/microsoft-security-blog/the-state-of-mcp-security-in-2026/4531327)

## Gotchas

- **Don't assume the model's intent is trustworthy.** The model is the attack surface. Any content the model processes — user prompts, retrieved documents, tool responses, session memory — can carry hidden instructions. Input sanitization must happen at the tool layer, not upstream.
- **Naive prefix/path checks are not sandboxing.** The Filesystem MCP server escape, the Red Hat documented sandbox escape, and the `mcp-run-python` CVE-2026-25905 sandbox escape (lack of isolation between Pyodide and the host JavaScript environment) all shared the same failure mode: application-layer path checks in place of infrastructure-layer isolation. Use containers, separate IAM roles, and network policies — not string comparisons.
- **"It's internal only" is not a security boundary.** The `NeighborJack` exposure — thousands of MCP servers bound to `0.0.0.0` with zero authentication — demonstrates that internal-only assumptions collapse the moment an agent makes an outbound HTTP call or an attacker can reach a metadata endpoint. Every MCP server needs authentication regardless of intended network exposure.
- **The Supabase incident was a feature, not a bug.** The agent correctly processed the support ticket. The flaw was that privileged service-role credentials were accessible to a tool that processed untrusted user input. The fix is not better prompt engineering — it is architectural: untrusted input must never reach privileged tools without validation and confirmation gates.
