# S-1812 · The Failure Recovery Stack — When Your Agent Gets Stuck and Keeps Spending

You demo the agent. It works. You ship it. Three days later you find it has been looping on the same failed API call, burning $400 in 90 minutes — or $12,000 over a weekend, which has also happened. The agent did not crash. It did not alert. It kept working, confidently, in the wrong direction. That is the core difference between conventional software failure and agentic failure: the system does not stop, it just stops being right. And without deliberate, layered failure recovery design, it will not stop itself.

## Forces

- **Agents fail non-deterministically.** A conventional service throws an exception and stops. An LLM API returns a 429, a malformed JSON tool call, a hallucinated function signature, or simply times out after 90 seconds. The failure modes are probabilistic, not structural — and try/catch alone does not catch them.
- **Naive retry amplifies cost, not reliability.** Simple retry loops create thundering herds against struggling APIs. A single unhandled rate-limit error triggered an infinite retry against GPT-4 that burned $400 in 90 minutes on one team's production pipeline. Counting distinct error types instead of total iterations is a silent killer.
- **The blast radius grows with capability.** As Anthropic's engineering team noted: "Twelve months ago, we'd have rejected out of hand the idea of granting Claude access sufficient to take down an internal service. Today that level of access is routine." Higher capability means higher potential damage when failure occurs — containment is not optional.
- **Deloitte's 2025 data shows the gap.** 30% of organizations exploring agentic AI, 38% piloting — but only 14% with solutions ready for deployment and 11% actively using in production. Fault tolerance is a primary reason teams stall between pilot and production.

## The move

Build failure recovery as a layered system, not a single pattern. Each layer handles a different failure class:

1. **Retry with exponential backoff + jitter.** After a transient failure (429, timeout, network error), wait before retrying. Exponential backoff prevents thundering herd. Jitter (randomization) decorrelates parallel retry attempts. Cap the maximum delay and the maximum number of retries.
2. **Circuit breaker.** After N consecutive failures to the same provider or tool, open the circuit — stop calling it for a cooling window. This is the difference between a cascade and an incident. Track consecutive failures, not distinct error types. A financial services company lost $12,000 because their detector counted distinct error types: three days and 47,000 failed API calls later, the bill told the story.
3. **Fallback chain across providers.** Route to provider B when provider A fails persistently. Route to a mid-tier model for simple queries even when a frontier model is available — this builds resilience proactively. A two-provider system keeps running when either one breaks.
4. **Loop detection and forced strategy change.** Log every tool call. Track total iterations, not distinct errors. After the same action fails 3 times, force a strategy change — do not let the agent retry the same approach indefinitely. Verify actual state change, not LLM-reported confidence.
5. **Context compaction and overflow recovery.** When context windows overflow mid-session, compact rather than truncate — summarize the conversation state and continue. Do not restart and lose progress.
6. **Hierarchical supervisor / dead-end trap guard.** Parent agents monitor child agents. Watch for dead-end states (LLM-modified state machines with no outbound transitions) as distinct from infinite loops — dead-end states fail silently. Every non-final state must have at least one outbound transition.
7. **Human-in-the-loop escalation.** For high-stakes operations (financial actions, deletions, external sends), enforce human approval after N consecutive failures. This is the final safety net. Courts in the US documented hundreds of legal briefs containing hallucinated citations and fictional case law in 2024–2025, filed by lawyers who trusted generative AI without validation.
8. **Blast radius containment at the environment layer.** Anthropic's core principle: cap what the agent *can do*, not what it *does*. Sandbox environments, scoped permissions, egress controls, and audit logs — assume the model will occasionally fail and engineer the blast radius accordingly. Idempotency guards ensure retries cannot create duplicate side effects.

## Gotchas

- **Counting distinct error types instead of iteration count.** The financial services example is the canonical case: loop detection that tracks error *types* passes silently while the agent makes 47,000 retries. Track the *number of attempts at the same action*, not how many different errors occurred.
- **Trusting LLM confidence for state verification.** Agents report progress confidently even when failing silently. Magnus Müller at Browser Use puts it directly: verify actual state change, not LLM-reported confidence. If a click action says it succeeded, check whether the UI actually changed before proceeding.
- **No blast radius containment because "the model is reliable enough."** Anthropic's postmortem and containment architecture both reject this assumption. Capability and access expand over time; the probability of failure never reaches zero. Environment-layer caps — sandboxing, scoped permissions, idempotency guards — are the only reliable defense.
- **Restarting on context overflow instead of compacting.** Truncating context mid-session loses all intermediate state, forcing the agent to re-derive what it already knew. Context compaction (summarization + continuation) preserves progress and is the correct response to overflow.
- **Treating dead-end states the same as infinite loops.** Infinite loops are predictable; dead-end states fail silently. When an LLM modifies a state machine, it reasons locally — it may create a non-final state with no outbound transition, producing silent failure rather than visible repetition. Detect structural completeness, not just iteration count.
