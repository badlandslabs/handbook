# S-1000 · The Agent-Eval Stack — When You Can't Measure It, You Can't Fix It

When your agent ships but you have no idea whether it works 60% or 96% of the time — and production quietly gets worse after every model upgrade. The agent has no self-knowledge; you don't either.

## Forces

- **Traditional metrics don't capture agent behavior.** BLEU, ROUGE, and single-turn accuracy miss the point — an agent can get the right answer via the wrong reasoning, or the wrong answer via the right reasoning. You need to evaluate trajectories, not outcomes.
- **Production AI fails silently.** Agents don't throw exceptions — they get quietly worse. A model upgrade fixes 10% of cases and breaks 2%. Without an eval harness, you don't find out until a customer tells you.
- **Evaluation is undersized relative to development.** Most teams spend 80% of effort on prompts and 20% on evals — the inverse of what separates shipping products from demos. Hamel Husain (CodeSearchNet, GitHub CoPilot precursor) identifies this as the root cause of nearly all failed AI products.
- **Trajectory failures are invisible to outcome-only evals.** TRAJECT-Bench (Amazon, arXiv:2510.04550) shows that agents can reach correct final answers using incorrect tool selections, wrong parameterizations, or broken ordering — and pass standard benchmarks anyway. The process matters as much as the output.
- **Agents fail non-deterministically.** Unlike traditional software, agents don't fail with stack traces — they produce plausible-but-wrong outputs, call hallucinated tools, or loop indefinitely. Try-catch is insufficient; you need agentic self-correction.

## The Move

Build an evaluation harness that treats the agent as a system, not a model. The harness has four layers:

**Layer 1 — Define what "good" means before you build anything.** Hamel's practitioner hierarchy (hamel.dev/blog/posts/evals/): (1) does it do the right thing? (2) does it do it efficiently? (3) does it fail gracefully? (4) does it improve over time? Evals are tests — they outlast the model, framework, and prompt. An Arize guide (June 2026) echoes this: your eval infrastructure is the one thing that shouldn't change as everything around it does.

**Layer 2 — Evaluate trajectories, not just outputs.** Standard benchmarks check final answers. TRAJECT-Bench (Amazon, Michigan State, Hippocratic AI) evaluates three fine-grained trajectory dimensions: (1) **tool selection** — did the agent pick the right tool? (2) **parameterization** — were arguments correct? (3) **ordering** — was the sequence right? AlphaEval (arXiv:2604.12162, 2026) goes further: it evaluates complete agent products against 94 production tasks sourced from seven companies across six O*NET occupational domains, using multiple evaluation paradigms (LLM-as-Judge, reference-driven metrics, formal verification, rubric-based assessment, automated UI testing) per domain. This is the benchmark that maps to real business value.

**Layer 3 — Self-correcting loops built into the agent loop, not bolted on.** The failure taxonomy (GitHub AI System Design Guide, ombharatiya/ai-system-design-guide) identifies five agent failure modes: (1) hallucinated tools (calling tools that don't exist), (2) tool call errors (wrong parameters), (3) loops (repeating the same tool with no progress), (4) reasoning drift (losing the original goal), (5) context overflow (state grows unbounded). Self-correction in production means explicit state machines with routing loops: the agent decides whether to continue or correct based on a grading step. LangGraph's `interrupt` and checkpoint primitives enable this natively — you save state after each step, then resume from the last checkpoint on failure instead of restarting the whole trajectory. The pattern: **Think → Act → Grade → (correct if needed) → Loop**. Per the `agent_trajectory_evaluation` framework (abhiai-git, MIT 2025), adaptivity — the agent's ability to recover from tool failures — is a first-class evaluation metric, not an afterthought.

**Layer 4 — Multi-paradigm evals in CI.** InfoQ's evaluation guide (March 2026) recommends combining: (1) automated scoring (LLM-as-judge for reasoning quality, trace analysis for efficiency), (2) golden dataset regression testing (fixed inputs → expected outputs, versioned and maintained), and (3) human judgment for edge cases and safety. DeepEval, LangSmith, and `agent_trajectory_evaluation` each provide different tradeoffs: DeepEval for developer-friendly pytest integration, LangSmith for production trace visualization, the trajectory-eval package for academic rigor on tool-call fidelity. The requirement-to-benchmark framework from AlphaEval provides a systematic methodology: transform authentic production requirements into executable evaluation tasks in minimal time. This is the process most teams skip, and the reason most evals don't track what actually matters.

## Gotchas

- **LLM-as-judge is useful but not sufficient.** It scales cheaply but introduces reliability challenges — judges have their own biases and can be gamed. Use it for efficiency and reasoning quality, but keep ground-truth regression tests for safety-critical paths.
- **Golden datasets drift.** Production inputs change, and a stale golden dataset is worse than no eval — it gives false confidence. Treat your eval dataset like code: version it, review it, retire stale cases.
- **Self-correction loops need explicit loop detection.** Without a max-iteration guard and a way to compare current state against previous states, an agent can "correct" by cycling between wrong answers. LangGraph's checkpointing addresses this by letting you compare state snapshots.
- **Trajectory eval is expensive.** Running full trajectory analysis on every CI build can be cost-prohibitive. Tier your evals: fast smoke tests on every commit, full trajectory analysis on release candidates, production shadow-mode evals on sampled traffic.
- **Eval coverage ≠ production coverage.** AlphaEval's key insight is that benchmark tasks are retrospectively curated with automatable metrics — they don't capture the implicit constraints, heterogeneous inputs, and evolving expert standards of real production work. Shadow mode on live traffic is the only way to catch what your test suite misses.
