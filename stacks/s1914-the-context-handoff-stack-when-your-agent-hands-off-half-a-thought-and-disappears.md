# S-1914 · The Context Handoff Stack — When Your Agent Hands Off Half a Thought and Disappears

Your multi-agent pipeline runs three agents in sequence: a researcher, a drafter, and an editor. In staging it works. In production, the drafter consistently produces outputs that ignore the researcher's key findings — not because the drafter is weak, but because the handoff message arrives as a 2,000-token wall of text with no structure, no priority signal, and no explicit citation. The drafter reconstructs what it thinks mattered. It guesses wrong. This is the context handoff problem: the hardest part of multi-agent systems is not orchestration logic — it is what you pass between agents.

## Forces

- **Context accumulates as noise.** Each agent in a pipeline adds to the shared state. By the time the third agent receives the message, the relevant findings are buried under conversation history, intermediate reasoning, and tool-call artifacts. Reddit practitioners report this visibly by step 5–6 of any multi-step workflow: "the accumulated history has become noise." The model loses track of the original goal not because it forgot, but because the signal-to-noise ratio collapsed.
- **Token duplication multiplies cost.** Different frameworks show dramatically different duplication rates: MetaGPT 72%, CAMEL 86%, AgentVerse 53%. In a 3-agent pipeline, this means the same context is re-encoded 2–3 times per step. At scale, this is not a latency problem — it is a cost and throughput problem.
- **Handoffs are underspecified.** Most orchestration code passes entire message histories between agents. What the receiving agent actually needs is a structured summary: what was found, what remains unverified, what the output format should be. Without this contract, the receiver infers intent — and inference fails.
- **Supervisor agents become bottlenecks.** A single orchestrator that routes to specialists introduces a single point of failure. If the supervisor misroutes or the routing prompt degrades under load, every downstream agent works on the wrong task.
- **Agents have no concept of "done."** Multi-agent systems frequently fail to converge because no agent owns the termination signal. Each agent keeps going or stops at an arbitrary step count. Explicit exit conditions per agent — treating it like a state machine, not a conversation — is the fix.

## The move

Design handoffs as structured state objects, not message appends.

- **Pass structured summaries, not raw histories.** The handoff payload should contain: (1) findings in bullet format, (2) confidence level per finding, (3) outstanding verification items, (4) explicit output specification for the next agent. This is 200–400 tokens regardless of how many steps preceded it.
- **Use a checkpoint journal for recovery.** When a step fails, the receiving agent picks up from the journal rather than replaying everything. This requires each agent to write its state before calling the next, and the orchestrator to check the journal on restart. CodeX-Verify runs full trace replay in under 200ms per sample — the cost is real but bounded.
- **Gate multi-agent on evidence, not architecture aesthetics.** Rule out first: context compression, better tool design, parallel tool calls, structured output with post-processing. Multi-agent is justified only when the task genuinely requires independent parallel reasoning, or when different agents are optimized for different subtasks (e.g., a coding-specialized model vs. a reasoning-specialized model).
- **Treat agents as state machines with explicit transitions.** Each agent has: an entry condition (what must be true before it runs), a success condition (what constitutes a valid output), and an exit condition (when to return control to the orchestrator). The orchestrator checks transitions, not messages.
- **Fan-out for parallelism, sequential for dependency.** Map-reduce patterns work when sub-tasks are independent. Sequential pipeline works when each step's output is the next step's input. Mixing these — trying to parallelize dependent steps to save latency — produces the worst of both worlds.
- **Route on task type, not on capability.** Supervisor routers should classify by task category (research, drafting, review) rather than by which agent is "smarter." Capability-based routing introduces nondeterminism; type-based routing is auditable and debuggable.

## Gotchas

- **Passing raw message history between agents re-introduces the context problem you were trying to solve.** If each handoff sends the full accumulated history, you have traded a single context overflow for a cascading one. Always compress before handoff.
- **Supervisor routing degrades under load.** A supervisor that works correctly at 100 requests/day may misroute at 10,000/day because its routing prompt was never tested at that scale. Test at 10x expected load before calling it production-ready.
- **Idempotency is not optional.** If agent B receives a partial result from agent A and crashes before writing its checkpoint, you need a deterministic replay path — not a "retry from start" that re-runs A and doubles your cost. Build this before you need it.
- **Diminishing returns are real.** CodeX-Verify data shows the accuracy jump from 1→2 agents is +39.7pp; the jump from 3→4 agents is only +11.2pp. Most teams add agents until they run out of budget, not until accuracy stops improving. The optimal count is usually 2–3 specialists, not 5+.
