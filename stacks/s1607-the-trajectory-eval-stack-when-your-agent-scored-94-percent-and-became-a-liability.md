# S-1607 · The Trajectory Eval Stack — When Your Agent Scored 94% and Became a Liability

Your eval suite says 94%. Your agent approved $180,000 in unauthorized refunds last quarter. The eval only checked the final answer — not the tool call sequence, not the reasoning path, not whether the agent got lucky on a 10-case test set. The score was real. So was the failure. This is the stack for measuring how an agent works, not just whether it ends well.

## Forces

- **Final-answer scoring hides reckless paths.** An agent can reach the right answer by calling the wrong tool first, ignoring guardrails, and recovering by accident. On a small eval set this passes. In production it compounds into a cost blowout or security incident.
- **Agents are probabilistic; the same input can produce different trajectories.** A single-pass exact-match test assumes determinism that doesn't exist. You need multiple trials and variance tracking, not one-shot assertions.
- **Trajectory quality is harder to measure than outcome quality.** Checking "did the agent land on the right answer" is a regex. Checking "did the agent take a sound reasoning path" requires either ground-truth trajectories or an LLM judge — both of which are expensive and non-trivial to build.
- **Eval suites drift from production.** Teams write evals against known failure modes, then the agent gets better at those cases while regressing on edge cases nobody thought to test. Without production traffic in the eval loop, you optimize for a moving target.
- **Tool selection is the first unmeasured failure point.** Most evals score the final output. They never check whether the agent chose the right tool — and a wrong tool choice cascades downstream into garbage results that look locally coherent.

## The Move

The core technique is **trajectory-first evaluation**: score the reasoning path, not just the destination. Combine deterministic trajectory matching (where you know the expected tool sequence) with LLM-as-judge scoring (where you don't) across five evaluation dimensions.

### Specific implementation pattern

- **Capture full trajectories as first-class outputs.** Every agent run should emit a structured log: input → tool calls → intermediate outputs → final answer. Treat trajectories as test artifacts, not debug dumps.
- **Use trajectory match for deterministic workflows.** When you know the exact tool sequence expected (e.g., a rigid multi-step API flow), hard-code the reference trajectory and compare step-by-step. This is fast, deterministic, and free — no extra LLM calls. Tools like LangChain's `agentevals` and `abhiai-git/agent_trajectory_evaluation` support this natively.
- **Use LLM-as-judge for open-ended or multi-path tasks.** When multiple valid trajectories exist, or when reasoning quality matters more than tool sequence, prompt a second LLM to score the trajectory on a rubric. Target ≥0.80 Spearman correlation with human judgment — calibrate before gating on it.
- **Evaluate across five dimensions, not one.** Anthropic's framework (Correctness, Groundedness, Safety, Trajectory, Efficiency) maps to: does it get the right answer? Is it supported by evidence? Did it violate policy? Did it follow a sound path? Did it use tokens efficiently?
- **Run multiple trials per task.** A single run gives you one point on a distribution. Run 3–5 trials per test case and track variance — a high-variance agent is a production risk regardless of its mean score.
- **Seed evals with production traffic.** Every production failure becomes a regression test. Build a pipeline that converts real failure cases into eval cases automatically. This closes the eval-drift gap faster than any curated test set.
- **Gate CI on trajectory metrics, not just pass/fail.** Track tool-selection accuracy, step efficiency, and hallucination rate as separate metrics with their own thresholds. An agent that gets the right answer by hallucinating evidence should fail even if the final answer is correct.

## Gotchas

- **LLM judges have biases.** Judges are themselves LLMs and can be over-permissive, biased toward longer responses, or unable to catch subtle reasoning errors. Calibrate judge prompts against human-rated samples before relying on them for pass/fail decisions.
- **High-variance agents fail silently in low-trial evals.** If your agent's score varies from 60–95% across 5 trials, the mean is meaningless. The variance itself is the signal — a high-variance agent needs variance-reduction (better prompts, constrained reasoning, tool specification) before it goes to production.
- **Eval suites develop survivorship bias.** If you only add test cases when something breaks in production, you never test for failures you haven't seen. Complement production-seeded cases with adversarial cases built by a separate team or generated via prompt injection / red-teaming.
- **Efficiency and correctness trade off.** An agent that takes 3x more tool calls to reach the right answer will score well on trajectory match and poorly on efficiency. You need both dimensions tracked separately and weighted by business priority — a correct-but-wasteful agent can be more expensive than an incorrect one.
- **Trajectory match fails for agents with valid multiple paths.** If your agent has genuinely different valid approaches to the same input, trajectory matching against one reference path will give false negatives. Switch to LLM-as-judge or criterion-based scoring (e.g., "did it use at least one search tool") rather than exact sequence matching.
